- [story] A core-banking outage will show a 503 on a **transaction read or new dispute raise**, not on `/health/ready` or dispute history ([AD-21 and AD-25](docs/architecture/architecture.md)). Specify the request and its expected `core-banking-unavailable` problem.

## Standards
- [decision] A manual release should use a controlled PostgreSQL transaction and a targeted, verified update—not an invented “release” HTTP endpoint or a blanket status reset. Document the permitted operator exception to AD-22 first ([PostgreSQL transactions](https://www.postgresql.org/docs/current/tutorial-transactions.html); [UPDATE](https://www.postgresql.org/docs/current/sql-update.html)).
- [story] Use Docker Compose’s documented [`up`](https://docs.docker.com/reference/cli/docker/compose/up/) and [`down -v`](https://docs.docker.com/reference/cli/docker/compose/down/) behavior. No other new mechanism is implied by these docs.

## Resolution

Sofia, 2026-10-30. The four `[decision]` points (no release operation, who may change a `Failed` row, the standard for a manual release, criterion 2 not testable) are settled by the human decision above: AD-22 now names the operator exception, and criterion 4 gives the precondition (`Status = 'Failed'`, the event ID from the failed-row log line), the fields that change (`Status`, `Attempts`, `NextAttemptAtUtc`; `Payload` and every other column unchanged), the `UPDATE 1` check before `COMMIT`, and the proof (row `Sent`, its offset below its successor's on the topic).
