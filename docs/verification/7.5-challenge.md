## 1. Pre-mortem
- [story] The workflow reports a successful deployment when SSM has only **accepted** Run Command, while `docker compose up -d --wait` later fails. It must wait for the command invocation’s terminal status.
- [story] The stack starts but sign-in fails: the current Compose and nginx files hard-code local hosts, HTTP forwarding, and loopback-bound gateway ports. Story 7.4’s override and gateway changes must be proven together with 7.5’s CloudFront configuration.
- [story] The first deploy fails at database initialization. `infra/db/10-roles-and-databases.sh` is a PostgreSQL container first-start script; the story does not specify how its roles and databases are initialized on RDS.

## 2. Simplest design
- [story] Keep AD-28’s single `envs/dev` root and named modules. Bootstrap the state bucket separately; apply Terraform locally; have the manual, main-branch OIDC workflow send a pinned image-digest deployment to EC2 and **wait for SSM’s result**. Retrieve SecureStrings on the instance, write a restricted `.env`, and fail deployment on any missing value or unhealthy service. Do not add an ALB, NAT gateway, deployment controller, or CI-side Terraform apply.

## 3. Assumptions
- [story] The account can run the specified instance and RDS class within its intended cost envelope. Architecture’s open questions explicitly say eligibility and sizing are unchecked; a budget alert is not a spending limit.
- [story] GHCR images will be pullable by the instance. AD-32 specifies digest-based deploys, but neither this story nor the existing CI workflow defines registry visibility or instance authentication.
- [story] The instance can reach SSM, GHCR, and package sources while RDS remains private. The story names no outbound route or connectivity check.

## 4. Standards
- [story] Treating `aws ssm send-command` success as deployment success would invent a success signal. Use [Systems Manager command status monitoring](https://docs.aws.amazon.com/systems-manager/latest/userguide/monitor-commands.html), checking the invocation’s terminal status and failure output.
- [story] A mock Terraform test is not a substitute for an applied environment. [Terraform provider mocks](https://developer.hashicorp.com/terraform/language/tests/mocking) exercise configuration without proving AWS eligibility, routing, cost, or teardown. Keep those as explicit human checks rather than recording them as passed.

## 5. Gaps
- [decision] Criterion 7 allows the story to close without AWS, but the epic’s “Done when” still requires the environment to **deploy and destroy cleanly**. Reconcile what “closed” means under the recorded fallback decision; mock validation cannot satisfy that epic outcome.
- [story] Criteria 1–6 mostly say “when read.” Add executable assertions for the OIDC trust conditions, least-privilege SSM/KMS paths, digest selection and rollback SHA bounds, SSM failure propagation, private RDS access, and absence of public ports other than the intended origin.
- [story] Specify who creates the state bucket and SecureStrings, how missing parameters and an existing `.env` are handled, and whether Terraform ever holds secret values in state. “Values come from SSM” alone does not establish a safe bootstrap or failure path.
- [story] State the budget amount, period, alert threshold, recipient, and how the alert is verified. `include_credit = false` alone cannot demonstrate that an alarm will notify anyone.

Sofia, 2026-10-30. The `[decision]` point (closing without AWS against the epic's "deploys and destroys cleanly") is settled by decision 1: the story closes on criteria 1 to 7 run against `mock_provider "aws"` and the written procedure of criterion 8, which says at its top that it has not been run; the `Unknown` gate is removed and `hitl` is false; the production-path note is an Input line for story 7.6. `[story]` points folded:

- SSM acceptance is not success: `deploy.yml` waits with `aws ssm wait command-executed` and fails unless the invocation's status is `Success`, printing its standard error (criterion 5).
- Local hosts and HTTP forwarding: story 7.4's override and AWS template are this story's inputs; their joint proof over CloudFront is a post-deploy check in the written procedure (criterion 8).
- RDS initialization: the deploy script runs `infra/db/10-roles-and-databases.sh` against RDS with `verify-full` only when the `disputedesk` role is absent (criterion 6).
- Executable assertions instead of reading: `terraform test` plans assert the OIDC trust conditions, the least-privilege SSM, KMS and Run Command permissions, the private RDS, the only ingress, and the absence of NAT and load balancers (criteria 2 to 5, 7); `deploy.test.sh` proves the script's failure paths with stubs (criterion 6); the `sha` input is bounded to 40 lower-case hex characters and an unpublished SHA fails before the SSM command (Inputs, criterion 5).
- Bootstrap and secrets: a `bootstrap` root creates the state bucket; a person creates the listed SecureStrings; Terraform holds exactly two secrets in state (origin-verify value, RDS master password), named as a shortcut with its upgrade; a missing parameter fails before any `docker` call and `.env` is replaced atomically with mode 0600 (criteria 1, 4, 6; Notes).
- Registry access and outbound route: the GHCR packages are public (Assumption) and the instance has an internet gateway route to SSM, GHCR and `ip-ranges.json`, with no NAT (criterion 2).
- Budget: amount, period, both alert thresholds, recipient and `include_credit = false` are asserted; confirming the email is a written step (criteria 7, 8).
- Mocks are not an applied environment: kept explicit; every AWS-only check is in the written procedure, never recorded as passed (criterion 8, Boundaries).
