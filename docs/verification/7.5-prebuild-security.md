# 7.5 pre-build security (status: findings; 2 decisions)

What already holds:
- The OIDC trust is pinned to `sub` = `repo:<repo>:ref:refs/heads/main` and `aud` with `StringEquals`.
- There is no IAM user and no access key.
- IMDSv2 is required.
- The only ingress is from the CloudFront prefix list.
- RDS is private and encrypted.
- `.env` is written atomically with mode 0600.

- **S7.5-1 medium [story] `AWS-RunShellScript` makes the deploy role root on the instance.**
  - Fix:
    - Terraform creates an `aws_ssm_document` (Command, schema 2.2) whose one step checks out `{{sha}}` and runs `infra/aws/deploy.sh` with String parameters that carry an `allowedPattern`: `^[0-9a-f]{40}$` for the SHA, and `^ghcr\.io/[a-z0-9-]+/disputedesk-[a-z-]+@sha256:[0-9a-f]{64}$` for each image.
    - `ssm:SendCommand` lists only that document and the instance.
  - Standard: AWS SSM document syntax (`allowedPattern`); restricting Run Command by document; ASVS 5.0 V8 and V2.2.
  - Builder must test: plan assertions on the SendCommand resources and the parameter patterns. Supervisor break: putting the `AWS-RunShellScript` ARN back fails the test.

- **S7.5-2 medium [story] Workflow input injection and overlapping deploys.**
  - Fix:
    - `inputs.sha` and the resolved digests reach scripts only through `env:`, never as `${{ }}` inside `run:`, and are validated first.
    - Add `concurrency: { group: deploy-dev, cancel-in-progress: false }` so two deploys never interleave.
  - Standard: GitHub, *Security hardening for GitHub Actions*, intermediate environment variable.
  - Builder must test: `actionlint` passes; `deploy.yml` has no `${{` inside any `run:`.

- **S7.5-3 medium [story] `deploy.sh` writes everything under `ssm_path` into `.env`.**
  - Problem: "every parameter under `ssm_path`" includes the RDS master password, and the Data Protection key ring XML too if that path is nested.
  - Fix:
    - `deploy.sh` reads an explicit allow-list of names, exactly 7.4's Inputs, and fails naming the first one missing.
    - It reads the master password separately, only for the one-time init, and passes it to psql as `PGPASSWORD`: never in argv, never in `.env`.
    - The key-ring path is a separate root, for example `/disputedesk-dataprotection/dev`.
    - Each value is checked against its bound (S7.4-6).
  - Standard: ASVS 5.0 V13.3 and V8.
  - Builder must test: a stub that returns extra parameters leaves them out of `.env`; a value outside its bound exits before any `docker` call; a plan assertion shows the key-ring path is not under `ssm_path`.

- **S7.5-4 medium [story] The deploy's standard error ends up in a public log.**
  - Problem: `deploy.yml` prints the invocation's standard error into the GitHub log, which is public for this repo. The story's test checks standard output only.
  - Fix: check both streams. No `set -x`; never print `.env`, `docker compose config` or `docker compose logs`.
  - Standard: ASVS 5.0 V16.2 and V13.3.
  - Builder must test: `deploy.test.sh` greps both stdout and stderr of every failure path for every stubbed secret.

- **S7.5-5 medium [story] `QA_DB_PASSWORD` is missing.**
  - Problem: `infra/db/10-roles-and-databases.sh` reads `\getenv qa_password QA_DB_PASSWORD`, but neither 7.4 nor 7.5 lists it. That invites a dev-only default or a broken init.
  - Fix: add it as a SecureString with the S7.4-6 bound, list it in the README, and add it to the allow-list.
  - Unverified correctness risk: on RDS the master user is `rds_superuser`, not a superuser, so `CREATE DATABASE … OWNER disputedesk` may need role membership. This only shows on a real apply; add it to the post-deploy checks.
  - Builder must test: `deploy.test.sh` fails when it is missing.

- **S7.5-6 medium [story] The maintainer's sign-in must use short-lived credentials.**
  - Fix: the README's administrator sign-in is IAM Identity Center with MFA and `aws sso login`. The root user has MFA and no access keys. No `aws iam create-access-key`, and no static keys in `aws configure`.
  - Standard: AD-28 (no long-lived keys); CIS AWS Foundations Benchmark, IAM section; AWS IAM best practices (temporary credentials for people).
  - Builder must test: the reviewer reads the README, and a grep finds no access-key commands.

- **S7.5-7 low [story] OIDC details.**
  - `deploy.yml` declares no `environment:`, because one would change `sub` to `repo:…:environment:<name>`. If the human wants a required-reviewer environment, pin `sub` to that environment instead.
  - Provider `client_id_list = ["sts.amazonaws.com"]`; `max_session_duration` 3600; `role-session-name` includes the run ID.
  - `sub` pins the branch, not the workflow. Customising the subject claim with `job_workflow_ref` goes in `docs/production-path.md`.
  - Standard: GitHub OIDC docs (example subject claims; customising subject claims).
  - Builder must test: a plan assertion that the trust has no `StringLike`.

- **S7.5-8 low [story] KMS.**
  - Fix:
    - One customer-managed key with `enable_key_rotation = true`, which the README's `put-parameter --key-id` names.
    - `kms:Decrypt` is conditioned on `kms:ViaService = ssm.<region>.amazonaws.com`.
    - `kms:Encrypt` is limited by `kms:EncryptionContext:PARAMETER_ARN` to the key-ring path.
  - Standard: AWS KMS, *How Parameter Store uses AWS KMS*.
  - Builder must test: plan assertions on the conditions.

- **S7.5-9 low [story] The managed policies are broader than the stated least privilege.**
  - `AmazonSSMManagedInstanceCore` reads every parameter in the account, and `CloudWatchAgentServerPolicy` can write to any log group. The README should say so: it is a dedicated account. Put AWS's documented minimal instance policy in `docs/production-path.md`. This goes with S7.4-8.

- **S7.5-10 low [story] State and committed files.**
  - Check whether the pinned providers support write-only arguments (`aws_db_instance.password_wo` and `aws_ssm_parameter.value_wo` with an ephemeral `random_password`, Terraform 1.11 or later). If they do, state holds only the origin-verify value.
  - The state bucket also gets a policy that denies `aws:SecureTransport = false`, plus `BucketOwnerEnforced`.
  - `.gitignore` gains `*.tfvars` (with `!*.tfvars.example`), because `budget_alert_email` is personal data. Pass it through `TF_VAR_`; tests use `example.com`.
  - Standard: Terraform, *Sensitive data in state* and write-only arguments; S3 security best practices.

- **S7.5-11 low [decision] Viewer TLS and no WAF.**
  - The default `*.cloudfront.net` certificate keeps the minimum viewer protocol at TLSv1 (ASVS 5.0 V12.1.1). Raising it needs a domain and an ACM certificate. There is no WAF either. Both go in `docs/production-path.md`. Origin HTTP is S7.4-9.

- **S7.5-12 low [story] The realip file can silently come out empty.**
  - Fix: `deploy.sh` fails closed if `ip-ranges.json` cannot be fetched or yields zero `CLOUDFRONT_ORIGIN_FACING` IPv4 ranges. Otherwise every client shares the edge address in rate limits and audit.
  - The README notes that the file can drift from the managed prefix list until the next deploy.
  - Builder must test: a stub with an empty list exits before Compose runs.

- **S7.5-13 low [story] Tightening.**
  - Security-group egress limited to 443, plus 5432 to the DB security group.
  - Assert `rds.force_ssl = 1`.
  - `deploy.yml` checks each digest's revision label against the SHA (with S7.3-2).

## Resolution

Sofia, 2026-10-30, with the human's decisions of 2026-10-30 on the `[decision]` points. The story keeps 8 criteria.

- S7.5-1: an `aws_ssm_document` with `allowedPattern` parameters; `ssm:SendCommand` only on it and the instance; a supervisor break restores `AWS-RunShellScript` (criterion 5).
- S7.5-2: `sha` and digests through `env:` only; `concurrency` group `deploy-dev` (criterion 5; Inputs).
- S7.5-3: an allow-list of names; the master password read separately into `PGPASSWORD`; the key ring under its own root `dataprotection_ssm_path`; each value checked against its bound (Inputs; criterion 6).
- S7.5-4: the test greps stdout and stderr; no `set -x`, no print of `.env`, the Compose config or logs (criterion 6).
- S7.5-5: `QA_DB_PASSWORD` is a SecureString on the allow-list with the 7.4 bound; its absence fails the test; the `rds_superuser` ownership check is in the post-deploy checks (Inputs; criteria 6 and 8).
- S7.5-6: IAM Identity Center with MFA and `aws sso login`; root MFA, no access keys (criterion 8).
- S7.5-7: no `environment:`, `client_id_list`, `max_session_duration`, a run-ID session name, no `StringLike` (criterion 5); the `job_workflow_ref` subject claim goes to the production path through story 7.6's Notes.
- S7.5-8: one customer-managed key with rotation; `kms:ViaService` and `kms:EncryptionContext:PARAMETER_ARN` conditions (criterion 7).
- S7.5-9: the README says the managed policies are broad and the account dedicated (criterion 8); the minimal instance policy goes to the production path through story 7.6's Notes.
- S7.5-10: write-only arguments for the master password where the pinned provider has them; state bucket `aws:SecureTransport` deny and `BucketOwnerEnforced`; `*.tfvars` ignored and the email through `TF_VAR_` (criterion 1; Inputs; Touches).
- S7.5-11 [decision], human: accepted; the default certificate's TLS 1.0 minimum and no WAF go to the production path (story 7.6's Notes), and the README says so (criterion 8). Origin HTTP is S7.4-9: plain HTTP stays, marked `# shortcut:` in Terraform (criterion 4).
- S7.5-12: `deploy.sh` fails closed on an empty or unfetchable range list, tested before Compose runs; the README notes the drift (criteria 6 and 8).
- S7.5-13: egress limited to 443 and 5432 to the database (criterion 2); `rds.force_ssl = 1` (criterion 3); the revision label checked against `sha` (criterion 5).
- From 7.4: the third (mail) distribution and `MAILPIT_HOST` (S7.4-1, criterion 4); the `DOCKER-USER` rule with its test (S7.4-8, criterion 6); value bounds before `.env` (S7.4-6, criterion 6); the README's fixture-login statement (S7.4-11, criterion 8).
