## 1. Pre-mortem
[story] A policy changes meaning during conversion because Terraform inserts a value into a JSON string without JSON-escaping it. The existing Terraform tests pin the six current policies, but only for their fixture values; future input values could still break rendering.

[story] A new policy bypasses name validation. jq reads the templates, but criterion 2 also promises to discover *every* policy attribute in HCL while forbidding the line-based HCL parsing used today.

[story] The first deploy fails to assume its role because the recorded OIDC API check describes configuration, not a token issued to the deploying job. The removed jobs previously compared an issued `sub` with Terraform’s value.

## 2. Simplest design
[story] Put the six existing documents in adjacent JSON templates, keep the SSM document as `jsonencode()`, extract names with jq, and reuse the existing reference checks and unchanged Terraform policy assertions. Remove the shell harness and two OIDC jobs; document the repository configuration check **before first deployment**. Do not recreate a general-purpose HCL parser in the xUnit test.

## 3. Assumptions
[story] The story assumes interpolated values remain safe inside JSON strings. Current examples are ARNs, paths, IDs and a subject; the stated input bounds do not establish that *all future values* are JSON-string-safe. Terraform’s [`templatefile()` guidance](https://developer.hashicorp.com/terraform/language/functions/templatefile) recommends `jsonencode` when generating JSON.

[story] It assumes the repository OIDC configuration still produces the pinned subject. Story 7.15 records an earlier API result and issued-token check; neither an unchanged Terraform assertion nor the proposed API command alone checks a newly issued token.

## 4. Standards
[story] Discovering arbitrary Terraform policy attributes with text or regex rules would retain the non-standard HCL parser this story removes. Either limit the guarantee explicitly to the six known attributes and test their rendered values, or use an [HCL parser](https://github.com/hashicorp/hcl) if exhaustive discovery of future HCL policy declarations is essential. Avoid adding that dependency merely to preserve a broader claim than the current slice needs.

## 5. Gaps
[story] Criterion 2 needs a precise scope: does “no action or no key is found” mean across the tree or per template? The compute trust policy has no condition key, so a per-template interpretation cannot pass. It also needs a test for a new policy whose attribute is not written on the expected line.

[story] Criterion 5 states a five-minute whole-check limit, but moving the fetch into the 15-minute `platform` job removes the existing five-minute CI step timeout. Require a whole-check cancellation deadline, including retries, and a failure that names the interrupted URL.

[story] Criterion 7 should say which API fields must be checked—particularly `use_immutable_subject` and `sub_claim_prefix`—what mismatch stops the first deploy, and when to repeat the check after a repository or OIDC-configuration change. The [repository endpoint](https://docs.github.com/en/rest/actions/oidc?apiVersion=2022-11-28#get-the-customization-template-for-an-oidc-subject-claim-for-a-repository) returns configuration fields, not the deploying job’s actual `sub`.
