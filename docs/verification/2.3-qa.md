## Findings

1. **Blocker, low effort: a non-numeric, empty or repeated `limit` returns 500 (AC3 input validation).** `GET /api/v1/transactions?limit=abc`, `?limit=` and `?limit=20&limit=30` return 500 `...:problem:internal`. The api logs `fail: UnhandledExceptionHandler ... BadHttpRequestException: Failed to bind parameter "Nullable<int> limit"`. Client input must be 400 `validation` naming `limit`, and a 500 here is an alert-noise bug. Fix: bind `limit` as a string and parse it in the endpoint, or map `BadHttpRequestException` to the 400 validation problem in the exception handler. The e2e test `a non-numeric limit is 400 validation, not a server error` fails today and goes green with the fix.
2. **Low: a very long cursor gives 503, not 400.** A cursor of 2000 or more characters reaches core banking, which answers 400, and the api reports 503 `core-banking-unavailable` ("Core banking is unavailable"). Cursors up to 1000 characters give 400. A real cursor is 14 characters, so cap the cursor length at the boundary (400 `errors.cursor`).
3. **Low, carried over from 2.2: `Accept: text/html` on an anonymous call gives a `text/plain` 401** ("Status Code: 401; Unauthorized"), not the problem body. Fetch from the SPA sends `*/*`, which gets the problem body, so not blocking.
4. Observations, no action: duplicate `X-Content-Type-Options` and `Referrer-Policy` headers (gateway plus Api); every authenticated response refreshes the session `Set-Cookie` (sliding expiry); the 403 and 401 responses are `no-store` as the security fix intended; `/api/v1/Transactions` and a trailing slash route to the same endpoint (routing is case-insensitive).
5. First start of the api after `compose up` logged one `Health check postgres ... Unhealthy` because `compose up` restarted Postgres first; readiness recovered. Not story-related.
