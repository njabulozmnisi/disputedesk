## Findings

1. **Low, accepted by the human (fix round decision): Radix `AlertDialog` scroll lock is blocked by the gateway CSP.** With the gateway's `style-src 'self'` added to the document, opening the inactivity dialog logs `Applying inline style violates the following Content Security Policy directive 'style-src 'self''` (twice in the run). The dialog works and axe is clean, but the injected `<style>` is dropped, so `body` keeps `overflow: visible` and the page behind can scroll while the dialog is open. `vite preview` sends no CSP, so this is shown only by the test's added header; nginx will behave the same once 2.5 serves the SPA. The decided `// shortcut:` comment is not in the source yet (grep of `frontend/src` finds no mention); the check stays in `e2e/` as an annotation, not an assertion, so a future nonce or CSP change does not break the run.
2. **Informational: the not-found copy is dispute-specific.** Every unbuilt route, including `/link` (where an unlinked customer lands from `/`), shows "We can't find that dispute. Check the link, or find it in your disputes. Go to your disputes", and that button goes to `/disputes`, which is not built and shows the same screen. This is what the story and mockup say; it reads oddly for C until the linking story lands.
3. **Informational: first Tab after a load skips the header.** Each route change and load focuses the page `<h1>`, so the first Tab goes to the first control after it (a Dispute link) and the logo and Sign out come after the tab bar in the wrap-around. Everything is reachable in reading order and there is no skip link; axe's bypass rule passes through landmarks. Shift+Tab reaches the header.
4. **Informational, pre-existing: duplicated security headers** on API responses through the gateway (`x-content-type-options: nosniff, nosniff`, two `Referrer-Policy` values), as noted in 3.1's QA. Not from 2.4.
5. **Repaired in `e2e/` (QA-owned, not a 2.4 defect): two assertions of `transactions.spec.ts` broke on 3.1's data.** (a) `row fields` rejected `/\d{10}/` in the JSON, which matched the random tail of a dispute UUID in the new `disputeId` field; UUIDs are now removed first, the check for full account, card and ID numbers is unchanged. (b) It expected exactly `{notEligible, outsideWindow}` as reasons; customer A now has disputes, so `alreadyDisputed` appears; it now requires the first two and rejects any value outside the three. Both failed before any 2.4 test ran.
