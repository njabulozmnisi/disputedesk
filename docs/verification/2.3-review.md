## Rework to the documented mechanisms (after a standards audit)

A standards audit found three home-grown mechanisms in the approved version; all three were replaced before merge, and every stage ran again.

| Before | After (documented form) | Source |
|---|---|---|
| Endpoint filter on the default policy resolving the customer | `Linked` authorization policy: cookie scheme named, `RequireAuthenticatedUser`, `LinkedCustomerRequirement` with a scoped handler that sets `CurrentCustomer`, and an `IAuthorizationMiddlewareResultHandler` writing 403 `linking-required` for that failed requirement (AD-10 amended) | [Policies](https://learn.microsoft.com/aspnet/core/security/authorization/policies), [Customize AuthorizationMiddleware](https://learn.microsoft.com/aspnet/core/security/authorization/customizingauthorizationmiddlewareresponse) |
| `limit` bound as a string and parsed in Application | `[Range(1, 50)] int limit = 20` with built-in validation; authorization runs before binding, so 403 still comes before 400 | [Minimal API validation](https://learn.microsoft.com/aspnet/core/fundamentals/minimal-apis#validation-support-in-minimal-apis) |
| Seed called by `DatabaseMigrator` after migrating, outside the lock | `UseAsyncSeeding` and `UseSeeding`, run by `MigrateAsync` inside EF's migration lock, with a downgrade guard (AD-30 amended) | [Data seeding](https://learn.microsoft.com/ef/core/modeling/data-seeding) |
