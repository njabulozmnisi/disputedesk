## Answers to the focus questions

**1. Can someone outside the trusted network spoof the client IP?** No.
- Every gateway location that proxies to the api overwrites `X-Forwarded-For` with `$remote_addr`, and sets `Host` and `X-Forwarded-Host` to the fixed `${GATEWAY_APP_HOST}` and `X-Forwarded-Proto` to `$scheme`. This is in `infra/nginx/templates/nginx.conf.template`, lines 73-134.
- The api publishes no host port. The only published ports are postgres, redpanda, mailpit, the aspire dashboard and the gateway, all on 127.0.0.1.
- In the Api, `KnownProxies` and the loopback `KnownIPNetworks` defaults are cleared. Only `ForwardedHeaders:TrustedNetwork` is trusted, `ForwardLimit` is 1, and For, Proto and Host are processed.
- No `ASPNETCORE_FORWARDEDHEADERS_ENABLED` or second forwarded-headers setup exists anywhere in the tracked files.
- `Connection.RemoteIpAddress` is used only by 6.1's `LinkingEndpoints.ClientIp`. No gate anywhere uses `RequireHost` or an IP check that the new trust could open.

**2. Can a chain longer than one hop get through?** No. `ForwardLimit` 1 takes only the rightmost entry, and the test `Start_ForwardedForFromInsideTheTrustedNetwork_AuditsTheForwardedAddress("192.0.2.1, 203.0.113.9")` covers it. The gateway also replaces the client's chain rather than appending to it. ASP.NET Core does not read the RFC 7239 `Forwarded` header, and `X-Forwarded-Prefix` is not enabled.

**3. Can a forged Host change the OIDC `redirect_uri` or another absolute URL?**
- **Through the gateway:** no. The app origin is nginx's `default_server` and always sends its fixed Host and `X-Forwarded-Host` upstream.
- **From inside the network:** an `X-Forwarded-Host` other than the allowed host is ignored. The tests cover `attacker.example`, `attacker.example:8080` and `localhost.attacker.example`.
- **Other absolute URLs:** the only ones the Api builds are the OIDC `redirect_uri` and `post_logout_redirect_uri`. Zitadel checks both against the fixed lists registered in `infra/zitadel/provision/provision.sh` (lines 139-157), so a forged host is bounded at the identity provider too. `returnUrl` is still checked with `IsLocalUrl`.

**4. Host filtering and the health check.** Host filtering stays `"*"`, as the story decided. The health check (`wget 127.0.0.1:8080/health/ready`) comes from loopback, which is no longer trusted, so it simply carries no forwarded headers. The builder's smoke check showed the stack healthy.

**5. Is the subnet the narrowest range that works?** `/24` is narrow, and the human decision trusts the whole Compose network. The production narrowing is recorded as an input to story 7.6, and the AWS value is story 7.4's. The architecture test proves the pinned subnet equals the configured range. One gap is L3 below.

**6. Do any logs still record tokens, codes or secret query strings?**
- **Identity origin access log:** fixed. The `identity` log_format records `$request_method $uri $server_protocol` with no `$request`, `$request_uri`, `$args` or `$http_referer`. It is set at server level, so it covers every location on that origin.
- **Api logs:** they don't log request URLs. `Microsoft.AspNetCore` is at Warning in `appsettings.json`, so the request-start lines that would include the query are not written. The installed `OpenTelemetry.Instrumentation.AspNetCore` 1.20.1 redacts the query in traces (`DisableUrlQueryRedaction` defaults off), and nothing in the repo turns redaction off.
- The Api never receives `id_token_hint`; it only redirects the browser to the end-session URL that carries it.
- The remaining gaps are L1 and L2.

**7. Is the config validated at start-up?** Yes. Both keys use `Validate` plus `ValidateOnStart`: a range that fails `IPNetwork.TryParse`, or an empty or blank host, stops the Api with an error naming the key. The tests cover null, empty, not a network, no prefix, `/33`, a trailing space and a blank host. See L4 for the one gap.

## Focus checks

**1. `DISPUTEDESK_SUBNET`: same variable and default in both places.**
- Verified with `docker compose config`: unset or empty gives `10.201.89.0/24` in both places, and `10.201.90.0/24` gives `10.201.90.0/24` in both. `:-` also covers the empty-string case.
- The api service has no `env_file`, so a shell `ForwardedHeaders__TrustedNetwork` can't reach the container.
- Nothing else hard-codes the subnet. The other `10.201.89` values are test constants in ApiFactory and ForwardedHeadersTests, which use a fixed in-process range.

**What happens if only one place is overridden.** One `compose up` can't produce a mismatch, because both values are filled from the same variable source (shell or `.env`). A mismatch is possible only three ways:
- someone edits `docker-compose.yml` (the architecture test catches this; see below);
- an extra Compose file overrides one key: `docker-compose.override.yml` is auto-loaded and not gitignored, or a second `-f` file (the test doesn't read either);
- a network left over from an earlier `up` keeps its old subnet. I couldn't verify whether Compose v5.6.1 recreates a network whose config has changed.

Every one of these fails closed:
- The Api trusts a range none of its peers is on, so it ignores forwarded headers.
- `ClientIp` becomes the gateway container's address, and the per-IP rate limit collapses onto it. That is a correctness and availability cost, not wider trust.
- `redirect_uri` stays correct, because the gateway sets `Host` itself.

Setting a wide value such as `10.0.0.0/8` moves the network to the same range, so it adds no new peers that can reach the api. The bridge-address case is already recorded as L3 for 7.6.

**Does the architecture test catch it?** Yes, for any tracked edit. It requires the subnet to equal the exact string `${DISPUTEDESK_SUBNET:-10.201.89.0/24}` and the trusted network to equal that string too. So hard-coding either place, or using a different variable or default, fails; the builder's deliberate break showed this. It can't see runtime override files, which is an accepted limit.

**2. AllowedHosts rejects ':' and wildcards, with start-up tests.**
- The new `Validate` sits under the existing `ValidateOnStart`, and its message names the key.
- `AllowedHosts` is a non-nullable `string` defaulting to `""`, so the new check can't throw a NullReferenceException.
- Any other odd value (a comma list, spaces) becomes one literal entry that never matches, so the forwarded host is ignored: fail-closed.
- This matches the documented semantics of `ForwardedHeadersOptions.AllowedHosts`: ports excluded, `*` allows every host, `*.x` allows subdomains, IPv6 needs brackets (https://learn.microsoft.com/dotnet/api/microsoft.aspnetcore.builder.forwardedheadersoptions.allowedhosts).
- Rejecting IPv6 literals is a deliberate assumption; the public host is a DNS name. This closes the earlier L4.

**3. The identity access_log test now covers location-level lines.** The new regex `\baccess_log\s+(?<path>[^\s;]+)\s*(?<format>[^\s;]*)[^;]*;` finds directives anywhere on a line, including the same line as a location. A directive with no format gives an empty format and fails, and so does `access_log off;` (stricter, documented). The slice correctly ends at the identity block's closing `\n  }\n` (template line 192). There is one weakening (L-a below).

**4. Nothing widens trust.** The default is unchanged, the new variable sets the network and the trust together, and validation is only stricter.
