**What holds.** The design is GitHub's documented one: a branch ruleset with no bypass actors; required status checks pinned to the GitHub Actions app on an up-to-date branch; squash-only merging enforced by the repository settings; auto-merge; and automatic head-branch deletion. Each rule type and enum the story names exists in the REST schema. The `code_scanning` rule is available on this repository (below), so the human decision needs no `docs/production-path.md` fallback. `git rebase --onto` is the right way to drop a squash-merged base's commits. The gaps are of three kinds:

- the account `gh` would run as;
- the bounds of the guard change;
- the sequencing of 9.3's own merge, its records and its Supervisor checks.

## Security checklist (security-story), applied to the design

- **AuthN/Z (who can change `main`).** The ruleset has no bypass actors, so the owner too goes through a pull request.
  - The two required checks are pinned to `integration_id` 15368. Anyone with write access can set a commit status (*Available rules*), so the pin stops a forged status. The pin's precondition (a recent check run by the app) holds, since 9.1's gates will have run.
  - `non_fast_forward` and `deletion` close the force-push and delete paths on `main`.
  - The remaining paths are around the ruleset, not through it:
    - the guard's force push to unprotected `feature/*` branches (P4);
    - settings changes through `gh api` and `gh repo` (P5);
    - a stacked pull request merged into its base branch (P7);
    - an armed merge that follows a later push (P6);
    - fork pull requests (P20).
- **Secrets.** Using the owner's token (P1) adds a `gh auth token` call inside `$(...)`; the value must never be echoed, logged or written to a file. A subagent can still run `gh auth token` and use the token with `curl`, which the guard cannot see. That gap predates this story; accept it, or add it to `docs/production-path.md` as a limit of a single-maintainer guard.
- **Supply chain.** No package, action or gh extension is added. CodeQL stays as configured, and the `code_scanning` rule reads its uploads.
- **Input validation.** The inputs are the story ID, the pull request number, a SHA and a base branch. The supervisor types them, but the guard is the boundary and must bound them (P4, P5).
- **Data, audit, headers, BFF, linking.** Not touched.
- **Standards.** These are documented mechanisms with no home-grown replacement:
  - GitHub rulesets, the REST *Rules* API, repository merge settings, auto-merge, automatic head-branch deletion and code scanning merge protection (GitHub Docs);
  - `--force-with-lease` and `--force-if-includes` (git-scm *git-push*);
  - the guard, a Claude Code `PreToolUse` hook already in the repo.

  OWASP Top 10 CI/CD Security Risks: CICD-SEC-1 (insufficient flow control: a protected `main`, required checks, no bypass) and CICD-SEC-2 (identity and access: P1's owner token, the guard).

## Simplicity

- Each piece is GitHub's built-in form, and the story keeps squash enforcement in one place (repository settings) rather than two.
- The `--match-head-commit` re-arm adds a step only where a head moves (P6).
- The guard rule is the one intricate part, a hand-written match on CLI arguments. Bounding it as one full-match form plus a short deny list (P4, P5) keeps it explainable in two sentences: "one exact lease-checked force push to a story branch asks; every other force push is denied. Any `gh` call that writes asks."
- Nothing here belongs in `docs/production-path.md`. The `code_scanning` rule is available, so the fallback named in Notes is not needed.
