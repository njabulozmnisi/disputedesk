## How the "held job" was done on the stack

The integration test holds the SIM-swap fake. On the stack there is no fake, so a `qa_readonly` session takes the same two-key advisory lock the job's transaction takes (`pg_advisory_lock(6005, first 4 bytes of SHA-256 of D's customer ID)`). Every D job then waits on its first statement in the transaction (confirmed in `pg_locks`: 4 not-granted advisory locks, the job concurrency), and releasing the lock lets them run one at a time. Only customer C's login is unlinked in the fixtures and D has no login, so the spec creates 8 throwaway Zitadel logins (`qa65.login1` to `8`, email verified, no role) with the provisioner token read from its volume and never printed.

## Standards

- RFC 6585 section 4: 429 for too many requests; `Retry-After` is optional, and it is absent here as the story and `docs/problems/rate-limited.md` say. Not a deviation.
- RFC 9457: `application/problem+json` with `type`, `title`, `status`, `detail`, `traceId`. Matches.
- RFC 9111: `Cache-Control: no-store` on the 429. Matches.
- RFC 9110: the capped start answers the same 202 and an empty body as every other outcome, so the cap does not reveal whether details matched (OWASP Forgot Password Cheat Sheet). Matches.
- OWASP Logging Cheat Sheet: unexpected-stop log line holds only the challenge ID and the exception type. Matches.

## Observations

- **O1 (low, new in 6.5): a budget over 30 s does not apply to the lock wait.** With the first run's `Linking__Budget=00:00:40`, a held lock ended the wait at 30.3 s, not 40 s. Npgsql's default 30 s command timeout fired first, so the job took the unexpected-exception path (`stopped on an unexpected NpgsqlException`, an error log line). The audit outcome is the same (`LinkingStart Failed`, nothing claimed), but the story allows a budget up to 60 s and the log line is an error rather than the budget path. With a 20 s budget the budget path ran as designed. Suggest the story or the options doc say the effective bound is 30 s, or the bound is lowered; the human decides.
- **O2 (pre-existing, not 6.5): a startup validation failure leaves the Api process running.** After `OptionsValidationException` the host logs "Hosting failed to start" and then "Unhandled exception", but the container stays `running` at about 100 percent CPU (still running after 6 minutes in one case). The same happens for an invalid `Linking:OtpHmacKey` (story 6.1). Under Compose it shows as `unhealthy`, but it never exits, so `restart` policies and orchestrators do not see a crash. Not caused by this diff; worth a separate look.
- **O3 (known, noted):** the cap now survives for an hour, so story 6.1's spec (`D` sends) cannot re-run on the same stack within the hour. It needs a fresh stack, as the spec header now says.

## Not covered on the stack, left to the integration tests

The exactly-1-hour edge, core-banking throwing an unexpected type, a failed `LinkingRateLimited` save, "a later start for D proceeds to a sent OTP" after an exception, and across distinct client IPs: all requests reach the Api through the gateway from one address and `X-Forwarded-For` is ignored by design, so only the "across logins" half of "logins and IPs" could be driven.
