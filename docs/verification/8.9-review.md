I tallied the patch's `proxy_*` lines. It removes 14 blocks (7 per template) and adds 4 server blocks with the same directives and values. So nginx's documented inheritance applies to every one of them. Locations that don't proxy (the SPA, `@rate_limited`, `@gateway_error`, the `return` locations) also inherit the block, but without `proxy_pass` it has no effect.

## Security checklist (below High-stakes)

- **Headers:** the response headers (`add_header`, the security, Scalar and identity header includes) are unchanged. The request headers sent upstream are unchanged route by route, and the local edge now also drops a client's `X-Origin-Verify`, so the edge is tighter. The `if ($http_x_origin_verify ...) { return 403; }` checks in AWS still run before any location.
- **Inheritance risk:** a location that later sets one `proxy_set_header` loses the whole block, and with it the `Forwarded ""` that Zitadel's instance resolution relies on. Two guards cover this. `ProxiedLocationCases_CoverEveryProxyPassInTheTemplate` counts the `proxy_pass` lines, so every proxied location needs a per-route case. That case's exact name list then fails when a client `Forwarded` gets through (break 1).
- **Secrets:** `scripts/secret-scan.sh` in the copy: no leaks. The origin-verify value is still in no log format. The patch has no forbidden terms.
- **AuthN/Z, BFF, linking, data, audit:** not touched.
- **Supply chain:** no packages.

## Findings

### L1. Low: local `/otlp/` still passes a client's `X-Origin-Verify`

`infra/nginx/templates/nginx.conf.template:170-190`.

The criteria pull two ways:

- Criterion 3: "no client `Forwarded` or `X-Origin-Verify` header on any route".
- Criterion 1: `/otlp/` "keeps its existing directives unchanged".
- The 2026-11-04 decision: "the local gateway strips the client's header too ... so both gateways behave alike".

The build follows criterion 1. A client's `X-Origin-Verify` still reaches the local OTLP receiver.

There is no security impact. The local edge has no origin-verify check, AWS has no `/otlp/` (it answers 404), and the receiver ignores the header. On every route the two gateways share, they now behave alike.

**Fix (only if the human wants "every route" literally):** add `proxy_set_header X-Origin-Verify "";` to `/otlp/`, and send the header in `LocalOtlpLocation_UpstreamRequest_...`. Otherwise, record that criterion 3's `X-Origin-Verify` clause covers the shared routes. The builder raised the same open question.

### L2. Low: the story text was not amended with the human decision

The diff follows the decision, but three places in the story still say otherwise:

- Criterion 3 says "with no test changed", but the decision needs the local rows to send the header.
- The Boundaries say "Must not change: ... any header value", but the decision adds a header drop.
- The Pre-build section says "Decisions: none raised", but `epic-8-decisions.md:18` records one for 8.9.

**Fix:** the product owner adds a dated line under Notes citing `epic-8-decisions.md:18`, so the story matches what merged. This is a record fix with no code change.
