## Findings (all low)
1. **L1, privacy test scope (AC8).** `backend/tests/DisputeDesk.Worker.IntegrationTests/Sla/SweepRig.cs:61` listens only to the `DisputeDesk` ActivitySource. The Worker also exports Npgsql spans, which are children of each batch span, and the test never captures them. Npgsql's defaults record the SQL text with placeholders, not parameter values, so I see no leak (I did not verify this against Npgsql 10.0.3). Fix: capture with `AddInMemoryExporter` as `RelayHost` and `WorkerTelemetryTests` do, and assert over every span. (ASVS 5.0 V16.2.5; OWASP Logging Cheat Sheet)
2. **L2, the warning window is computed in SQL.** At `SlaQueries.cs:45` the window is `{now} + {leadTime}`, a `timestamptz + interval` sum done by PostgreSQL. If Npgsql sends the `TimeSpan` as days plus time (unverified), the sum depends on the session time zone across a daylight-saving change, so the claim's edge could differ from `RecordSlaWarning`'s by an hour. The stack's Postgres runs in UTC, so this is not reachable today. Fix: pass `{now + leadTime}` as one parameter, which is also plainer.
3. **L3, counts after a failure outside a savepoint** (`SlaSweep.cs:166`, `134` to `141`). The stream load at line 166 has no savepoint. A server-side error there aborts the whole batch transaction, so the later saves fail, and committing an aborted PostgreSQL transaction ends as a rollback. If Npgsql does not throw on that (unverified), the counters at lines 137 to 141 and the batch log would count disputes that were rolled back. That would break AC5's "a dispute whose save rolled back counts nothing". Stored data stays consistent because the whole batch rolls back. Fix: verify Npgsql's behaviour, or record it in `docs/production-path.md`.
4. **L4, a stalled head of the queue** (`SlaSweep.cs:102` with `ORDER BY "SlaDueAtUtc"`). If 50 or more due disputes fail every time (for example a stream that won't replay), each loop claims the same 50, changes none and stops. Disputes due later are then never escalated, so FR-26 is missed, though each failure is logged at Error every 30 s. Fewer than 50 such disputes only slows the sweep down. Fix: a production-path line. No code change is needed for v1.
5. **L5, the automation-actor rule is a text check** (`SourceRulesTests`). A `using static` import or a cast to `ActorType` would get past the regex. In practice no HTTP path can reach `Automation`: actors are built in nine known places, and there is no wire-to-domain actor-type mapping. This is informational only.
6. **L6, test hygiene.** `WorkerHostTests.cs:22` and `WorkerTelemetryTests.cs:44` start the full Worker host, which now also starts the sweep on the real clock. With no connection string configured it fails harmlessly each loop. But in a shell with `ConnectionStrings__DisputeDesk` set, a sweep that changes data would run against that database. The relay had the same exposure before, but it changes nothing. Fix: remove the `SlaSweep` registration in those two tests, as `RelayHost` now does.
7. **L7, missing test (challenger gap).** No test shows that a dispute whose save failed is escalated by a later loop once the cause is gone. `Sweep_OneDisputeFailsToSave_...` keeps its trigger in place. Fix: drop the trigger, run `SweepAsync()` again, and assert one escalation for the failed dispute.
8. **L8, simplicity (pass 2).** `ToWholeMicroseconds` now has 4 copies (raise, withdraw, operations, sweep) and `Later` has 3, which passes the "abstract on the third real case" rule. Leave it for the refactor sweep, not this story. A nit as well: the `Claim` enum drives three `claim == Claim.Overdue ? … : …` branches. It reads fine, so no change is needed.

## Item 4 (L3): savepoint per dispute (closed)
Code: `backend/src/DisputeDesk.Worker/Sla/SlaSweep.cs`, lines 123 and 166 to 212.

**A failed load or save rolls back to the savepoint, and the batch continues.**
- `CreateSavepointAsync` runs before `ChangeAsync`, so the stream load is inside the savepoint as well as the save.
- Both catches run `RollbackToSavepointAsync` then `ReleaseSavepointAsync`, and the batch moves on to the next dispute.
- `AppDbContext.SaveChangesAsync` clears the change tracker on any failure (`AppDbContext.cs:67-87`). So a failed dispute's rows cannot ride along with a later save.
- A cancellation, or a failure in the savepoint calls themselves, propagates. The batch transaction is then disposed and rolled back, and the loop logs only the exception type.
- If release fails after a successful save, the generic catch rolls back to the savepoint and returns false. Data and the count stay consistent.
- `AutoSavepointsEnabled = false` keeps it to one savepoint per dispute. The 120-savepoint test still asserts 120; it would show 240 if EF's automatic savepoints were still on.

**Counters count only committed escalations.**
- Metrics, span tags and `LogBatch` are still set only after `CommitAsync`.
- Every statement between the claim and the commit now runs inside a savepoint. So the transaction can no longer be aborted at commit time, which was the r0 path where Npgsql silently rolled back.
- `NpgsqlCommit_OfATransactionTheServerAborted_DoesNotThrowAndRollsBack` pins the Npgsql behaviour the code relies on.
- `Sweep_TheServerRefusesOneStreamLoad_RollsBackThatDisputeOnlyAndCountsOnlyWhatCommitted` asserts (1,1) / (0,0) / (1,1), both counters at 2 and the span tag at 2. It reproduces the r0 failure: the load was outside any savepoint.
- The builder's break (removing the rollback in the generic catch) would leave the transaction aborted, so this test catches it.

**The race tests still prove what they did.**
- `SlaRaceTests.cs` is unchanged; its assertions are as in r0.
- `VersionClashInterceptor` now writes the competing event when the dispute's savepoint is created, just before it, so rolling back to the savepoint keeps that event.
- It also makes the first stream load stale (`Version < armed.Version`), so the first decision appends a duplicate version and the real unique index refuses it.
- Operations-escalate race: if the clash catch did not roll back, the second `CreateSavepointAsync` would fail in the aborted transaction and the batch would roll back the armed event too. The stream would then be `[Raised]` and the `[Raised, Escalated by ops-race]` assertion would fail. So the test proves the rollback to the savepoint, the replay and the skip.
- Start-review race: it proves the replay after the clash and the escalation at version 3.
- Staging the clash inside the sweep's transaction is still legitimate: while the sweep holds `FOR UPDATE`, the stored event's foreign-key lock blocks any other append.

**Savepoint names are not built from input.** The name is the constant `"sla_sweep_dispute"` (line 44). No dispute ID or other value goes into it.
