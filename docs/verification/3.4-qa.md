**Events hop (criterion 6).** The outbox payload is `disputedesk.dispute.status-changed.v1`, specversion 1.0. Its `id` equals the stored event ID. `data` holds `disputeId`, `fromStatus` submitted, `toStatus` withdrawn, `action` withdraw, `actorType` customer, `occurredAt` and `disputeVersion` 2. It has no note, and `data` has exactly the fields the committed schema requires. The traceparent trace ID is 32-hex, and the status is Pending with 0 attempts. The topic `disputedesk.disputes` has high watermark 0 on all three partitions, because the outbox relay is story 4.1. So the events hop stops at the outbox row, as in earlier QA runs.

**Integrity queries.** 13 disputes were Withdrawn, and 0 of them lacked exactly one `DisputeWithdrawn`. 0 `Disputes` rows had a Version different from the stream's maximum. 0 stored events lacked an outbox row.

**Privacy.** The API log holds no occurrence of the withdraw note, the login `sub` or a customer ID.

**Standards.** Statuses and problem types follow RFC 9110 and RFC 9457; each problem has `type`, `status` and `traceId`, with no exception text. The gateway's coarse rate limit (10 requests a second per address, burst 20, 429) is an nginx setting. My test suite paces itself against it.

- The version-clash cases, the withdraw metrics and the failed-audit-save 500. They need test-only interceptors or a metrics collector. The integration tests cover them, and the verifier ran those.
- Criterion 7 (metrics): I looked only at logs, and I did not scrape `disputedesk.dispute_actions` or `withdraw_age`.
