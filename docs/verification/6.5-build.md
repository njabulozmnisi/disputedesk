# 6.5 build

I built story 6.5 and it is not committed. The full backend suite passed once (1196 tests, 0 failures), and all five criteria have tests. Two Touches items are blocked by the guard and need someone else to apply them:

- **`docs/problems/rate-limited.md`**: the page still says only that the Api's limits send `Retry-After`. Text to add: "A linking start also gets this when too many linking starts are already waiting to be checked. That answer carries no `Retry-After`: a full queue has no window to report, and it is the same for every start, whatever its details." The client-advice line gets: "Without `Retry-After`, wait a little and try again."
- **`frontend/src/api/generated/`**: needs regenerating with orval. `backend/openapi.json` is already updated: the only change is a 429 ProblemDetails response on `POST /api/v1/linking/start`.

**What changed**
- **The cap:** after the match and link check, the job opens one EF Core transaction at Read Committed. The transaction locks the customer, counts their sends from the last hour (cap 3) and runs the SIM-swap check. It then claims the send and commits before the SMS goes out.
- **Release keeps `OtpSentAtUtc`:** the release now clears only `OtpHmac` and `ExpiresAtUtc`, so a failed send can never verify but still holds its cap slot.
- **Unexpected exceptions:** the job catches them, logs only the challenge ID and exception type, and records `LinkingStart Failed` through a fresh DI scope.
- **Full queue:** it now answers 429 `rate-limited` through the new `ErrorKind.RateLimited` and `ErrorResults.ToProblem`, with no `Retry-After`. It saves `LinkingRateLimited Rejected` in a second save. If that save fails, the 429 is unchanged and one error line is logged.
- **Options bounds:** `QueueCapacity` and `Budget` are checked at start-up with the Options pattern's `.Validate(...)` plus `ValidateOnStart`.

**Raw SQL (one named method, `OtpSends.LockCustomerAsync`)**
- Generated: `SELECT pg_advisory_xact_lock(@p0, @p1)`, with both parameters as `Int32`, sent through `ExecuteSqlAsync` (interpolated, so parameterised).
- Why EF can't do it: EF Core has no API for PostgreSQL advisory locks.
- The cap count stays in LINQ and generates `SELECT count(*)::int FROM "LinkingChallenges" AS l WHERE l."CustomerId" = @customerId AND l."OtpSentAtUtc" > @after`.

**Things to check at the diff review**
- **6.1 restart test changed:** `LinkingRestartTests.Restart_WhileTheEarlierJobIsBeforeItsClaim…` now holds the earlier job at the core-banking match instead of the SIM-swap check. The SIM-swap check is now inside the customer lock, so the second job for the same customer waited on the lock until its budget ran out. Its assertions are unchanged.
- **Budget lower bound:** I read "a budget of 0 or negative fails" as `Budget > 0`, not "at least 1 second", because 6.1's tests use 0.5 seconds.
- **Unexpected exceptions after the claim:** a failing release, for example, is still only logged, as in 6.1. AD-12 asks for the audited stop only before the claim.

**Other checks:** the build, dotnet format, floor-guard, the secret scan and the EF pending-model check are all clean. Mailpit got 3 messages, the 4th start was audited `LinkingSendCapped Rejected` for CUS-000004, and no advisory lock was left held. The stack is stopped and the temporary smoke script is deleted.
