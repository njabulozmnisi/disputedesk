# 5.3 build, fix round 1

Fix round 1 for 5.3 is built in `/Users/njabulomnisi/Projects/Dojo/disputedesk/.claude/worktrees/5.3-r1`, on `origin/main` 7cba058. Nothing is committed. The 5.3 patch applied with no conflicts and is staged; the fixes from this round are unstaged, so `git diff` shows only this round.

**Checks:** full suite 1544/1544 passed. Build had 0 warnings, and format verify, floor-guard, the secret scan and the EF pending-model check were all clean.

**Item 4 found a real bug.** On Npgsql 10.0.3, committing a transaction that PostgreSQL has already aborted does not throw; it silently rolls back. A new test pins this. In the r0 sweep, a failed stream load (which had no savepoint) aborted the batch's transaction. The disputes already escalated in that batch were then rolled back at commit, but the counters and the batch log still counted them. The new test failed on r0: the dispute saved before the refused load ended with no escalation.

The fix puts one explicit savepoint around each dispute's load and save, using EF Core's documented manual savepoint API. EF's automatic savepoint is turned off, so there is still exactly one savepoint per dispute and the existing count of 120 holds. Two race tests had to change their setup: the competing event used to be written inside what is now the dispute's savepoint, so the rollback erased it. It is now written just before that savepoint, and the sweep's first replay is made stale so its save still loses the version race. Both race tests pass with the same assertions.

**The other items:**
- **Item 1:** the pattern now matches `ActorType . Automation` and line breaks around the dot, and ignores comments. Three of the new samples failed against the old pattern.
- **Item 2:** a new host-level test runs the real `WorkerHost` against a real database, with one refused save and one refused load. It captures every log category (EF Core's errors included), every exported span (Npgsql's included) and every metric with the in-memory exporters. The test passes as built, so its failing-first proof is a deliberate break: setting `Include Error Detail=true` leaked 6 of the 10 forbidden values.
- **Item 3:** the warning claim sends `now + leadTime` as one parameter; the 48-hour boundary tests still pass.
- **Item 5:** the full-host tests that start the host remove the sweep.
- **Item 6:** the test passed on r0 as well. The behaviour was already right and only the test was missing, so there is no failing-first proof and no break for it.

**Smoke check: only partial.** The rebuilt Worker came up healthy, so the sweep heartbeat is fresh, and its logs show no failures. The demo dispute does show exactly one escalation by `worker:sla-sweep`, but at 13:42, from an earlier run on the existing database volume, so it doesn't prove this build. Getting a clean proof means wiping the shared database volume, which I didn't do; that is still the supervisor's "fresh `docker compose up`" check. I stopped the stack afterwards.
