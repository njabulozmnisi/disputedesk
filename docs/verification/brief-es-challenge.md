## 1. Pre-mortem

- [decision] The audit cleanup removed successful dispute actions from `AuditLogEntries`, but the agreed requirements still required them there. An incident review then had two incompatible definitions of the security record. The brief §5 directly changes PRD FR-13, FR-18, FR-25, FR-26, NFR-DATA-2, NFR-SEC-10; initiative R10, R21, R22, R28; and architecture AD-14 and AD-14a. This needs a product and architecture decision, not just updated tests.
- [story] A rebuild lost seeded disputes or changed their customer-visible histories. AD-30 deliberately seeds disputes **without events**, while the proposed `DisputeEvents` store would be the source of truth. The existing code has `Disputes` and `TimelineEntries`, but no `DisputeEvents`; the backfill and seed strategy must be specified before migration.
- [story] Publishing every stored event exposed internal notes or other sensitive material, or produced event types consumers did not recognise. Brief §3 says one outbox row *per event*, while §0.8 puts internal events in the same stream; PRD FR-28 and AD-19 permit only two public event types with no personal data.

## 2. Simplest design

- [story] Keep event sourcing limited to `Dispute`. Add an append-only, per-dispute versioned event table; replay its lifecycle events for decisions; update the existing `Disputes` read row and customer timeline in the **same database transaction** as the append and outbox insert. Keep the existing public `raised.v1` and `status-changed.v1` contracts, projecting them explicitly from stored events rather than treating a private event payload as a public CloudEvent.
- [story] Build only the five lifecycle event types needed for the current actions. A deny-by-default customer timeline mapping can be tested with an unknown or internal test event; adding `AgentNoteAdded` or `SlaWarningRaised` solely to exercise that mapping adds a product feature without a use case. The proposed `EventType` index, independent `SchemaVersion` alongside versioned type names, `GlobalPosition`, snapshot policy and bank-scale replay design should each have a named present-day use before entering the migration; otherwise document them as future work. Keep the existing separate outbox and relay, which solve the database–Kafka atomicity gap.

## 3. Assumptions

- [story] “Streams are at most five events” (brief §2) assumes the current lifecycle remains the whole stream. Brief §0.8 itself estimates 15–100 events once internal work is included. Do not use the five-event claim to justify an unconditional future performance rule.
- [story] The migration assumes each existing `TimelineEntry` contains enough information to recreate a complete `DisputeRaised` event and transaction snapshot. It records status, actor and visible note; the snapshot currently lives on `Disputes`. Specify a backfill from **both** tables and verify replay matches the existing row before switching reads.
- [story] The brief assumes the relay properties in §6 are already demonstrable. `WorkerHost.cs` says the relay registers in a later story; currently `CommitRows.cs` emits only `raised.v1` and throws for other actions. Mark relay ordering, failure handling and published-payload equality as pending work, not audited facts.

## 4. Standards

- [story] A `GlobalPosition` generated by a PostgreSQL identity or sequence is **not a commit-order checkpoint**: sequence values can have gaps and transactions can commit out of allocation order. If a global replay/checkpoint is required, specify how it handles outstanding transactions and gaps; otherwise omit it for now. PostgreSQL documents that [sequence values are not rolled back](https://www.postgresql.org/docs/current/functions-sequence.html). Per-stream uniqueness and database transactions are sufficient for this build; use [EF Core concurrency handling](https://learn.microsoft.com/en-us/ef/core/saving/concurrency) and [transactions](https://learn.microsoft.com/en-us/ef/core/saving/transactions).
- [story] Do not equate the internal event-store `EventType` with the published CloudEvent `type`: five lifecycle facts currently map to two public contracts, and future private facts must not automatically leave the bank. Use the existing [CloudEvents 1.0 specification](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/spec.md) for the public envelope and its stable ID; retain the [transactional outbox pattern](https://microservices.io/patterns/data/transactional-outbox.html) for publication. A hand-written event-store schema is a local implementation choice, not a new messaging standard.

## 5. Conflicts and gaps

- [decision] Resolve the audit change explicitly across the PRD, initiative and AD-14/AD-14a **before** stories are written. Removing a duplicate successful-action row may be reasonable, but calling the event stream the security audit changes the agreed audit guarantee and its retention/access assumptions. Brief §5 also adds sign-in/sign-out audit actions absent from AD-14a’s closed action set.
- [decision] Resolve whether seeded disputes must be replayable. Brief §1 makes the event store authoritative, but PRD FR-29, initiative R24 and AD-30 require seeded disputes to publish no events and currently create them without an event-store path. “No *published* seed events” could be preserved while storing seed events, but that distinction must be agreed and recorded.
- [decision] Decide what data the immutable stored `DisputeRaised` event contains and who may read it. Rebuilding the projection needs ownership and snapshot facts, while NFR-SEC-5/initiative R31 prohibit personal data in “events” and brief §0.8 anticipates sensitive internal notes. Distinguish private stored facts from public events, define minimisation and access, and reconcile retention with NFR-DATA-7.
- [story] Specify which stored events produce an outbox row, how a stored lifecycle event maps to `status-changed.v1`, and whether the same event ID is used for that public message. The brief alternates between “one outbox row per event” and an internal-only stream without defining this boundary.
- [story] Specify the migration cutover and failure proof: backfill existing disputes and timelines, compare replayed state and customer timeline to current rows, preserve the one-dispute-per-transaction constraint, then change the write path. `AppDbContext.SaveChangesAsync` currently consumes pending changes **before** saving; account for retry or rollback so a failed save cannot silently discard a pending event.
