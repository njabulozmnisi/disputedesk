## 1. Pre-mortem

- [decision] An incident review found two incompatible definitions of the security record: successful dispute actions were recorded only as stored events, while the agreed requirements put them in `AuditLogEntries`. The brief §5 touches PRD FR-13, FR-18, FR-25, FR-26, NFR-DATA-2, NFR-SEC-10; initiative R10, R21, R22, R28; and architecture AD-14 and AD-14a. This needs a product and architecture decision, not just updated tests. Settled by ad-009: the stored events are the record of successful dispute changes, and the audit log holds linking, refused or forbidden actions, operations reads, and sign-in and sign-out.
- [story] A rebuild lost seeded disputes or changed their customer-visible histories, because seeded disputes did not go through the stored-event path while the stored events are the source of truth. The seed strategy must be specified. Settled by ad-009 and AD-30: the seeder calls the domain methods, and seeded disputes go through the full commit path, stored events and outbox rows included.
- [story] Publishing every stored event exposed internal notes or other sensitive material, or produced event types consumers did not recognise. Brief §3 says one outbox row *per event*, while §0.8 puts internal events in the same stream; PRD FR-28 and AD-19 permit only two public event types with no personal data. Settled by ad-009: one exhaustive mapping in Infrastructure decides what is published, and `SlaWarningRaised` has no outbox row.

## 2. Simplest design

- [story] Keep event sourcing limited to `Dispute`. Add an append-only, per-dispute versioned event table; replay its lifecycle events for decisions; write the `Disputes` read row in the **same database transaction** as the append and outbox insert, and build the customer timeline from the stored events. Keep the public `raised.v1` and `status-changed.v1` contracts, projecting them explicitly from stored events rather than treating a private event payload as a public CloudEvent. Settled by ad-009 in this shape.
- [story] Build only the five lifecycle event types needed for the current actions. A deny-by-default customer timeline mapping can be tested with an unknown or internal test event; adding `AgentNoteAdded` or `SlaWarningRaised` solely to exercise that mapping adds a product feature without a use case. The proposed `EventType` index, independent `SchemaVersion` alongside versioned type names, `GlobalPosition`, snapshot policy and bank-scale replay design should each have a named present-day use before entering the migration; otherwise document them as future work. Keep the separate outbox and relay, which solve the database–Kafka atomicity gap. Settled by ad-009: `SlaWarningRaised` is a stored event type with a present use (the SLA sweep records it before the SLA is due, story 5.3); there is no `AgentNoteAdded`, no `GlobalPosition` and no `EventType` index; deny-by-default is also tested with a test-only unknown type.

## 3. Assumptions

- [story] “Streams are at most five events” (brief §2) assumes the current lifecycle remains the whole stream. Brief §0.8 itself estimates 15–100 events once internal work is included. Do not use the five-event claim to justify an unconditional future performance rule.
- [story] Replaying a stream must reproduce the whole dispute row, including the transaction snapshot, not only the status, actor and visible note. Settled by ad-009: `DisputeRaised` holds the snapshot, and a test replays each stream and checks it reproduces the row and the timeline.
- [story] The brief assumes the relay properties in §6 are already demonstrable. `WorkerHost.cs` says the relay registers in a later story; currently `CommitRows.cs` emits only `raised.v1` and throws for other actions. Mark relay ordering, failure handling and published-payload equality as pending work, not audited facts.

## 4. Standards

- [story] A `GlobalPosition` generated by a PostgreSQL identity or sequence is **not a commit-order checkpoint**: sequence values can have gaps and transactions can commit out of allocation order. If a global replay/checkpoint is required, specify how it handles outstanding transactions and gaps; otherwise omit it for now. PostgreSQL documents that [sequence values are not rolled back](https://www.postgresql.org/docs/current/functions-sequence.html). Per-stream uniqueness and database transactions are sufficient for this build; use [EF Core concurrency handling](https://learn.microsoft.com/en-us/ef/core/saving/concurrency) and [transactions](https://learn.microsoft.com/en-us/ef/core/saving/transactions). Settled by ad-009: no global position; per-dispute `Version` with a unique `(DisputeId, Version)`, and the cross-dispute options are in the production path.
- [story] Do not equate the internal event-store `EventType` with the published CloudEvent `type`: five lifecycle facts currently map to two public contracts, and future private facts must not automatically leave the bank. Use the existing [CloudEvents 1.0 specification](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/spec.md) for the public envelope and its stable ID; retain the [transactional outbox pattern](https://microservices.io/patterns/data/transactional-outbox.html) for publication. A hand-written event-store schema is a local implementation choice, not a new messaging standard. Settled by ad-009: stored event types are domain events, mapped to the two integration events by one exhaustive mapping.

## 5. Conflicts and gaps

- [decision] Resolve the audit scope explicitly across the PRD, initiative and AD-14/AD-14a **before** stories are written. Keeping one record of a successful action may be reasonable, but calling the event stream the security audit changes the agreed audit guarantee and its retention/access assumptions. Brief §5 also adds sign-in/sign-out audit actions absent from AD-14a's closed action set. Settled by ad-009 and AD-14a: the audit log holds linking, refused or forbidden actions, operations reads, and `SignIn` and `SignOut`.
- [decision] Resolve whether seeded disputes must be replayable. Brief §1 makes the event store authoritative, so seeded disputes need an event-store path, and whether seeded events are published must be agreed and recorded. Settled by ad-009 and AD-30: seeded disputes are stored and published once per fresh database, and no relay test depends on an empty outbox.
- [decision] Decide what data the immutable stored `DisputeRaised` event contains and who may read it. Rebuilding the projection needs ownership and snapshot facts, while NFR-SEC-5/initiative R31 prohibit personal data in “events” and brief §0.8 anticipates sensitive internal notes. Distinguish private stored facts from public events, define minimisation and access, and reconcile retention with NFR-DATA-7. Settled by ad-009: stored events are private records with the same access as `Disputes`, never logged or traced, kept under NFR-DATA-7; the no-personal-data rule applies to published events.
- [story] Specify which stored events produce an outbox row, how a stored lifecycle event maps to `status-changed.v1`, and whether the same event ID is used for that public message. The brief alternates between “one outbox row per event” and an internal-only stream without defining this boundary. Settled by ad-009: stored event ID = outbox ID = CloudEvent `id`.
- [story] Specify the failure proof: replayed state and customer timeline match the rows, and the one-dispute-per-transaction constraint holds. `AppDbContext.SaveChangesAsync` takes pending changes **before** saving; account for retry or rollback so a failed save cannot silently discard a pending stored event. Settled by ad-009 (the replay test); the failed save is covered by story 3.8.
