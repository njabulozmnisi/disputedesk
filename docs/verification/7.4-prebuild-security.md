# 7.4 pre-build security (status: findings; 3 decisions)

- **S7.4-1 medium [decision] Mailpit is served on the customer app's origin.**
  - Problem: `/mailpit/` on `APP_HOST` puts a third-party UI, including its HTML email rendering, on the SPA's origin with a weaker CSP. Any script running there is same-origin with the SPA. It can GET `/api/v1/bff/antiforgery` and call every customer and linking endpoint with the session cookie. SameSite=Strict and the synchronizer token give no protection against same-origin requests.
  - This contradicts AD-28's Images line, so it is a decision.
  - Options:
    - (a) Mailpit on its own origin: a third CloudFront distribution (no fixed cost) and its own nginx server block that also checks the origin-verify header. Recommended.
    - (b) No public route: reach Mailpit through SSM Session Manager port forwarding. Demo viewers would then need AWS access to read an OTP.
    - (c) Accept it, with the Mailpit location still sending `frame-ancestors 'none'`/`X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy`, HSTS and a Mailpit-specific CSP. The builder must check whether Mailpit v1.32.0 sends its own CSP.
  - Standard: same-origin isolation of untrusted content; ASVS 5.0 V3 (Web Frontend Security); OWASP CSP Cheat Sheet.
  - Builder must test, for (a): the app host answers 404 on `/mailpit/`, and the Mailpit host answers 401 without credentials and 200 with them.

- **S7.4-2 medium [story] Weak bounds on internet-facing credentials.**
  - Problem: `MAILPIT_UI_AUTH` has no minimum length. `ZITADEL_ADMIN_PASSWORD` only has to meet Zitadel's default policy. Both guard internet-facing logins with no lockout; Mailpit basic auth has none.
  - Fix:
    - Both are generated, with the password part `[A-Za-z0-9]{32,128}`.
    - `/mailpit/` sits under `limit_req zone=coarse`.
  - Standard: ASVS 5.0 V6.2 (password strength), V13.3 (generated secrets), V2.4 (anti-automation).
  - Builder must test: `compose.test.env` meets the bounds; `gateway.test.sh` shows `limit_req` applies to `/mailpit/`.

- **S7.4-3 medium [story] The Zitadel console is exposed to the internet behind a password-only admin.**
  - Problem: the AWS identity host proxies `/ui/console` to anyone. The first-instance human admin signs in with a password only, with no MFA.
  - Fix: the AWS auth template returns 404 for `/ui/console`. Provisioning uses the IAM_OWNER PAT over the APIs, so the console is not needed. If anyone ever needs it, 7.5's README says to reach it through SSM port forwarding.
  - Standard: ASVS 5.0 V6.3.3 (MFA, L2) and V13.4 (no exposed admin interfaces).
  - Builder must test: with the right origin header, `/ui/console/` answers 404 while `/.well-known/openid-configuration`, `/oauth/v2/*` and `/ui/v2/login` still reach Zitadel.

- **S7.4-4 medium [story] Criterion 3 tests only the trusted path.**
  - AD-23 says "a test proves a spoofed header from anywhere else is ignored". `gateway.test.sh` must add:
    1. A request from an address outside the realip file, carrying `CloudFront-Viewer-Address`, reaches upstream with `X-Forwarded-For` set to the socket address.
    2. A trusted request carrying a client-sent `X-Forwarded-For: 203.0.113.9` reaches upstream with only the viewer address: `$remote_addr`, never `$proxy_add_x_forwarded_for`.
    3. `real_ip_recursive` stays off.
    4. A request with no `CloudFront-Forwarded-Proto` gets a defined result, either 403 or `https`, never an empty `X-Forwarded-Proto`.
  - Standard: nginx realip module docs; AD-23; ASVS 5.0 V4.

- **S7.4-5 low [story] The origin-verify secret is passed upstream.**
  - Problem: nginx passes client headers upstream by default, so the Api and Zitadel would receive the secret and could log it.
  - Fix: add `proxy_set_header X-Origin-Verify "";` to every proxied location on both hosts. No log format includes the header.
  - The secret also sits in the health-check command, where `docker inspect` shows it to root. That is acceptable; a loopback-only health `listen` would avoid it.
  - Builder must test: the upstream echo never sees the header.

- **S7.4-6 medium [story] The allowed secret characters break connection strings and `.env`.**
  - Problem: "1 to 128 printable ASCII, no `@ : /`" still allows:
    - `;`, which injects Npgsql keywords into `…;Password=…` (for example `x;SSL Mode=Disable` defeats `verify-full`);
    - `? # %`, which break Zitadel's DSN URL;
    - `$`, which Compose `.env` interpolation rewrites;
    - quotes and spaces.
  - Fix:
    - Every secret is generated from `[A-Za-z0-9]`. Database passwords and `LOGIN_SESSION_COOKIE_SECRET` are 32 to 128 characters, and `ZITADEL_MASTERKEY` is exactly 32.
    - `LINKING_OTP_HMAC_KEY` keeps the `LinkingOptions` bounds.
    - 7.5's `deploy.sh` checks each value against its bound before it writes `.env`.
  - Standard: Npgsql connection-string syntax; Compose `.env` interpolation docs; ASVS 5.0 V1 and V2.2.
  - Builder must test: 7.5's `deploy.test.sh` rejects a value containing `;` and one containing `$` before any `docker` call.

- **S7.4-7 low [story] Data Protection key ring in SSM.**
  - Fix:
    - Set the package's KMS key option explicitly from configuration (its README documents `KMSKeyId`; check the pinned version). Otherwise SSM silently uses `alias/aws/ssm` instead of the one key 7.5 grants.
    - `DataProtection:SsmParameterPath` must be outside 7.5's `ssm_path` (see S7.5-3), with no trailing `/`.
    - `SetApplicationName("DisputeDesk")` stays unchanged.
  - Standard: AWS SSM Data Protection provider README; ASVS 5.0 V11 and V13.3.
  - Builder must test: the integration test asserts the repository type and the configured key ID.

- **S7.4-8 medium [decision], shared with 7.5. Every container can get the instance role's credentials.**
  - Problem: with hop limit 2 (AD-28), every bridge-network container can fetch the instance role's credentials, including the internet-facing Zitadel, zitadel-login and Mailpit. Through that role, which includes `AmazonSSMManagedInstanceCore` (`ssm:GetParameter(s)` on `*`), a container can read every SecureString, write the key ring, and with that reach RDS. Only `api` and `otel-collector` need credentials.
  - Fix:
    - The override pins `ipv4_address` for those two services.
    - `deploy.sh` inserts an `iptables -I DOCKER-USER` rule that drops traffic to 169.254.169.254 from the Compose subnet except from those two addresses.
    - Alternatively, accept this for the synthetic demo and add a production-path entry.
  - It is a decision because AD-28 fixes hop limit 2 and the managed policies.
  - Standard: Amazon ECS Developer Guide (blocking container access to instance metadata through DOCKER-USER); EC2 IMDS hop-limit docs; ASVS 5.0 V8 (least privilege).
  - Builder must test: `deploy.test.sh` asserts the rule. The README's post-deploy check shows a metadata request from Mailpit fails while the api gets credentials.

- **S7.4-9 medium [decision] CloudFront to origin is plain HTTP.**
  - Problem: CloudFront reaches the Elastic IP over plain HTTP on port 80. Session cookies, OTPs, ID numbers, Mailpit basic credentials and the origin-verify secret all travel unencrypted on that leg.
  - Fix: either an HTTPS origin, or CloudFront VPC origins (a private subnet, which needs NAT or VPC endpoints and so costs money). Or accept it as a `# shortcut:` with a production-path entry.
  - AD-28 chose the HTTP origin, so this is a decision.
  - Standard: ASVS 5.0 V12.3.1; CloudFront, *Requiring HTTPS between CloudFront and your custom origin*.

- **S7.4-10 low [story] Collector settings.**
  - No `debug` exporter in any pipeline.
  - Receiver endpoints are set explicitly to `0.0.0.0:4317/4318`, because recent collector versions bind to localhost by default.
  - No `ports:` on the collector service.
  - Builder must test: `check-compose.sh` asserts no ports; a check confirms no `debug` exporter.

- **S7.4-11 low [decision] Demo logins with published passwords are live in AWS.**
  - With the seeder on in AWS (AD-26), customers A, B and C sign in with fixture passwords published in the repo (`fixtures/local.json`). `check-compose.sh` never sees that file. Self-registration also lets anyone link to customer D.
  - Fix: accept it explicitly as a synthetic demo, say so in 7.5's README, and add a production-path entry.

## Resolution

Sofia, 2026-10-30, with the human's decisions of 2026-10-30 on the `[decision]` points. The story keeps 8 criteria.

- S7.4-1 [decision], human: option (a). Mailpit lives on its own origin, a third CloudFront distribution and its own nginx server block with basic auth (Mailpit's `MP_UI_AUTH`) and the origin-verify check; the app host answers 404 on `/mailpit/`. AD-28's Images line (and the Edge line's distribution count, and AD-23's IPv6 sentence) are amended. Story: new input `MAILPIT_HOST`, criterion 4 rewritten; 7.5 adds the distribution.
- S7.4-2: generated credentials with the password part `[A-Za-z0-9]{32,128}` (the Zitadel admin password also needs `-`, because Zitadel's default policy requires a symbol); `limit_req zone=coarse` on the Mailpit server block (Inputs; criteria 1 and 4).
- S7.4-3: the identity host answers 404 on `/ui/console` while discovery, `/oauth/v2/*` and `/ui/v2/login` still reach Zitadel (criterion 3); 7.5's README says to reach the console through SSM port forwarding if it is ever needed.
- S7.4-4: the four spoofing cases are in criterion 3; a missing `CloudFront-Forwarded-Proto` gives `https` (Notes decision).
- S7.4-5: `proxy_set_header X-Origin-Verify "";` on every proxied location, tested by the upstream echo, with a supervisor break (criterion 3).
- S7.4-6: every secret from `[A-Za-z0-9]` with the stated lengths; 7.5's `deploy.sh` checks each bound before writing `.env`, and its test rejects `;` and `$` (Inputs; 7.5 criterion 6).
- S7.4-7: `DataProtection:KmsKeyId` set explicitly (AD-26 key list amended); the key-ring path is outside `ssm_path` with no trailing `/`; the test asserts the key ID (Inputs; criterion 8).
- S7.4-8 [decision], human: pin the api's and the collector's container addresses (criterion 2); 7.5's `deploy.sh` adds a `DOCKER-USER` iptables rule dropping traffic to 169.254.169.254 from every other container, the Amazon ECS guide's method, with a test (7.5 criterion 6). AD-28's Compute line is amended.
- S7.4-9 [decision], human: CloudFront to origin stays plain HTTP for the free-plan demo with synthetic data, marked `# shortcut:` in Terraform (7.5 criterion 4), with a production-path entry for an HTTPS or VPC origin, a domain, an ACM certificate with a TLS 1.2 minimum viewer protocol, and WAF (story 7.6's Notes). AD-28's Edge line is amended.
- S7.4-10: explicit `0.0.0.0` receiver endpoints, no `debug` exporter, no collector ports (criteria 2 and 5).
- S7.4-11 [decision], human: accepted and documented; 7.5's README says the fixture logins are live on the AWS demo, and story 7.6's Notes carry the production-path entry.
