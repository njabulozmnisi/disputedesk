**What the seeder does.** It reads the clock once and cuts it to whole microseconds. It checks every fixture dispute before writing any; a bad entry throws a message naming only its position, such as `Fixture disputes[2] cannot be seeded: …`. Then, per customer, it builds a second `AppDbContext` on the migrating connection with that customer set, reads each dispute by `accountRef` + `transactionId` through the ownership filter, and raises only the missing ones. Each new dispute goes through its actions with back-dated instants and is committed in one `SaveChanges`.

**One finding the story didn't anticipate.** When no migration is pending (a restart on an existing database), EF Core seeds inside its own transaction. The customer context's first write then failed with "A transaction is already in progress", and the existing downgrade test caught it. The fix is the documented cross-context pattern: the customer context joins that transaction with `Database.UseTransaction(...)`, and each `SaveChanges` becomes a savepoint, so a dispute's events still commit all or nothing. A new test covers this path.
