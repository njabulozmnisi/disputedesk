## Finding

**L1 (low): the cap's hour can be up to one budget shorter than an hour.**
- **Cause:** `RunAsync` reads `now` once, when the job starts. The claim stamps `OtpSentAtUtc = now`, but the claim can happen up to one `Linking:Budget` later (default 10 s, maximum 60 s), after the core-banking call, the lock wait and the SIM-swap check.
- **Effect:** a 4th SMS can reach the customer up to one budget less than an hour after the 1st. At most 3 SMS land in any window of 1 h minus the budget, not quite FR-4's "per hour". The OTP's 5-minute life is shortened by the same amount, which is the safe direction.
- **Exploitability:** an attacker gains at most 60 s, so this is low.
- **Doc wording:** the doc on `LinkingChallenge.OtpSentAtUtc` ("When the OTP send was claimed", in `backend/src/DisputeDesk.Application/Linking/LinkingChallenge.cs`) is slightly inaccurate.
- **Simplest fix:** accept it, and reword that doc to say it is the job's start instant, at most one budget before the claim. A `// shortcut:` note is optional. Changing the stamp would break AD-4's one clock reading and criterion 1's exact-hour test.
- **Standard:** ASVS 5.0 V2.4.1 (anti-automation limits on functions).

## Your focus points

1. **Can the 3-per-hour cap be beaten? No route found.**
   - **Parallel starts:** `ClaimUnderCustomerLockAsync` in `LinkingJobSteps.cs` runs in one explicit EF Core transaction at Read Committed. Its first statement is `pg_advisory_xact_lock(6005, <first 4 bytes of SHA-256(customerId)>)`, followed by the count, the SIM-swap check and the claim. It commits before the send.
     - The lock lives in the database, so it holds across the 4 workers in one process and across Api replicas.
     - Under Read Committed, each statement after the lock sees the previous holder's committed claim.
     - No retrying execution strategy is configured, so the explicit transaction is valid.
     - The parallel test holds the first job between its count and its claim and waits until 3 jobs are queued on the lock.
   - **Failed send:** `ReleaseAsync` now clears only `OtpHmac` and `ExpiresAtUtc`. The only code that writes `OtpSentAtUtc` is the claim, and nothing deletes `LinkingChallenges`. A superseding start sets only `SupersededAtUtc`.
   - **Other logins or IPs:** the count is keyed on `CustomerId`, which the claim writes from the core-banking match. Unclaimed or blank challenges carry no customer and don't count.
   - **Failure cases fail closed:**
     - A lock wait past the budget becomes the budget's `LinkingStart Failed`.
     - A commit error after the claim stops the job with no send, and the claim still counts.
     - A failed release after a stamped claim leaves an undelivered OTP. Its code was never sent, it is still guarded by the 3-attempt lockout, and the claim counts. This was already so in 6.1.
2. **Full-queue 429: no leak.** The handler never calls core banking, so every well-formed start reaches `TryWrite` the same way. The answer is the constant `LinkingErrors.QueueFull` through `ToProblem`, with the same type, title, status and detail, and no `Retry-After`. The ID number and account number are only in the job, which is dropped and never stored. The test compares the match and no-match bodies with `traceId` removed and checks both audit trails.
3. **OTP HMAC: unchanged.** `Otp.cs` is not in the diff. `Otp.NewCode()` (`RandomNumberGenerator.GetInt32`) now runs at job start instead of at the claim. The code stays in memory only, and the HMAC call and its inputs are unchanged.
4. **Exception path logging: as required.**
   - `LogUnexpectedStop` logs only `ChallengeId` and `exception.GetType().Name`. The span gets a fixed status text.
   - The test throws an exception whose message holds the ID number. It asserts the error log has no `Exception`, exactly those two attributes, and that the ID number appears in no log line.
   - EF sensitive-data logging is not enabled anywhere in `src`.
5. **Audit rows on every refusal: all present.**
   - Each of these records an audit entry: capped (`LinkingSendCapped Rejected` with the `CustomerId`), a failed SIM-swap check, an unexpected exception (`LinkingStart Failed`, written through a fresh scope on `CancellationToken.None`), a budget timeout, and a full queue (`LinkingRateLimited Rejected` with the client IP, in a second save on `CancellationToken.None`).
   - A failed audit save logs only the challenge ID and the action, and the 429 is unchanged (tested with an interceptor).
   - The one stop without an entry is a host shutdown before the claim, which is documented.
6. **Options bounds: validated at start-up.** `QueueCapacity` must be 1 to 1000 and `Budget` more than 0 and at most 60 s, using `.Validate` plus `ValidateOnStart`. Each error message names the key, never its value.
   - Not a security issue: the builder read "0 or negative fails" as `Budget > 0`, so sub-second budgets are allowed. That can only hurt availability. It is in the builder's assumptions for the human review.
7. **Raw SQL: parameterised.** There is one statement, `OtpSends.LockCustomerAsync`, sent through `ExecuteSqlAsync` with an interpolated string. It generates `SELECT pg_advisory_xact_lock(@p0, @p1)` with two `Int32` parameters, which picks the two-key overload. The two-key lock space never overlaps the relay's one-key lock. The cap count stays in LINQ.
