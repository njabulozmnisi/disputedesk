## Pre-mortem
- [decision] More than three SMS messages reach a customer in an hour: SMTP accepts a message but the sender reports a timeout, so the release clears its timestamp and another start takes the freed slot. The story’s database count cannot distinguish that outcome from a message never sent. This conflicts with FR-4’s *at most three OTPs sent* guarantee.
- [story] A database connection remains occupied while the SIM-swap HTTP call runs inside the transaction. Under parallel starts, lock waits plus the call’s five-second deadline can consume the job’s ten-second budget; a fast-fake parallel test would not expose that production failure mode.

## Simplest design
- [story] Keep one bounded channel. After match and link check, use one explicit EF Core transaction on one connection: acquire the customer advisory lock, count timestamps strictly newer than the one-hour cutoff, stop if capped, otherwise check SIM swap and conditionally claim; commit before sending. Retain 6.1’s conditional release and write the full-queue 429 through the existing ProblemDetails path. No new queue, repository, or error kind is needed.
- [decision] Settle what “sent” means when SMTP acceptance is uncertain **before** choosing whether release may free a cap slot. No transaction around a database row and an SMTP send can make those operations atomic.

## Assumptions
- [story] The build can extend 6.1’s handler and job, but those linking files are not present in the current `backend/` tree. Validate the transaction and channel wiring against the actual 6.1 implementation before calling 6.5 ready.
- [story] The parallel proof assumes six jobs finish within their budgets despite a four-job worker limit and a serialized, potentially five-second SIM-swap call. AD-12 specifies those limits; test the deadline and waiting cases, not only immediate fake responses.

## Standards
- [story] Advisory locking is a documented PostgreSQL mechanism, and bounded `TryWrite` is a documented Channels mechanism; neither needs a custom substitute. State explicitly that the lock, count, and claim share an [EF Core explicit transaction](https://learn.microsoft.com/en-us/ef/core/saving/transactions), using the documented [PostgreSQL transaction-level advisory lock](https://www.postgresql.org/docs/current/explicit-locking.html#ADVISORY-LOCKS). The story currently names the lock but not the transaction mechanism.

- [story] Criterion 3 does not say what happens if its **second audit save fails** after the challenge has become current. Specify and test the response and audit-failure handling; otherwise the promised audited 429 is not assured.

## Human decision (2026-10-30)

Every claim counts toward the send cap, delivered or not; a failed send clears the OTP but never frees a cap slot. This guarantees at most three SMS per hour (FR-4); a customer hit by delivery failures waits for the window.
