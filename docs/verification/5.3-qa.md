## Findings

- **F1 (5.3 regression in a 5.4 e2e spec, fixed, QA-owned).** `e2e/tests/seeded-disputes.spec.ts` asserted the SLA demo dispute stays `Under review`. The sweep escalates it five minutes after start-up (recording the warning at the first loop), so the spec failed in the first full run (test 1) and its serial block did not run. Updated: `beforeAll` waits up to 8 minutes for the demo dispute to be Escalated; the demo dispute expects `Escalated`, its stream is the seeded actions plus `SlaWarningRaised` and `DisputeEscalated` (actor `worker:sla-sweep`), its timeline ends with `escalate` (the warning is not a step), and the stored-event and outbox counts are seeded actions + 2 and + 1. Re-run: 9/9 on a fresh database, and green in the second full run. Copied to the main checkout (main's version equalled HEAD). Builder note: the spec now depends on the sweep, so any later story that changes the demo dispute moves it here.
- **F2 (not 5.3, existing data-budget fragility): `dispute-withdraw.spec.ts:332` and `:347` fail in the full suite, pass alone.** On a fresh database run alone, all 16 tests pass. In the full suite `:347` finds only 1 of customer A's 8 reserved transactions still disputable (the first describe of the same spec raises on them) and `:332` finds an earlier spec's Withdraw audit row for customer B. Same class as F2 of the 5.2 QA. Same two failures in both full runs. The sweep touches only the demo dispute and writes no audit row.
- **F3 (not 5.3, flaky): `linking-verify.spec.ts` (customer D, SMS, Mailpit).** Full run 1 and 2: criterion 3, 8 failed ("no LinkingOtpSent audit row"), 6 serial tests did not run. In the subset run on a fresh database: a different test failed (criterion 4, released challenge: `OtpSentAtUtc` not null) and 4 did not run. Different failures on the same stack state means a timing or state race in story 6.x linking tests; nothing in it reads or writes what the sweep touches. Not retried further.
- **F4 (observation): the lost-race log level and API start-up noise are unchanged from earlier stories.** Worker log: 0 `fail:` or `crit:` lines in the whole session, including three Worker restarts. API log: key-ring and `zitadel-discovery` lines at start-up and two EF command failures that come from the linking tests; none from the sweep.
- **O1 (observation): a "pause the Worker" check cannot test the 90-second threshold.** `docker pause` made the container `unhealthy` at once (the health check cannot exec in a paused container) and `healthy` within 11 s of `unpause`. The threshold was therefore proved directly, see criterion 7.

## Criteria walked

Spec: `e2e/tests/sla-sweep.spec.ts` (9 tests, in the tree and in the main checkout). Extra live checks were run by hand on a QA-only fixture variant (below); they are not committed because they need that fixture.

### 1. The 240-hour boundary, as `automation`

Live: the seeded demo dispute has `SlaDueAtUtc` = seeding instant + 5 minutes and `CreatedAtUtc` 240 hours earlier. Fresh stack, due 14:49:38.13 UTC: the sweep's `DisputeEscalated` is stamped 14:49:47.69 (9.6 s after due, never before), actor `Automation` / `worker:sla-sweep`. In the spec the lateness must be in [0 s, 35 s] (one 30-second loop plus the batch). The sub-microsecond boundary itself is integration-test only (fake clock, `SlaBoundaryTests`), not reproducible live.
Variant fixture: a dispute due about 1 day ago (raised 11 days ago, Submitted) was escalated by the first loop, one `DisputeEscalated`, no warning (see criterion 6). Seeded Escalated, Resolved and Withdrawn disputes carry no sweep event (spec test 7: no sweep event after a Resolved or Withdrawn terminal event, and every sweep escalation has `fromStatus` `submitted` or `underReview`).

### 2, 3. Batches, `SKIP LOCKED`, catch-up

Live: the 3-batch 50/50/20 split, the held-lock case and two concurrent sweeps need 120 disputes and a second connection holding locks: integration-only (`SlaBatchTests`, verified by the verifier's 1,544-test run; I did not re-run them). Live evidence: the Worker's first loop on a stack with one overdue seeded dispute (variant fixture) ran `Overdue batch changed 1 of 1 claimed` and escalated it (catch-up shape); `disputedesk.sla_sweep.batch` spans carry `claim`, `claimed`, `changed` tags (a trace of the demo escalation: root batch span `claim=overdue claimed=1 changed=1`, five Npgsql child spans, one producer span `send disputedesk.disputes`). Index and column exist after the migration: `Disputes.SlaWarningRaisedAtUtc` timestamptz null, `IX_Disputes_SlaDueAtUtc` (partial on Status in Submitted, UnderReview), `IX_Disputes_SlaWarning` (btree on `SlaDueAtUtc`, partial on `SlaWarningRaisedAtUtc IS NULL` and Status in Submitted, UnderReview).

### 4. Races end in one escalation

Live, on the variant stack: the Worker was restarted at 15:17:40.10, five seconds before the demo dispute fell due (15:17:46.84), and an operations escalate was sent at 15:17:47.08. Result: operations got 200 and won (`DisputeEscalated` v4, `ActorType` `Operations`, stamped 15:17:47.12); the restarted sweep skipped it. One `DisputeEscalated` only, two outbox status-changed rows (v2, v4), no audit row, no 5xx, no deadlock, no `fail:` log. Spec: the operations escalate on an already sweep-escalated dispute is 409 `action-not-allowed`, stream unchanged. The reverse order (the sweep first) is the 409; the true same-instant race and the version-clash savepoint recovery are integration-only (`SlaRaceTests`), not reproduced live.
