## Criteria

1. **Seven records.** As above.
2. **ad-007 exception.** The browser never holds an access or refresh token; the one exception is `id_token_hint` in the end-session redirect (RP-Initiated Logout 1.0), already spent and short-lived, because without it Zitadel's session outlives sign-out. Linking keeps the session key (decided 2026-10-30, story 6.2); the last Consequence points at P32.
3. **ad-008 guess bound.** Per challenge (FR-7), per login window (FR-8, in memory, reset on restart); the send cap (FR-4) limits codes issued, not verification attempts. It is not the account-wide limit of NIST SP 800-63B-4, *Rate Limiting (Throttling)*: a restarted challenge starts at 0 attempts, no control counts failed attempts across challenges, and the only limit across challenges is the in-memory 15-minute windows, which count every start and verify. The upgrade points at P30, with no control change in v1. "Account-wide" appears only in the negative.
4. **Mapping table.** The counts above; one entry per source, a one-line reason per row.
5. **Context, estimates and named entries.** The opening line is "a large retail bank with tens of millions of clients", followed by "That count is an estimate"; the only other scale figure is P26's labelled estimate. The ad-009 entries are P17, P24, P25, P26 and P27; P30 is the OTP guess bound, P28 migrations as a bundle, P39 problem `type` URLs on an owned domain.
6. **Idempotency (P29).** The current mechanism comes first (`IdempotencyKeyClaims.ClaimAsync`, `INSERT … ON CONFLICT`, AD-16), then "Proposed future change, not built", which is not called an EF Core upsert or an established guarantee.
