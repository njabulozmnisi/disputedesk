## 1. Pre-mortem

- [story] The rate-limit screen could give a wrong wait time—or no useful action—because the current `ApiError` discards response headers. The story’s queue-full 429 also deliberately has **no** `Retry-After`, unlike limiter rejections.
- [story] A successful OTP verification could navigate to `/transactions` while the cached session still says `unlinked`; `SessionGate` would send the customer back to `/link`.

## 2. Simplest design

- [story] Add `/link` and `/link/otp` under the existing `SessionGate`; use the generated start and verify mutations, one input per field, the existing form/error-summary pattern, and the existing problem-type matcher. Keep the OTP as **one pasteable input**—six independent inputs, custom paste handling, and auto-submit are unnecessary.
- [story] On verification success, refresh or update the session cache to `linked` before navigating, then use the existing polite live region to announce success. On `already-linked`, refresh session state as part of redirecting rather than relying on a stale `unlinked` cache.

## 3. Assumptions

- [story] The OTP page can be opened or refreshed without navigation state. The UX specifies `/link/otp` as a route, but the story only describes arriving there after a 202; define its direct-entry behaviour without storing the ID, account number, or OTP.
- [story] “Start again” means returning to the details form; the **next successful start submission** supersedes the old challenge. The architecture invalidates a challenge on start, not on navigation back.

## 4. Standards

- [story] Do not invent a countdown from the problem body: it contains no retry duration, and `ApiError` currently retains no headers. Preserve `Retry-After` from the HTTP response and interpret either HTTP-date or delay-seconds per [RFC 9110 §10.2.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.3). For queue-full 429 without that header, show “Try again later” with no countdown, as the architecture specifies.
- [story] Keep paste and one-time-code autofill enabled on the single OTP control under [WCAG 2.2 SC 3.3.8](https://www.w3.org/TR/WCAG22/#accessible-authentication-minimum); require an explicit Verify submission rather than auto-submit under [SC 3.2.2](https://www.w3.org/TR/WCAG22/#on-input). No other new mechanism is needed.

## 5. Gaps

- [story] Criterion 3 needs separate, testable cases for a limiter 429 **with** `Retry-After` and queue-full 429 **without** it, including what happens while the form is disabled and when retry becomes available.
- [story] Criterion 4 conflates opening `/link` with receiving an API 403. `SessionGate` can redirect an already-linked customer **before any linking request**; test that path separately from a `403 already-linked` returned during a mutation.
- [story] Criterion 2 should specify that `attemptsRemaining` is displayed only for `otp-incorrect`, with the generic wrong-code copy also used for expired or unsent codes; `linking-locked` has no attempts count. Add the no-challenge and correct-on-third-attempt outcomes to the component cases.
- [story] The forms’ bounds belong in the criteria: ID number **13 ASCII digits plus checksum**, account number **6–16 ASCII digits**, OTP **exactly 6 ASCII digits**. Specify client and API 400 field-error handling, unexpected/network errors, and the existing focused error summary. The current “Vitest tests pass” verification line alone does not prove those behaviours.

## Resolution

Sofia, 2026-10-30. Every point was `[story]`; all are folded into the story, no `[decision]` raised.

- `ApiError` discards headers and the full queue has no `Retry-After`: `ApiError` keeps the header, one function reads delay-seconds or an HTTP-date (RFC 9110 §10.2.3) within stated bounds, and the full-queue 429 shows "Too many attempts. Try again later." with the button usable; limiter, HTTP-date, gateway and full-queue cases are each tested, including the disabled period and its end (criterion 7; Inputs).
- Stale `unlinked` session after a link: the session cache is set to `linked` with `setQueryData` before navigating, a test asserts the pathname stays `/transactions`, and a 403 `already-linked` takes the same path (criterion 6); a supervisor break proves it.
- Simplest design: `/link` and `/link/otp` under `SessionGate`, the generated mutations, 4a's form and error-summary pattern, the problem-type matcher, one pasteable OTP input, explicit Verify, success announced through the live region (criteria 1 to 6, 8).
- Direct entry to `/link/otp`: shows the normal 2b screen with nothing carried from 2a and nothing stored (criterion 1).
- "Start again": a link to `/link` that sends no request; only the next successful start supersedes the challenge (criterion 3).
- WCAG 2.2 SC 3.3.8 and 3.2.2: paste and `one-time-code` autofill on the one input, no auto-submit, tested by a no-request check (criterion 4).
- `SessionGate` redirect versus a mutation's 403 `already-linked`: separate cases (criteria 1 and 6).
- `attemptsRemaining` only for `otp-incorrect`; one copy for wrong, expired and unsent codes and a login with no challenge; no count on `linking-locked`; the no-challenge and correct-third-attempt cases are in the component cases (criterion 5).
- Form bounds and errors: ID number 13 ASCII digits with the Luhn check, account number 6 to 16 ASCII digits, OTP exactly 6 ASCII digits after removing spaces; client errors, API 400 field errors, unexpected and network errors and the focused error summary (Inputs; criteria 2 and 4); the Verify line now also requires axe, typecheck and lint.
