## Points

### S1 [story] No personal data at the Kafka boundary: name R31 and test the new surfaces (if missed: medium)

The story's `covers` lists R23, R26, R27, R28, R36, but not R31 (NFR-SEC-5: published events carry no personal data). The `Payload` bytes are already guarded by 3.8 (`PublishMappingTests.OutboxMessage_EachType_PayloadHoldsNoPrivateField`, `RaisedEventTests.Raise_Succeeds_PayloadCarriesNoPersonalDataAmountOrNote`), and criterion 1 proves the value equals `Payload`. What the relay adds is new surface: the record key and headers, the producer span, the Failed log line, `LastError` and the `disputedesk.outbox.failed` metric. Add R31 and state:

- The record headers are exactly `traceparent`, `content-type` and an optional `tracestate`, and nothing else. The OpenTelemetry SDK's default propagator is the composite of trace context and baggage, so the relay injects with empty baggage and no `baggage` header is written.
- The producer span's attributes are exactly the criterion 6 set. There is no message body attribute, and on a failed send only `error.type` is set, to the Kafka error code.
- `disputedesk.outbox.failed` has no labels, or only the event type (AD-20: no label carries personal data).
- The Failed log line is one `[LoggerMessage]` template with the event ID (and the dispute ID if wanted). It never logs `DeliveryResult`, `Message` or the value.
- `LastError` holds only `Error.Code` and `Error.Reason`, within a stated length bound.
- Test: one Worker privacy test raises a dispute with marker values in every private field of `DisputeRaised` (customer ID, account reference, transaction ID, the snapshot's description and masked card, note, expected and disputed amounts) and in the actor ID. Then, across a send, a per-record failure and a Failed row, no captured log line, span attribute, metric tag, Kafka header or `LastError` holds any marker (Known pitfall from 3.8: check every private field). This extends AD-20's span test to the Worker.
- Sources: PRD NFR-SEC-5; AD-19, AD-20; OWASP Logging Cheat Sheet (data to exclude); ASVS 5.0 V14 (Data Protection) and V16.2 (log content).

### S2 [story] `tracestate` is client-controlled: re-validate it with the propagator (if missed: low)

The browser's request context reaches `Activity.TraceStateString` at the commit (`CommitRows.Message`; `RaisedEventTests.Raise_WithTraceContext_StoresTheRequestActivitysTraceParentAndTraceState`). Forwarding the raw `TraceState` column gives every topic consumer untrusted input. Criterion 6 says headers are injected through `Propagators.DefaultTextMapPropagator`. State that the stored pair is also read through the same propagator's `Extract`, over a carrier of the two columns, rather than parsed by hand. Only the extracted context is used and injected, so a malformed `traceparent` gives a root span and a `tracestate` the propagator rejects is not forwarded. Add one test row with a `tracestate` that breaks the W3C list rules (more than 32 members, or over 512 characters): the record still publishes, without that `tracestate`.

- Sources: W3C Trace Context §3.3 and §8 (privacy: `tracestate` must carry no personal data); OpenTelemetry .NET `TraceContextPropagator`; ASVS 5.0 V2.2.1 (input validated against its expected structure).
- Unverified: which `tracestate` rules the installed OpenTelemetry propagator enforces on `Extract`. The builder checks the pinned version's source.

### S3 [story] Kafka configuration key and its validation (if missed: low)

The story names no configuration key for the broker, and AD-26's key list has none. State one options class bound with `ValidateOnStart` (for example `Kafka:BootstrapServers`, and only that key), its Compose value in the worker service's environment (`docker-compose.yml` is in Touches), and no broker address or credential in `appsettings.json`. If the AWS override needs it, `docker-compose.aws.yml` uses `${VAR:?}`. The supervisor adds the key to AD-26's list; that adds to the list and contradicts nothing.

- Sources: Microsoft Learn, *Options pattern* (`ValidateOnStart`); AD-26; ASVS 5.0 V13.3 (secret management) and V13.2 (configuration).

### S4 [decision] Kafka has no TLS and no client authentication (if missed: low; human decides)

Redpanda runs in `dev-container` mode with plaintext listeners and no SASL (`docker-compose.yml`, `redpanda` service). AD-28 runs the same Compose on EC2. Any container on the network can produce forged dispute events to `disputedesk.disputes`, and consumers cannot tell them apart. No architecture decision records this posture, and `docs/production-path.md`, which AD-17 points to, does not exist on main. The options are:

- **(a)** Accept it for v1. Mark the producer configuration `// shortcut: plaintext, no client auth; upgrade to TLS + SASL/SCRAM or mTLS with topic ACLs (only the relay principal writes) before a shared network`, and add the production-path entry.
- **(b)** Build TLS and SASL now.

I recommend (a): the broker is reachable only on the Compose network and `127.0.0.1:19092`.

- Sources: ASVS 5.0 V12.3.1 (encrypted internal connections) and V13.2.1 (authenticated backend communication); Redpanda, *Configure authentication*.

### S5 [story] The dedicated lock connection's SQL (if missed: low)

Criterion 5 puts every outbox read and update on a dedicated `NpgsqlConnection`, so the relay writes its own SQL. State that:

- commands are parameterised only (`NpgsqlParameter`, no interpolation);
- every identifier is double-quoted (AD-22);
- the instant is `@now` from `TimeProvider`, never `now()` (AD-4; the source-rules test greps for it);
- only `"OutboxMessages"` is touched (AD-14's source-rules test fails on raw SQL against `StoredEvents` or `AuditLogEntries`);
- the update sets only `Status`, `Attempts`, `NextAttemptAtUtc`, `SentAtUtc` and `LastError`, never `Payload`, `Id`, `EventType`, `DisputeId`, `DisputeVersion`, `TraceParent` or `TraceState`. This keeps the published bytes the committed bytes (AD-14 Payload, AD-22 "updated only by the relay");
- the connection uses the existing `ConnectionStrings:DisputeDesk` and adds no new credential.

The raw-SQL evidence the user's standards ask for is AD-17's same-connection requirement. The report cites it.

- Sources: Npgsql, *Basic usage* (parameters); PostgreSQL, *Advisory Locks*; ASVS 5.0 V1.2.4 (parameterised queries).

### S6 [story] Supply chain and image (if missed: low)

- Confluent.Kafka (2.16.0 in the architecture's Stack table) pulls the native `librdkafka.redist` in transitively. Run `dotnet list package --vulnerable --include-transitive` and report the result.
- Testcontainers.Redpanda runs the Compose image `docker.redpanda.com/redpandadata/redpanda:v26.2.2@sha256:468bd13a…`, pinned explicitly, not the module's default tag.
- `worker-local` derives from `worker`, so it keeps `USER $APP_UID`. It adds only busybox from the pinned `probe` image, as `api-local` and `core-banking` do.
- Run Trivy on the `worker-local` image.
- Sources: AGENTS.md (Dependency verification); AD-27 (images non-root, pinned by tag and digest); ASVS 5.0 V15.2.1 (no components with known vulnerabilities).
