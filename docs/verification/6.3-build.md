# 6.3 build

Story 6.3 is built and every check passed; nothing is committed. There is one decision for you: when the login limit rejects a request, the IP limit loses two permits, not the one the story says.

**The two-permit edge.** The ASP.NET Core rate-limiting middleware asks the global limiter twice before it rejects a request: first `AttemptAcquire`, then `AcquireAsync` (I checked `RateLimitingMiddleware.cs` on `release/10.0`). With the IP limiter chained first, it grants a permit both times before the login limiter refuses. So once a login has used its 5 requests, it can use up the remaining 15 IP permits in about 8 more requests. That locks out other people behind the same address, such as a shared NAT. The test pins the two-permit count and still fails if the chain order is swapped. Changing the count would mean a custom limiter wrapper, which I did not write because it is not a standard mechanism. FR-8, AD-12 and the story's wording need either amending to say "IP permits" or a different decision.

**Other choices to confirm:**
- **429 body.** It has a fixed `detail`, "Too many linking requests. Try again later." The criterion asks for `type`, `title`, `status` and `traceId` only, but the full-queue 429 it says to match also carries a `detail`, because `ErrorResults.ToProblem` always sets one. The detail names no login, address or count, and both limits return the same body.
- **The README line "limits held in memory"** is not written: the guard blocks the root `README.md` for the backend builder. The supervisor needs to add it.
- **The Orval client is unchanged.** The only contract change is a 429 on verify; start already had one. Regenerating the client from main's `openapi.json` and from this story's gives identical output, so `frontend/src/api/generated` needs no edit.
- **Window tests wait in real time** (about 7 s and 5 s). The sliding-window limiter and `MemoryCache` read the system clock and take no `TimeProvider`. The tests use margins of at least 0.5 s.
- **The first-rejection cache holds at most 10,000 entries.** When it is full, rejections for new partitions are audited every time until entries expire.
