**Items:**
1. **Lock holders (M1):** a new fixture property, `LockHolderConnectionString`, opens the test's lock-holding connections with `Pooling=false`. The leadership and heartbeat tests use it. Before the fix, the full suite failed `Relay_BrokerUnreachable…` with a 30 s timeout: a pooled holder kept the lock, so the relay never became leader.
2. **librdkafka logs:** the producer now uses `SetLogHandler` and `SetErrorHandler`, checked against the 2.16.0 XML docs. The docs say that without a log handler, lines go to stderr. Both handlers feed the existing warning with only the facility (`FAIL`) or error code (`Local_Transport`), never the message text or a record value. The new test captures `Console.Error`. Before the fix it timed out with no native warnings and lines on stderr; after, stderr is empty.
3. **Heartbeat during a slow send:** the relay now touches the file before each send as well as after. The test holds a table lock for 4 s, which keeps the batch query just under its 5 s command timeout, then lets the send run out its 10 s timeout against a dead broker. The fake clock follows real time because librdkafka times the send on its own real clock. Without the fix the file reached 14.1 s old; with it, it stays within 11 s (10 s plus librdkafka's once-a-second timeout scan).
4. **Criterion 3 wording:** no code change. The leadership test already asserts one host logging the lock, one record per row and one producer span per row.
5. **Reviewer L2:**
   - A missing connection string now gives the same warning (`ConnectionStringMissing`) and backoff, without throwing. Before the fix the test saw `InvalidOperationException`.
   - Dropping `InvalidOperationException` from the catch completely broke the terminated-connection test. EF Core wraps the terminated session as `InvalidOperationException("…likely due to a transient failure")` around a `PostgresException`, and the host stopped. So the catch is narrowed to an exception whose inner exception is an `NpgsqlException`; any other `InvalidOperationException` still surfaces. The test is green again.
6. **Reviewer L3:** the publish test moves the clock 17 ticks past the second and expects the stored microsecond value. The break with the old expectation failed (expected `.0000017`, got `.0000010`), which confirms Npgsql truncates.
7. **Security F1:** `AccountLast4` is now `"QZXW"` (not hex, so no GUID or trace ID can contain it by chance), and the transaction date in `yyyy-MM-dd` is a marker. The published payload holds neither value, so no real relay change can leak them in 4.1. The break was a contrived span tag holding the date, and the test caught it.
8. **Nits:** the csproj comment now names `CreateProducerConfig` and `Backoff`. The Compose comment says the worker must not set `TMPDIR`. A comment by `SaveChangesAsync` says the stopping token stays until 4.2.
