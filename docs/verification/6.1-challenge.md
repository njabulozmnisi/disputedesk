## Pre-mortem

- [decision] A restart reached the conditional database update, then the login started again before SMTP sent the OTP. AD-12 checks supersession **before** calling `ISmsSender`, so criterion 6’s promise that a late job sends nothing has no defined guarantee once sending is in flight.
- [decision] SMTP failed after `OtpSentAtUtc` was filled. AD-12 then counts an unsent OTP against the three-per-hour cap and starts its five-minute lifetime before delivery. The story calls that timestamp the *send instant*; the architecture’s order does not establish one.
- [story] Linking start was exposed before story 6.3’s per-login and per-IP limits. The customer send cap constrains matches, but not repeated unmatched lookups; the story needs an explicit release dependency or an interim limit.

## Simplest design

- [story] Keep the documented bounded `Channel` and `BackgroundService`, existing core-banking, SIM-swap and SMS ports, one challenge table, `AuditLog.Record`, and the existing `Unlinked` policy and antiforgery filter. Validate at the endpoint; return the fixed 202 for admitted, well-formed starts; let the job match, check the cap and SIM swap, conditionally fill, then send. No new repository, queue service, identity abstraction or Worker hand-off is needed.
- [decision] Settle what “sent” and “superseded” mean **at the SMTP boundary** before choosing the transaction order. Adding retries or another state machine without settling those guarantees would make the design larger, not clearer.

## Assumptions

- [decision] The PRD says a challenge is created **only on a match with no linked login** (FR-4); AD-12 requires a blank challenge for **every** well-formed start. These are incompatible record invariants, not merely different implementations. Decide which governs story 6.1.
- [story] The story assumes the existing audit API can record client IP. `AuditLog.Record` and `AuditLogEntry` currently have no IP field, although the architecture diagram includes `ClientIp` and `LoginSub`; the epic itself leaves ownership of that migration open. Assign it explicitly to 6.1.
- [story] The story assumes “every outcome returns 202” includes overload. AD-12 instead specifies an audited 429 when the channel is full; later linking rate limits also return 429. State that uniform 202 applies to **admitted, well-formed** requests across the three match outcomes.

## Standards

- [story] The bounded-channel hosted service is a [documented ASP.NET Core queued-background-task pattern](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/host/hosted-services?view=aspnetcore-10.0), not a reason to invent a queue abstraction. Document its in-memory loss on process failure and the observable 429 on saturation.
- [decision] A conditional row update cannot by itself make a subsequent SMTP send atomic or prove its timestamp is the delivery instant. Use the documented [EF Core affected-row/concurrency approach](https://learn.microsoft.com/en-us/ef/core/saving/execute-insert-update-delete#concurrency-control-and-rows-affected) for the database decision, then explicitly define the external-send guarantee; do not describe the two operations as one atomic mechanism. Uniform responses and non-enumerating behavior should follow the [OWASP Forgot Password guidance](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html).

## Gaps

- [story] Criterion 2 has no account-number length, character set or normalization rule. The PRD fixes the ID number at 13 digits with a checksum, but only says “malformed” for the account number. Specify both request fields’ bounds and tests for missing, null and oversized values.
- [story] Criterion 3 covers SIM-check errors and timeouts but not an explicit **recent SIM swap** answer; add that fail-closed case. Specify the audit outcome for core-banking unavailability and SMS failure without changing the public response by match outcome.
- [story] Criterion 6 needs a concurrency test that distinguishes a queued stale job from an already-in-flight send, plus a defined result for a full channel and a failed challenge save. Otherwise “late job sends nothing” cannot be verified against the actual ordering.
- [story] Criterion 8 says “every stop” but does not enumerate stops or specify how a failed audit save is surfaced in a background job. List at least no match, already linked, capped, SIM-swap refused/failed, OTP sent and send failed; test the seeded ID against database rows, captured logs and spans. The nine criteria also exceed AGENTS.md’s approximately eight-criterion story limit; split or consolidate after resolving the decisions above.

### `[decision]` points (human, 2026-10-30)

- **Supersession and "sent" at the SMTP boundary; the conditional update is not atomic with the send.** Claim, send, release on failure: one conditional `ExecuteUpdateAsync` claims the send only if the challenge is current and unsent (EF Core rows affected), then `ISmsSender`; an SMTP failure clears the stamp with a second conditional update, so it counts nothing toward the cap and starts no lifetime. The lifetime starts at the claim. A late send for a superseded challenge is harmless (only the current challenge verifies); a crash between claim and send loses that OTP. The two steps are never called atomic. 6.1 criteria 5 and 6; AD-12 and FR-4 now say the same.
- **FR-4 vs AD-12 record invariant.** AD-12 governs: every well-formed start writes a challenge; only a match with no linked login gets an OTP; writes, timing and response are uniform (OWASP Forgot Password Cheat Sheet). 6.1 criterion 1.
