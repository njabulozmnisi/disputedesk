## Findings

- **N1 (low, already accepted in `3.9-verify.md` round 2): the 129-character cursor gets a different 400 body** (`errors.cursor`: "The field cursor must be a string or array type with a maximum length of '128'.", no `detail`) from the eight layout failures ("The cursor is not valid."). The story's line 35 literally says every malformed-cursor case gets the same body; line 38 allows built-in length validation. The difference reveals only the documented 128 bound, not a parse step. No action needed unless the human wants one body for all nine.
- **N2 (info): the gateway's rate limit (10 r/s, burst 20 per client) returns 429 `rate-limited` to a customer who pages quickly** (observed with the list and detail calls of one test). It is the platform setting, not 3.9; the SPA in 3.7 should not fire page requests in tight loops.
- **N3 (info, test coverage not stack): the tied `CreatedAtUtc` split, the escalated, `upheld` and `rejected` values, the 7-digit snapshot date, enum input cases and the alias rule have no way to be created or are not stack behaviours**; they rest on the integration and architecture tests that `3.9-verify.md` shows passing. I did not re-run them (the Testcontainers slot was held by another lane).
- No defect found in 3.9.
