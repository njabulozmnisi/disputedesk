# 5.3 build

Story 5.3 is built and left uncommitted in the worktree. The full backend suite passes on the final tree (1522 of 1522), and the smoke check passed on the running stack.

**What the sweep does.** `Worker/Sla/SlaSweep.cs` is a hosted service on a 30-second `PeriodicTimer` that uses the injected clock. Each loop:
1. It runs escalation batches. Each batch is one transaction that claims up to 50 IDs, replays each dispute, calls `Escalate` as `worker:sla-sweep` and saves each dispute separately. EF Core puts each save inside a savepoint, so one failed dispute doesn't undo the batch.
2. It then runs warning batches the same way through `RecordSlaWarning`.

The heartbeat file `/tmp/heartbeat-sweep` is touched every loop and after every batch. Escalations are counted only after the commit.

**The raw SQL** (`Infrastructure/Sla/SlaQueries.cs`). The escalation claim as EF sends it, taken from a test that asserts this exact text:
```sql
SELECT "Id" AS "Value"
FROM "Disputes"
WHERE "Status" IN ('Submitted', 'UnderReview') AND "SlaDueAtUtc" <= @p0
ORDER BY "SlaDueAtUtc"
LIMIT @p1
FOR UPDATE SKIP LOCKED
```
The warning claim has the same shape, with `"SlaWarningRaisedAtUtc" IS NULL` and `"SlaDueAtUtc" > @now AND "SlaDueAtUtc" <= @now + @leadTime`, on `IX_Disputes_SlaWarning`. EF Core's LINQ has no row-locking clause, so `FOR UPDATE SKIP LOCKED` can't be written through the query builder. `Database.SqlQuery<Guid>` with an interpolated string makes every value a parameter. It returns IDs only, and no query filter applies to it.

**Order of statements in one save.** I checked this against the installed versions: EF Core 10.0.14 sends `UPDATE "Disputes"` before `INSERT INTO "StoredEvents"` in the same batch. A test now guards this, because the reverse order would deadlock an operations escalate racing the sweep.

**Things that differ from what you asked for:**
- **Smoke check: catch-up, not a fresh start.** The Postgres volume already held disputes seeded at 07:02 today, so the demo dispute had been overdue since 07:07. When the stack came up, the sweep escalated it at 13:42:29 at version 3, as `Automation` / `worker:sla-sweep`, with no warning. Its `status-changed.v1` was Sent, with the batch trace, and reached Kafka with `actorType` `automation`. Customer A sees `underReviewPrioritised` with exactly one escalate entry by `theBank`. No other dispute got a warning, the worker was healthy, and the sweep heartbeat was refreshing every 30 seconds. I did not run `docker compose down -v` to get the "due 5 minutes after start-up" case, because it wipes the shared dev volumes. The supervisor's fresh-stack check still covers that case. The stack is stopped and the lock released.
- **A version clash can't happen naturally while the sweep holds its claim.** The stored event's foreign key check needs a lock that `FOR UPDATE` blocks, so no other transaction can append to the stream. The version-race tests therefore stage the clash inside the sweep's own transaction, just before its savepoint. The real race with an operations escalate is tested separately.
- **The run stops early if a full batch changes nothing.** I added this guard so a batch of 50 disputes that all fail is not claimed forever. A short batch still ends the run, as the story says.
- **The automation-actor rule also allows `Application/Disputes/DisputeWire.cs`.** That file only translates a recorded actor type to the wire format. Comment lines are ignored.
- **Three test files outside the story's Touches changed:**
  - `DisputeSchemaTests` lists the new index. It was the one failure in my first full run.
  - `RelayHost` removes the sweep, because its timer would wait on the relay tests' fake clock.
  - `WorkerHostTests` checks that both hosted services are registered.
