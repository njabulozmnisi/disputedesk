# 6.4 security review

Pass, no findings. The whole staged change was read (base 7ec0ffd, 23 files under `frontend/`) against the security-story checklist and the four pre-build points (S6.4-1 to S6.4-4), each built and tested.

- **Values kept out of the browser's memory and records.** ID numbers, account numbers and codes live only in React Hook Form state and the mutation variables. Both mutations set `gcTime: 0` (checked in `@tanstack/query-core` 5.105.0: `removeObserver` schedules GC), and `linkingPrivacy.test.tsx` asserts the mutation cache is empty after the 202 and the 204. No storage, `console`, `history.pushState`/`replaceState` or `dangerouslySetInnerHTML` in the change. Navigations carry no search params or state. Error-summary links are `#<fieldId>` and call `preventDefault`. `react-hook-form` 7.91.0's `handleSubmit` calls `preventDefault`, so no native GET submit. `startTracing.ts` is unchanged (no request body recorded). Note, not a finding: after a failure the last variables stay in memory while the screen is mounted, as the visible fields do; the story requires clearing once the screen is gone.
- **No token in the browser.** `customFetch` uses `credentials: 'same-origin'` and sets no `Authorization`.
- **Antiforgery.** Both POSTs get `X-XSRF-TOKEN` (asserted in `DetailsScreen.test.tsx:159`, `OtpScreen.test.tsx:135`); the server's `/linking` group keeps `AntiforgeryFilter`, the unlinked policy and the rate-limit metadata (unchanged).
- **No oracle in the UI.** Every 202 shows the same 2b screen; every `otp-incorrect`, `linking-locked` and 429 one copy each; 5xx, network and other 4xx one fixed notice; `title` and `detail` never shown.
- **Retry-After.** Delay-seconds (`^[0-9]+$`) or a regex-checked IMF-fixdate, bounded 1 to 86 400 s, both sides of each bound tested; the longest timer is below the `setTimeout` limit. (The verifier separately notes RFC 9110 §5.6.7 asks recipients to accept all three HTTP-date forms; see `6.4-fixes.md`.)
- **Headers and CSP** unchanged; `z.config({ jitless: true })` keeps CSP free of `'unsafe-eval'`.

Standards: ASP.NET Core antiforgery in a header (ASVS 5.0 V3.5), BFF same-origin cookie (V10), values only in the body (V14.2), nothing kept client-side and `spellcheck=false` (V14.3, V14.2), no values in telemetry (V16.2), RFC 9110 §10.2.3, RFC 9457 §3.1.1. No home-grown mechanism.

Scanners: `scripts/secret-scan.sh` in the tree over the whole change, no leaks; Semgrep (`p/react`, `p/typescript`, `p/secrets`) 110 rules, 17 files, 0 findings; `npm audit` not run (no package change).
