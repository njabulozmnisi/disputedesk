# 5.4 security

Security review of story 5.4 (seeded disputes): **findings**. Two low findings, no high or medium, nothing to escalate. I reviewed only 5.4's own change (both delta diffs), reading against the new54 tree.

## The focus questions

- **Can seeding run outside the demo or be switched on by input?** No.
  - `Seed:Enabled` defaults to false in `SeedOptions` and is absent from `appsettings.json`.
  - It is set only in `docker-compose.yml`, and 5.4 changes only the comment there.
  - Only the Api calls `AddSeeder`, through `Program.cs:41`, and the Worker never seeds.
  - No HTTP path reaches it. The fixtures path comes from configuration only.
  - Start-up refusal in a real deployment is recorded as a production-path item in story 7.6's Notes (ASVS 5.0 V13).
- **Does any seeded row cross customers?** No.
  - `SeedDispute.PlanOne` requires the transaction to be on one of the dispute's own customer's accounts.
  - The per-customer context is grouped by the same `(CustomerId, LoginSub)` the dispute carries, so the context's customer always equals the dispute's owner.
  - If another customer ever held the same `accountRef` + `transactionId`, the filtered read would miss it and `UQ_Disputes_AccountRef_TransactionId` would fail the seed. It fails closed.
  - The ownership test (`Seed_BsOneDispute_...`) proves A gets the same 404 for B's dispute as for an unknown ID.
- **Pre-build check S1 is met.**
  - Each customer context gets its own new `CurrentCustomer` (`Seeder.ContextFor`). The migrator scope's own `CurrentCustomer` stays unset.
  - The existence read is `Entities<Dispute>().AnyAsync(dispute.Matches())` through the ownership filter. There is no `IgnoreQueryFilters` under `Seeding/`, and `OwnershipRulesTests` still enforces that.
  - The key is `accountRef` + `transactionId`, and `everDisputed` comes from that read.
  - S2, S4, S5 and S6 are also met: one `SaveChanges` per stream, all-zero counts with seeding off, a fixture test for the notes, a counts-only log line, and zero audit rows asserted.
- **Second `AppDbContext` and its transaction.**
  - It is built on `migrating.Database.GetDbConnection()` and does not own the connection. It has no seeding delegates, so it cannot recurse, and no interceptors.
  - It joins EF's ambient transaction with `Database.UseTransaction(...)` (Microsoft Learn, EF Core Transactions: cross-context transaction, and savepoints). This is the documented form.
  - With a transaction open, each dispute's `SaveChanges` is a savepoint. A failed seed rolls back the whole run.
  - With no transaction open (fresh database), each dispute's stream is committed whole on its own. A failure part-way leaves only whole disputes, each owned by its own customer, and the re-run skips them. No partial or cross-customer state is left (ASVS 5.0 V2.3.3).
- **`worker:seeder` actor.**
  - Raise and withdraw are stored as `Customer` with the fixture login's `userId`. Start review, escalate and resolve are stored as `Automation` / `worker:seeder`, which the test checks.
  - Published events carry the actor type only (`CommitRows` uses `DisputeWire.ToWire(ActorType)`), so neither actor ID reaches Kafka.
  - No `AuditLogEntries` row and no action metric are written, which is asserted.
- **Failure leaves readiness unhealthy.**
  - Every bad entry throws `InvalidOperationException` naming only `disputes[n]`. `DatabaseMigrator` logs it and retries every 5 s, so readiness stays 503 (tested for 5 kinds of bad entry).
  - Note and bound checks run in the aggregate (`Raise`, `Withdraw`, `Resolve`), not only at the endpoint, so the seeder cannot get around them.
  - No error detail is switched on anywhere in the app: no `Include Error Detail` on the connection string, no `EnableSensitiveDataLogging`, no `EnableDetailedErrors`. So the logged exceptions do not carry key values from Postgres.
- **Logging.** The new log line is `Seeded {Count} disputes` through `[LoggerMessage]`, counts only (AD-20; ASVS 5.0 V16.2.5).

## Delta review: correctness and simplicity

- **Per-action instant test** (`Seed_EachSeededAction_OccursAtTheInstantResolvedFromItsFixtureEntry`): it works out each action's instant from the fixture JSON on its own, without calling the production code, and compares the whole list with the stored `OccurredAtUtc` values. Because it compares lists, a missing or extra action also fails. The builder's break, which stamps every action with a fresh clock reading, fails it. Sound.
- **Read-the-clock-once test** (`Seed_EitherPath_ReadsTheClockOnce`, sync and async): it calls `Seeder` directly with a clock that counts reads and expects exactly 1 for a full seed, links included. Other services use their own clock, so they don't affect the count. The builder's async-only break failed the async case (19 reads). Sound.
- **7-day test**: it asserts criterion 6's exact bound, `SlaDueAtUtc > seededAt.AddDays(7)`. It covers Submitted and Under review disputes other than the SLA demo, and checks that B's dispute is among them. It runs at 00:00:01 and 23:59:59 South African time. The 48-hour lead time is only a comment.
- **Moving the migration in `InvalidFixtureDisputesTests` (fix item 3)** to `CreateMigratedDatabaseAsync` is correct. It removes the race between two migrations creating the history table.
- I checked every new break case against `fixtures/local.json`. Each one edits the action type it names and triggers only the rule it is named for.
- **Simplicity:** `CheckShape` is small and flat. Inlining `DisputesByCustomer` removed a one-line wrapper. Nothing new is speculative.
