VERDICT: RETHINK

## Pre-mortem
- [decision] Removing `AcceptsMetadata([])` makes routing select a policy-less 415 endpoint for a `text/plain` resolve request. Its fallback authentication can answer a bearer caller with a cookie 401, breaking criterion 5. The existing metadata and tests were added specifically to prevent this (`OperationsEndpoints.cs`, AD-8); enabling validation does not change routing.
- [story] Moving note errors into built-in validation can change the 400 body, not just its timing. Existing tests assert the domain error messages, while the story says problem bodies must not change.

## Simplest design
- [story] Use `AddValidation`, `[Required]` and `IValidatableObject` for body-only rules; remove `.DisableValidation()` and the handlers’ duplicate checks, but retain the domain rules for other callers. No new validation layer is needed.
- [decision] Decide separately whether to retain the resolve routing metadata to preserve bearer 401/403 before 415, or relax that requirement. Requiring both its removal and the unchanged criterion-5 results is not a buildable instruction as written.

## Assumptions
- [story] The story assumes `AddValidation()` in `Program.cs` discovers validation metadata for request records declared in `DisputeDesk.Contracts`. [Microsoft Learn’s cross-assembly guidance](https://learn.microsoft.com/aspnet/core/fundamentals/validation?view=aspnetcore-10.0#register-validation-across-assemblies) says registration in the host alone does not generate that metadata; prove these records are discovered before removing handler checks.
- [story] “No row is written” for a refused resolve token assumes no audit entry. `AuthorizationResultHandler` deliberately writes a `Denied` audit row on operations 403s, as AD-14a requires.

## Standards
- [story] Data annotations and `IValidatableObject` are the [documented Minimal API validation mechanism](https://learn.microsoft.com/aspnet/core/fundamentals/minimal-apis?view=aspnetcore-10.0#validation-support-in-minimal-apis); keep validation on the request type rather than adding another filter.
- [decision] The empty-list `AcceptsMetadata` behavior is acknowledged in AD-8 as framework-source behavior, not a documented mechanism. Neither [parameter binding](https://learn.microsoft.com/aspnet/core/fundamentals/minimal-apis/parameter-binding?view=aspnetcore-10.0) nor [RFC 9110’s status definitions](https://www.rfc-editor.org/rfc/rfc9110#section-15.5) supplies a replacement that guarantees bearer authorization before routing’s 415. D1 must resolve that trade-off explicitly.

## Gaps
- [story] Criterion 5 should distinguish **no dispute or event row** from the required `Denied` audit row on 403.
- [story] Criterion 6 must specify whether the old exact error messages and `detail` are preserved or whether the changed validation body is an accepted contract change; its current tests check those messages.
- [story] “Every route” needs stated exceptions: the raise idempotency filter can return 409 or 422 before the transaction lookup (AD-16), and the transaction-dependent expected-amount check still returns 400 after lookup. These are already present in the code and should not be hidden by a single claimed status order.
