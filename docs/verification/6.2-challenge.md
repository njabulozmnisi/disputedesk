## Pre-mortem

- [decision] The third attempt uses the correct OTP but is rejected: AD-12 says the attempt that uses the last try returns `linking-locked`, while FR-7 locks only **after three wrong codes**.
- [decision] A login with no challenge can try indefinitely without reaching lockout. FR-6 says those attempts count, but AD-12 specifies only an update to an existing challenge and returns `attemptsRemaining: 2` when no row exists.
- [decision] A link commits but session re-issue fails—or the cookie is not delivered. AD-12 requires them to “commit together,” yet the current `SessionTicketStore.StoreAsync` opens its own database scope and the cookie is an HTTP response, not part of a database transaction.

## Simplest design

- [story] Use the existing `Unlinked` policy, request validation, audit helper, unique link indexes and cookie handler. Atomically claim one attempt, compare a six-digit OTP HMAC against a same-length dummy for blank rows, and conditionally consume the challenge while inserting the link and audit entry in one database transaction. Re-issue the cookie through `SignInAsync`; do not add a custom session protocol or another OTP store.
- [decision] First settle whether a third **correct** attempt succeeds and how a verify with no challenge persists its failure count. Without those decisions, a plain implementation cannot meet both the PRD and AD-12.

## Assumptions

- [story] Story 6.1 will land first with the stated challenge columns and HMAC input (`challenge ID + code`). No linking implementation is present in the current backend tree, so this assessment uses its story contract rather than executable behavior.
- [story] Re-issuing a session should preserve its original 12-hour absolute expiry. AD-7 says that limit never moves, but `SessionTicketStore.StoreAsync` currently assigns a fresh `now + 12 hours` to every new key.

## Standards

- [decision] “Commit together” across a database transaction and an HTTP cookie is not a framework-supported atomic operation. Specify the database commit boundary using [EF Core transactions](https://learn.microsoft.com/ef/core/saving/transactions), then state how a failed or undelivered [cookie sign-in](https://learn.microsoft.com/aspnet/core/security/authentication/cookie) is recovered; retain [OWASP’s session-ID renewal after a privilege change](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html).
- [story] The conditional attempt update is justified by [EF Core’s affected-row concurrency pattern](https://learn.microsoft.com/ef/core/saving/execute-insert-update-delete#concurrency-control-and-rows-affected). The story should specify an equally conditional consume so parallel correct requests cannot both pass comparison and proceed as winners.

## Gaps

- [story] List the verify request’s sole input and bounds: required JSON string, exactly six ASCII digits, including leading zeroes; specify missing, null, wrong-type, malformed-JSON and oversized-body outcomes. The current criteria do not test them.
- [story] Define the exact response and `attemptsRemaining` on the third wrong attempt, on a correct third attempt, after consumption or supersession, and for the unique-index race loser. “Generic failure” alone does not establish a testable response shape.
- [story] Criterion 7 does not say which audit action and result apply to a no-row attempt, a race loser, or a failed session re-issue, nor whether a failed audit save prevents linking. Name those outcomes and assert the committed audit/link relationship.

## Human decisions (2026-10-30)

1. FR-7 wins: a correct code on the third attempt links; lockout comes after three wrong codes (amend AD-12). A blank challenge (no match, already linked, SIM swap failed) answers and counts exactly like a wrong code. A login with no challenge row gets the same wrong-code answer without counting: it holds no OTP, so it can never succeed and learns nothing.
2. Link first, then re-issue: consume the challenge and insert the link in one EF Core transaction; after it commits, sign out and sign in to re-issue the session with a new key. If the re-issue fails, the link stands and the old session keeps working (linked state is read from the database on every request), and the failure is logged. Amend AD-12's "commit together".

## Resolution

Sofia, 2026-10-30. The three `[decision]` points are settled by the human decisions above: FR-7 governs the third attempt and a login with no row is not counted (criteria 3 and 4; AD-12, FR-6 and FR-7 amended); link first, then re-issue (criteria 1 and 2; AD-12's "commit together" replaced). `[story]` points folded: the conditional consume in the link transaction (criterion 1), the input bounds (criterion 5), the response for every attempt position, consumption, supersession and the race loser (criteria 3, 4, 7), the audit action per outcome and the audit inside the link transaction (criterion 8), and the absolute expiry carried (criterion 2).

New `[decision]` raised by this refine: the decided re-issue does not work with the built-in cookie handler. In ASP.NET Core's `release/10.0` source, `HandleSignOutAsync` removes the session row but leaves `_sessionKey` set, and a later `HandleSignInAsync` in the same request calls `ITicketStore.RenewAsync` with that removed key, not `StoreAsync`. Result: no new key, the row is gone, and the next request gets 401. Options: (A) keep the session key at linking and drop AD-7's renewal (the key is minted server-side at sign-in and the store rejects any key it did not mint, so fixation is already prevented), with a production-path line; (B) the verify response signs out the cookie scheme and the SPA goes through `/api/v1/bff/login`, where Zitadel's live session signs in again without a prompt and `StoreAsync` mints a new key (FR-6's "no new sign-in" reads as "no credentials entered"). Story 6.2 stays not ready until a human picks one; its criterion 2 is then rewritten.

Human decision on the new `[decision]` (2026-10-30): option (A). Linking keeps the existing session key, with no sign-out or sign-in; AD-7's renewal of the key after linking is dropped because the key is minted server-side at sign-in and the ticket store rejects any key it did not mint, so fixation is already blocked. Applied: story 6.2 criterion 2 (session, key and absolute expiry unchanged; the next request sees the linked customer), its Notes and `tickets.toml` (the Unknown removed), AD-7, AD-12 (the `[ASSUMPTION]` cleared), FR-6, and a production-path line in story 7.6's Notes.
