## Findings

- **L1 (low, non-blocking): the instant carries 100 ns ticks, the database keeps microseconds.** In the second raise the 201 body `createdAt`/`occurredAt` and the outbox CloudEvent `time` read `…57.6071427`, while the three database columns read `…57.607142`. Criterion 5 says the stored event instant equals the CloudEvent `time`, and criterion 12 says the timeline built later equals the 201's; both hold only at microseconds. The integration tests hide it with a fixed clock and a `Microseconds()` helper. Whoever reads the stream later (story 3.3's history) will show an instant up to 0.9 microseconds earlier than the 201 did. Fix, if the exact claim is wanted: truncate `time.GetUtcNow()` to microseconds once in `RaiseDisputeHandler`. The e2e spec compares at microseconds and will pass either way.
- **L2 (info): startup noise in the API log.** On a fresh start the API logs `42P01 relation "DataProtectionKeys" does not exist` and a `core-banking` name-resolution failure before migrations and the stub are up; both clear and the stack goes healthy. Not caused by this story.
- **E1 (environmental, pre-existing, not from this story): `e2e/tests/transactions.spec.ts` now fails one test per run with 429 from the gateway.** The gateway's coarse limiter (`limit_req` 10 r/s, burst 20, `infra/nginx/templates/nginx.conf.template`) is hit by that spec's own paging bursts; which test trips it varies (`customer A never sees B rows` in the full run, `limit above 50` in the three reruns). The 3.8 diff touches nothing in `infra/nginx`, the transactions endpoint or that spec. The full suite: 47 passed, 1 failed (E1). The new spec: 14 passed in 8.6 s, and again in the full run.
