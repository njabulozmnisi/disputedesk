## Findings

1. **Sign-out needs a click at Zitadel (medium).** The Api redirects to `end_session` without an `id_token_hint`, and Login v2 answers with a "Click an account to end the session" page. Until that click the Zitadel session is alive: I opened `/api/v1/bff/login` in a second tab at that point and it signed straight in with no prompt and created a new Api session. After the click the browser lands on `/` and a fresh login prompts again. The criterion text (redirect carries `client_id` and `post_logout_redirect_uri`) is met; the supervisor check "Zitadel shows no session" holds only after the click. Decide whether to accept this, or send `id_token_hint` (needs the ID token stored server-side, against `SaveTokens=false`), or accept it as hosted-login behaviour. The e2e test performs the click.
2. **`DataProtectionKeys` key ring stored unencrypted (low, flag for security).** The log warns `No XML encryptor configured. Key ... may be persisted to storage in unencrypted form.` `qa_readonly` can read that table, and so can anything with database read access, which could unprotect the stored tickets (claims only, no tokens). Fine for the local stack; belongs in `docs/production-path.md`.
3. **First-start error noise (low).** On an empty database the Api logs three `fail:` entries `relation "DataProtectionKeys" does not exist` (key ring loaded before the migration ran at line 107), then recovers. Readiness is healthy afterwards. Also logged: two antiforgery warnings `required antiforgery cookie is not present` for the missing-token requests.
4. Observations, no action needed: the logout POST from an anonymous caller is not antiforgery-checked by design and redirects to `end_session` (logout CSRF, low impact). Cookies are not `Secure` on the local HTTP stack (`ExternalSecure` and `SecurePolicy` come from configuration, default `Always`). Duplicate `X-Content-Type-Options: nosniff` header (gateway and Api both add it). A validation problem from the antiforgery filter has no `errors` object; acceptable because there is no field.
5. The Zitadel cookies on `auth.localhost` (`sessions`, `zitadel.useragent`, `fingerprintId`) are Zitadel's, not the Api's; they are separate from the "only two cookies" requirement, which applies to `localhost`.
6. My probe in finding 1 left one extra `Sessions` row from the stray sign-in. It is not removable with the read-only role and expires on its own.
