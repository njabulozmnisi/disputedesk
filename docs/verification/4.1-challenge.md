## Pre-mortem
- [decision] A leader loses its PostgreSQL connection while a Kafka send remains in flight. Its replacement sends the same row and then the next version; the old send can complete last, placing an older event after a newer one. A session advisory lock does not fence an already-running Kafka producer, so AD-17’s lock check before each batch cannot prove the promised order during handover. [PostgreSQL advisory locks](https://www.postgresql.org/docs/current/explicit-locking.html#ADVISORY-LOCKS)
- [story] Broker timeouts are classified as permanent record failures, exhausting five attempts during an outage despite criterion 3. The story needs an explicit, testable distinction between broker-unavailable errors and permanent record rejection.
- [story] A long send, batch or backoff interval exceeds the relay’s 30-second heartbeat threshold; Compose restarts a Worker that is still making progress.

## Simplest design
- [story] Use one `BackgroundService` and one dedicated PostgreSQL connection for both the advisory lock and outbox reads/updates. Select the eligible head of each dispute, await each Kafka delivery report, then mark it Sent; retain the row and its stable CloudEvent ID for retry. Keep the existing payload and telemetry registration. No dead-letter topic, CDC, HTTP endpoint in the Worker, or second coordination mechanism is needed. [Microsoft hosted services](https://learn.microsoft.com/en-us/aspnet/core/extensions/hosted-services)
- [decision] Before building, resolve the handover guarantee: either accept and specify how consumers handle a late duplicate, or choose a mechanism that actually enforces the required order across leader loss. Adding more pre-batch lock checks alone does not resolve it.

## Assumptions
- [story] The relay can use its lock connection for all database work. The existing `AddInfrastructure()` registers a scoped EF context from a connection string, not from that dedicated connection; the implementation must not silently use a second connection for outbox updates.
- [story] The Worker can be declared healthy with only a relay heartbeat. AD-25 describes **both** relay and sweep files, but story 5.3 adds the sweep later and owns its health-check addition. State explicitly which file 4.1 checks.
- [story] Every row has `tracestate`. `CommitRows` stores it as nullable, while criterion 1 requires that header unconditionally; the W3C header is optional. [W3C Trace Context](https://www.w3.org/TR/trace-context/)

## Standards
- [story] The implied rule “a pre-batch advisory-lock check makes Kafka sends single-leader” is not a fencing standard. PostgreSQL defines the lock’s connection lifetime, not cancellation of external sends; revise the guarantee or document a mechanism that covers that gap. [PostgreSQL advisory locks](https://www.postgresql.org/docs/current/explicit-locking.html#ADVISORY-LOCKS)
- [story] Do not invent trace-header formatting. Use the specified OpenTelemetry propagator and Kafka producer-span conventions, with absent `tracestate` allowed. [OpenTelemetry Kafka conventions](https://opentelemetry.io/docs/specs/semconv/messaging/kafka/) · [W3C Trace Context](https://www.w3.org/TR/trace-context/)

## Gaps
- [decision] Criterion 5’s “only one publishes at a time” and “without duplicating order” cannot be established by the specified lock-termination test or AD-17’s pre-batch check. Specify the expected result when termination occurs **during** an in-flight send, including late delivery and duplicate IDs.
- [story] Criteria 3–4 do not identify which Kafka errors count toward `Attempts`, how a timed-out send with unknown delivery outcome is retried, or how permanent rejection is induced in a test.
- [story] Criterion 7 says the default shutdown timeout needs “no code,” but does not bound a send or batch, define what happens to an interrupted row, or say how heartbeat freshness is maintained during backoff. Test SIGTERM with an in-flight send and specify the row’s expected state.
- [story] Criterion 6 needs assertions for absent and malformed stored trace context and absent `tracestate`; criterion 8 should specify how tests distinguish their own Kafka records from seeded or concurrent records.
