## The builder's open question P13 (fork pull requests and `id-token: write`)

**What the docs say.**
- *Workflow syntax*, "How permissions are calculated for a workflow job": on a pull request from a fork (without "Send write tokens to workflows from pull requests"), "the permissions are adjusted to change any write permissions to read only".
- *Reusing workflow configurations*: a called workflow's permissions "can be only downgraded (not elevated)".

No page says whether the called job's `id-token: write` is checked against the caller's declared grant, which passes, or against the fork-capped set, which would fail. It also does not say whether that check happens at run creation, which would apply even though `deploy` is skipped by its `needs` and `if`.

**Public reports.** I searched issues for GitHub's error text "is requesting 'id-token: write', but is only allowed". Over 600 results show the check runs at startup ("failed at startup") when a caller grants too little. The two fork-specific reports I found (yedeya-labs/kanon#285, projectbluefin/utah-packages#822) leave the fork case unverified too.

**Judgment: a known limit, not a finding.** If GitHub does check against the capped set, a fork pull request's CI run fails at startup and `ci-passed` never reports. That fails closed: the pull request cannot merge, and no token can be minted. It is an availability effect on a path this flow does not have (one maintainer, no Dependabot), and 9.3 already makes a fork pull request fail its checks. It is not a security gap. Fork runs get no `id-token: write` in any case, and `dev`'s branch rule refuses `refs/pull/N/merge` before a job reaches a runner (*Deployments and environments*; *Workflow syntax*, "All deployment protection rules must pass before a job referencing the environment is sent to a runner").

The story's Notes already record what to do if it is seen: record it, and do not block `main`. I keep it as an open question for QA or the security agent, unresolved by the docs.

## Pass 2: simplicity and standards

- **Smaller design?** No.
  - Two jobs with opposite `if`s is the least GitHub allows: a calling job has no `steps`, and a skipped job writes no notice.
  - One reusable workflow serves both the automatic deploy and rollback.
  - The `images` step's two paths share one output contract, so the AWS steps stay untouched.
  - The three short loops over the five names (publish, the call path, switched-off) are plain duplication in three different files with three different jobs. Abstracting them would add indirection, not remove it.
  - The early `exit 0` keeps the call path flat.
- **Every abstraction earns its place.** The one new Terraform variable is the environment name, kept for AD-28's second environment (story decision). There is no new interface, option or wrapper.
- **Standards.** Each mechanism has its documented source in `9.2-build.json`'s `standards`, and I checked each against the pages above:
  - GitHub reusable workflows (`workflow_call`, `environment` on the called job, permissions passed down);
  - job outputs;
  - `vars` in `if` and `with`;
  - the `notice` workflow command;
  - job concurrency;
  - GitHub OIDC's environment subject with immutable IDs;
  - AWS IAM web-identity trust with exact `StringEquals`;
  - environment deployment branch policies (REST);
  - 12-factor build, release, run.

  The reference shape check is the same regular expression the SSM document's `allowedPattern` uses. There is no home-grown mechanism. The test harness (extract each `run:` with yq and run it with stubs) is 9.1's established repo pattern.

## Security-relevant observations (context for the security agent)

- **Who can get the `environment:dev` subject.** Only a job that names `dev` gets it (*OIDC reference*), and `dev`'s rule is matched against `GITHUB_REF`. That keeps out a pushed `story/**` branch that edits the workflow, any `pull_request` run (`refs/pull/N/merge`), fork branches and tags.
- **`id-token` holders.** No other workflow names an environment or holds `id-token`. Neither `security.yml` nor `ci.yml` (apart from `deploy`) does, and no workflow uses `pull_request_target` or `workflow_run`.
- **Input handling.** Inputs reach scripts only through `env`. `GITHUB_OUTPUT` lines are written only after a full-match regular expression, so no newline can be injected.
