## Standards

- Microsoft Learn, Forwarded Headers middleware: trust is by the connection's address; `KnownIPNetworks` holds only the configured range; `ForwardLimit` 1; an untrusted connection's headers are ignored. Observed behaviour matches, including the positive control from inside the range.
- RFC 9110 and RFC 9457: unchanged; no new problem body. `Cache-Control` and statuses are as before.
- OWASP Logging Cheat Sheet and ASVS 5.0 V14.2.1 (no sensitive data in URLs or logs): met for the identity origin's `end_session`; see O2 for the app origin.
- RFC 7239: see O1.

## Observations (none is a defect against the 6.6 criteria; the human decides)

- **O1 (low, new surface seen here): the gateway passes a client's RFC 7239 `Forwarded` header on to the upstreams.** `curl -H 'Forwarded: host=evil.example;proto=https' http://auth.localhost:8080/.well-known/openid-configuration` answers 404 `unable to set instance using origin &{evil.example https} (ExternalDomain is auth.localhost)`, so Zitadel resolves its instance from the client's header (the same request with `X-Forwarded-Host: evil.example` or `X-Forwarded-Proto: https` answers 200, because nginx replaces those two). The effect is limited to the sender's own request (a browser that sends `Forwarded` cannot sign in), and the Api ignores `Forwarded` (only the three `X-Forwarded-*` are processed: the `redirect_uri` stayed correct with it forged). A cheap fix is `proxy_set_header Forwarded "";` beside the other `proxy_set_header` lines in each location. The browser flow in the new spec therefore forges the three `X-Forwarded-*` headers only; the `Forwarded` header is forged in the request-context test, which only reaches the Api.
- **O2 (low, pre-existing, outside criterion 2): the app origin's access log (default `combined` format) records the sign-in callback's query.** Lines such as `GET /api/signin-oidc?code=<encrypted authorization code>&state=<state>` appear in the gateway log. It is a one-time code (single use, PKCE-bound) and the `state`, not the `id_token_hint`, and not the identity origin, which this story's criterion 2 covers. ASVS V14.2.1 would still prefer a path-only format for the app origin too. The new spec allows exactly this line and fails on any other token-shaped value in the log.
- **O3 (informational):** on Docker Desktop the gateway sees the host's client as the Compose network's own gateway address `10.201.89.1`, so every local client is audited as `10.201.89.1`. That is "the address the gateway saw" and is inside the trusted range, which is correct for the local stack; behind CloudFront (story 7.4) the real address would come from the trusted header.
