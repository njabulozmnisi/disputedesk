**Each focus point:**
- **Brute force: met.** Each attempt is one `UPDATE … SET "Attempts" = "Attempts" + 1 … AND "Attempts" < 3 RETURNING …` that commits on its own (backend/src/DisputeDesk.Infrastructure/Linking/OtpAttempts.cs). Postgres takes a row lock and re-checks the WHERE under Read Committed, so parallel attempts can never pass 3; the 10-parallel test asserts exactly 3. A correct third code links, and any fourth attempt gets 409 because the update returns no row and the follow-up read finds the locked row. Expired attempts count too.
  - A new start does supersede the challenge and insert one with Attempts 0. That is FR-7 as written ("start linking again"). Each reset costs a fresh SMS and gives 3 guesses at a new code. The limit across starts (FR-8 per-login and per-IP limits, and the hourly send cap) belongs to 6.3 and 6.5, which are not in this tree. Until 6.3 lands, verify is limited only by the gateway's limit_req, as the story's Boundaries say. Nothing for 6.2 to fix, but 6.2 should not run anywhere exposed before 6.3.
- **Timing: met.**
  - Otp.Matches always computes the HMAC and uses CryptographicOperations.FixedTimeEquals against a 32-byte dummy when OtpHmac is null. The path with no challenge row computes it too, keyed on Guid.Empty.
  - I timed a correct code, a wrong first digit, a wrong last digit, the blank dummy and the no-row dummy, 200k runs each over 5 shuffled rounds. All fell between 0.4 and 2.3 us, with no stable order and no link to where the mismatch was. That noise is far below one database round trip.
  - A claimed challenge with a wrong code and a blank challenge run the same statements (the attempt update, then an audit insert).
- **Enumeration: met.**
  - Blank (no match, already linked, SIM swap failed), released and expired challenges answer exactly like a wrong code: 422 with attemptsRemaining 2, then 1, then 409. VerifyOtpChallengeKindTests compares the bodies attempt by attempt.
  - A login with no row always gets 422 with 2 and is never counted. That login is the caller's own, so it learns nothing.
  - No request field names a challenge or customer, and a superseded challenge's OTP fails on the current one (tested).
- **Race safety: met.**
  - Consuming the challenge (conditional, must be exactly 1 row) and inserting the link share one explicit EF Core transaction.
  - UQ_CustomerLinks_CustomerId and UQ_CustomerLinks_LoginSub map to LinkingErrors.LinkClash, and the handler catches it. The loser's consume rolls back and it gets the counted wrong-code answer, never a 500.
  - AppDbContext.SaveChangesAsync clears the change tracker after a failed save, so the loser's Linked Rejected entry saves cleanly. The two-login race test asserts it.
- **Linked audit entry: met.** Linked Succeeded is recorded inside the link transaction with the CustomerId and client IP. A failed audit save commits neither the link nor the consume (tested).
- **Session fixation (key kept, human decision): accepted and tracked.**
  - SessionTicketStore.StoreAsync mints the key server-side with RandomNumberGenerator.GetBytes(32) and stores only its SHA-256. RetrieveAsync returns null for any key it did not mint.
  - The tests show no Set-Cookie, and KeyHash, LoginSub and AbsoluteExpiresAtUtc unchanged.
  - The remaining risk is that a key stolen before linking becomes linked. That differs from the OWASP Session Management Cheat Sheet and ASVS V7.2.4 (renew the token after a privilege change). The human accepted it, and it is recorded as an input to story 7.6's production-path list. Not a new finding.
- **Privacy: met.**
  - The code never reaches SQL; only loginSub and the constant are parameters.
  - Npgsql tracing records only the statement text, and no request or body logging is registered.
  - VerifyOtpRequest and the handler's Attempt record both seal ToString. CountedAttempt is a class, so its ToString prints only the type name.
  - The audit-failure log line holds only the action. The privacy test covers a verify, including the HMAC of a submitted wrong code.
  - No ID number is involved.
- **Raw SQL: met.** Database.SqlQuery<CountedAttempt> takes an interpolated FormattableString, so values become database parameters, and nothing is composed on top. The SQL is given as evidence in the build report.
- **Antiforgery: met.** The verify route sits in the /linking group, which has the Unlinked policy and the AntiforgeryFilter. The tests cover 401 (anonymous, and a bearer token alone), 403 already-linked before validation, and a missing token giving 400 with no attempt counted and no audit row.

**Findings (both low; neither is a security weakness):**
- **L1, metric accuracy.** In VerifyOtpHandler.RefuseAsync (backend/src/DisputeDesk.Infrastructure/Linking/VerifyOtpHandler.cs), a parallel request from the same login can carry the third count and then lose the consume to a sibling that linked. It still calls metrics.RecordLocked() and answers 409, so `locked` is counted for a challenge that actually linked. The same happens when a new start supersedes the challenge mid-verify. This breaks criterion 8's "counts locked once per challenge, when it locks", and no test covers it because the 10-parallel test does not check metrics. Fix: count `locked` only when the attempt was compared and failed, not when the consume is lost.
- **L2, pre-existing 6.1 code, informational.** OtpSends.ClaimAsync (backend/src/DisputeDesk.Infrastructure/Linking/OtpSends.cs) does not check Attempts. If someone makes 3 wrong guesses while the start's job is still pending, the job still sends an SMS for a challenge that is already locked. It cannot be used to brute force (early guesses are wasted against the dummy), but it is a needless SMS to the customer. Better suited to 6.3 or 6.5 than to 6.2's fix round.

**AC7: the builder's choice is right, and the story wording should follow.**
- **Why it is right:** when the other login's link wins, the loser's consume rolls back with its failed insert. If that attempt was its third, its challenge now has 3 attempts and is still current, so it really is locked.
  - Criterion 8 says the attempt that locks is `LinkingLocked` and that `locked` is counted once per challenge, when it locks.
  - Recording `Linked` instead would mean `locked` is never counted for that challenge, because later attempts are not counted. That would break criterion 8.
  - The client gets 409 either way, as criterion 3 requires for any counted attempt at 3.
  - Recording the lock fits OWASP ASVS V16.3.1 (log authentication events, lockouts included).
  - Nothing is lost for an audit: the `LinkingLocked` entry carries customer D's `CustomerId`, so it can still be matched with the winner's `Linked Succeeded`.
- **Suggested wording for criterion 7:** "...it gets the counted-attempt answer of criterion 3 (422 `otp-incorrect` with its `attemptsRemaining`, or 409 `linking-locked` when it is its third), never a 500...; the loser records `Linked` `Rejected`, unless it was its third attempt, which locks its challenge: `LinkingLocked` `Rejected`, and `locked` counted (criterion 8)."
- **Suggested wording for criterion 8:** change "a race loser is `Linked` `Rejected`" to "a race loser is `Linked` `Rejected`, except a two-login loser on its third attempt (criterion 7)". Add "a verification that loses the consume to a parallel verification or a later start counts no `locked`".

**Findings (all low):**
- **L1, test proof.** The fix list asked to drop both conditions from `ConsumeAsync` (`backend/src/DisputeDesk.Infrastructure/Linking/OtpAttempts.cs:44`) together; the builder did that, and the superseding tests catch the superseded condition every time.
  - If only `ConsumedAtUtc == null` is dropped, the parallel test fails only when the third-counted attempt loses. That should be about 2 runs in 3; I worked this out but did not run it.

- **L2, missing test for the new branch.** The two-login loser on its third attempt is untested. A sequential test would make it deterministic:
  1. Start linking for both logins before either verifies.
  2. Login B sends two wrong codes.
  3. Login A links.
  4. B sends its correct code and expects 409, `LinkingLocked Rejected` with D's `CustomerId`, `locked` counted once, and B's challenge at 3 attempts and not consumed.
- **L3, privacy test text forms** (`LinkingPrivacyTests.cs:65`, `:67`, `:76`, `:92`). The hex checks are lowercase and case-sensitive, so `Convert.ToHexString`'s default uppercase output would go unnoticed. The row checks use hex only, so a Base64 HMAC in a text column would be missed. Fix: compare hex with `OrdinalIgnoreCase` and add Base64 to the row checks.
- **L4, simplicity and test strength** (`VerifyOtpInputTests.cs:70-73`). Under the AD-8 decision the conditional `if (TryGetProperty("errors"))` can never fail. Fix: assert that `errors` is absent, and change the theory's comment ("no field can be named, but none other than `code` is") to say no field is named.
