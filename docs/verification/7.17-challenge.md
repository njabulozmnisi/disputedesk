## Pre-mortem
- [story] The test passes locally but fails in CI because the generated private key is mounted with the host user’s ownership and PostgreSQL’s container user cannot read it. The story requires restrictive permissions but does not say how the server user obtains access.
- [story] A server that never becomes ready leaves the test waiting indefinitely or consumes the platform job’s existing 15-minute limit. No readiness deadline is specified.
- [story] The test passes while a real RDS deployment fails because the local `CREATEROLE` master does not reproduce every `rds_superuser` permission or RDS certificate behavior. The story correctly calls this an approximation; keep that limitation explicit in the result.

## Simplest design
- [story] Use one pinned PostgreSQL container on one disposable network, generate one CA and server certificate, create a non-superuser `dbmaster`, and run byte-for-byte copies of the deploy and init scripts through the specified narrow stubs. Reuse that server for the first and later deploy; use fresh database state for the two certificate-failure cases. No additional harness, image, or emulated AWS service is needed.
- [story] Remove the proposed `sslmode=require` deliberate-break expectation. It adds a misleading check rather than proof of `verify-full`.

## Assumptions
- [story] A certificate/key generated in the host temporary directory will be readable by the PostgreSQL server user. That does not follow from `0600` permissions on a bind-mounted file; specify ownership or a copy into a server-owned location.
- [story] The local role is a sufficient stand-in for the RDS master. AD-28 marks applying `infra/images/postgres` against RDS as an assumption, and the story expressly excludes proof of exact `rds_superuser` privileges.

## Standards
- [story] The supervisor check misunderstands libpq: with a root CA file present, `sslmode=require` also verifies the CA, so its wrong-CA run should **not** succeed. Change the mutation to `verify-ca` and expect only the wrong-host test to catch it. See [PostgreSQL 18 libpq SSL support](https://www.postgresql.org/docs/18/libpq-ssl.html).
- [story] The proposed TLS and `hostssl` mechanisms themselves follow [PostgreSQL’s server TLS](https://www.postgresql.org/docs/18/ssl-tcp.html) and [`pg_hba.conf`](https://www.postgresql.org/docs/18/auth-pg-hba-conf.html) approaches; no replacement mechanism is warranted.

## Gaps
- [story] Criterion 1 needs a testable way to put the key under the server user’s ownership while retaining PostgreSQL-accepted permissions; checking the file mode alone does not establish that the server can start.
- [story] Criterion 6 needs a bounded server-readiness wait and a failure message that distinguishes startup/TLS configuration failure from deploy failure. No new external request input lacks a stated bound; this missing bound is on test execution.
