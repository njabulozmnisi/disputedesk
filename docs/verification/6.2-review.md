# 6.2 review

## Review of story 6.2: OTP verification links the login (high-stakes)

**Verdict: changes.** The production code is correct on every focus point you named. I found no high findings. Two medium test gaps need fixing because this story is high-stakes: no test proves the conditional consume, and the 10-parallel test asserts a count the design does not guarantee, which could fail randomly on CI.

I reviewed the staged diff in `/private/tmp/claude-501/-Users-njabulomnisi-Projects-Dojo-DisputeDesk/77858989-3f5b-4d04-8184-f4d922dc16d1/scratchpad/t62` against b3c9dbf. I did not run the suite.

### Pass 1: correctness, by focus point

- **Attempt-counting raw SQL** (`backend/src/DisputeDesk.Infrastructure/Linking/OtpAttempts.cs:22-34`)
  - It is one `UPDATE … RETURNING` statement through `Database.SqlQuery<CountedAttempt>`. It is not composed on, and it commits on its own.
  - It is parameterised: the interpolated `FormattableString` turns `loginSub` and `MaxAttempts` into `@p0` and `@p1`.
  - **Why `ExecuteUpdate` cannot express it:** `ExecuteUpdateAsync` returns only the row count, and EF Core has no RETURNING form for bulk updates. Running a conditional `ExecuteUpdate` and then a read is racy: the read can see another parallel attempt's increment (wrong `attemptsRemaining`), or the row a superseding start just inserted (HMAC compared against a different challenge).
  - The WHERE clause matches the filter of `UQ_LinkingChallenges_LoginSub`, so it hits at most one row.
  - The builder's report gives the SQL as evidence, as the story asks.
- **Wrong codes answer 2, 1, then locked; a correct third links.** `RefuseAsync` returns `3 - Attempts` while under 3 and `Locked` at 3. When the update returns no row, one read tells locked from no challenge. `VerifyOtpAttemptTests` covers both runs, plus a fourth attempt with the correct code still answering locked.
- **Expiry.** `now >= ExpiresAtUtc` is checked against the stored value. Both boundary instants (one microsecond before, and exactly at expiry) are tested.
- **Consume, link insert and `Linked` audit in one transaction.**
  - The handler uses an explicit `BeginTransactionAsync`, the conditional `ExecuteUpdate` with exactly 1 row, then one `SaveChanges` for the link and the audit entry, then commit.
  - A race loser is handled cleanly: `AppDbContext.SaveChangesAsync` clears the change tracker on every failure, so the loser's later `Linked Rejected` save does not retry the failed insert.
  - If the audit insert fails, neither the link nor the consume commits (tested).
- **Every challenge kind answers like a wrong code.** No match, already linked, SIM swap failed and released each give the same status and body (apart from `traceId`) as a real challenge given wrong codes, attempt by attempt. A login with no challenge gets 2 every time and counts nothing.
- **`FixedTimeEquals` against a dummy.** `Otp.Matches` always computes the HMAC and compares it with a 32-byte zero dummy when `OtpHmac` is null. The no-challenge path does the same HMAC work.
- **Races.** The two-login race answers the loser 422 with 2 remaining, leaves it 1 attempt with its consume rolled back, and records `Linked Rejected`. Removing the `UQ_CustomerLinks_*` mappings fails it, as the supervisor check expects. There is no deadlock path: each transaction locks only its own challenge row, and the second insert waits on the first.
- **Session unchanged.** No `Set-Cookie`, the same cookie value, and the `Sessions` row keeps `Id`, `KeyHash`, `LoginSub` and `AbsoluteExpiresAtUtc`. The next request reads customer D's transactions and gets 403 on both linking routes. Logout still sends `id_token_hint`.
- **Code bounds.** `[Required, RegularExpression("^[0-9]{6}$")]`. `RegularExpressionAttribute` requires the match to cover the whole value, so `"123456\n"` is refused (tested). For bodies that do not bind, a 400 that names no field follows 6.1's `StartLinkingInputTests` precedent.
- **Other checklist items.** No null-forgiving `!` in production code. The OpenAPI change is only the verify operation and `VerifyOtpRequest`. Errors map as AD-3 says: 422 `BusinessRule`, 409 `Conflict`.
- **Handler location.** The handler sits in Infrastructure, not `Application/Linking/VerifyOtp/` as the story's Touches list says. This is justified: `CustomerLink` and `Database.SqlQuery` live in Infrastructure, and 6.1's `LinkingJobSteps` already sits there. The Touches list should be corrected at capture.

### The first full-suite failure: a test defect, not an environment flake

Two challenges created at the same test-clock instant get `Guid.CreateVersion7` IDs whose bits after the timestamp are random. So `ChallengesAsync`, which orders by `CreatedAtUtc` then `Id`, returns them in random order. A positional assertion on them fails about half the time.

- The builder fixed it properly, by picking each challenge by its state (the superseded-challenge test and the privacy test).
- No production code relies on that order.
- I grepped every `ChallengesAsync` use and found no remaining positional lookup in 6.2's tests. 6.1's `StartLinkingUniformTests:80` indexes by position, but it advances the clock 30 s first, so its order is fixed.
- A different timing-dependent assertion remains (finding 2).

### Pass 2: simplicity and standards

The code reads plainly. `OtpAttempts` follows `OtpSends`, `CountedAttempt` is what `SqlQuery` needs, and the `Error.BusinessRule` overload with extensions mirrors the existing `Conflict` one. The only indirect spot is finding 5.

Every mechanism follows a cited standard, and none is home-grown:
- `UPDATE … RETURNING` through `SqlQuery<T>`: https://learn.microsoft.com/ef/core/querying/sql-queries#querying-unmapped-types and https://www.postgresql.org/docs/current/sql-update.html
- Conditional consume checked by rows affected: https://learn.microsoft.com/ef/core/saving/execute-insert-update-delete
- Explicit transaction: https://learn.microsoft.com/ef/core/saving/transactions
- Constant-time comparison: `CryptographicOperations.FixedTimeEquals`, plus HMAC (RFC 2104)
- Generic responses: OWASP Authentication Cheat Sheet
- Input bounds: minimal API validation
- Race losers: the existing `UniqueViolations` (SQLSTATE 23505)
- Metrics: `IMeterFactory`

### Findings

1. **Medium.** `backend/src/DisputeDesk.Infrastructure/Linking/OtpAttempts.cs:44` (tests in `VerifyOtpRaceTests.cs` and `VerifyOtpLinkTests.cs`)
   - **Issue:** No test proves the conditional consume (criterion 1's "exactly 1 row", and security point S4: a start that supersedes mid-verify cannot link). You could delete `SupersededAtUtc == null && ConsumedAtUtc == null` from `ConsumeAsync` and every test would still pass:
     - In the same-login parallel test, `UQ_CustomerLinks_LoginSub` catches the second consume with the same outward result.
     - The superseded-challenge test never reaches the consume, because the count statement already filters out the superseded row.
   - **Fix:** Add a test that holds a correct-code verify between the count and the consume (for example a `DbCommandInterceptor` gate on the consume `UPDATE`, in the style of `FailAuditInsertInterceptor`). Start again for the same login (this supersedes the challenge), then release the verify. Expect 422 `otp-incorrect` with `attemptsRemaining` 2, no `CustomerLinks` row and `Linked Rejected`. Add "drop the consume's conditions" as a deliberate break.

2. **Medium.** `backend/tests/DisputeDesk.Api.IntegrationTests/Linking/VerifyOtpRaceTests.cs:45` (`Assert.Equal(3, challenge.Attempts)`)
   - **Issue:** The design guarantees at most 3 attempts, not exactly 3. Once the first matching request's consume takes the row lock, later count statements block. After that request commits, they see `ConsumedAtUtc` set and count nothing. So `Attempts` ends at 1 or 2 whenever the winner's consume lands before two other counts. That window is about one database round trip, so a loaded CI runner can hit it and fail the test.
   - **Fix:** Make it deterministic without changing the criterion. Gate every consume `UPDATE` with an interceptor until the test sees `Attempts == 3` in the database, then release them all: exactly one consumes and the others get 0 rows. This also exercises the conditional consume under contention, which supports finding 1.

3. **Low.** `backend/src/DisputeDesk.Infrastructure/Linking/VerifyOtpHandler.cs:88-91` and `:133`
   - **Issue:** When a same-login parallel verify loses the consume on attempt 3, `RefuseAsync` calls `metrics.RecordLocked()`. That challenge was consumed (linked), not locked, so `locked` is over-counted against criterion 8 ("once per challenge, when it locks"). The two-login loser on attempt 3 is correctly counted, because its consume rolled back and its challenge really is locked.
   - **Fix:** In the `consumed != 1` branch, answer without recording `locked`, for example with a flag to `RefuseAsync`.

4. **Low.** `backend/tests/DisputeDesk.Api.IntegrationTests/Linking/VerifyOtpInputTests.cs:44` and `:75`
   - **Issue:** This is the known pitfall: a short literal checked for absence against the whole body. `"12345"` and `"123456"` are matched against raw text that includes a random 32-hex `traceId`. Also, an echoed `"١٢٣٤٥٦"` would be JSON-escaped (`١…`), so the raw-text check cannot detect it.
   - **Fix:** Parse the body, remove `traceId` (as `StatusAndBodyAsync` already does), and check the decoded string values, not the raw text.

5. **Low (simplicity).** `backend/src/DisputeDesk.Infrastructure/Linking/VerifyOtpHandler.cs:91, 111, 132`
   - **Issue:** Passing `AuditAction.Linked` to `RefuseAsync` doubles as a "lost a race" flag that `lockingAction` then decodes. A reader has to work that out.
   - **Fix:** Pass the race-loss fact explicitly (for example `bool lostRace`). This can be done together with finding 3.
