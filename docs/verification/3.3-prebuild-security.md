## Points

### C1 [story] Three authorization states and the check order on both new GETs (if missed: medium)

Criterion 6 proves that the `Linked` policy is attached, which is metadata only. The checklist asks for each endpoint to be tested in all three states, and the transactions list already does this (`TransactionsAuthorizationTests`). For `GET /api/v1/disputes` and `GET /api/v1/disputes/{disputeId}`, state and test:

- anonymous gets 401 `unauthorized`, with no redirect and no `WWW-Authenticate` (AD-8);
- an unlinked login gets 403 `linking-required`;
- a linked customer gets 200;
- an unlinked login with `limit=51`, a 129-character `cursor`, or a non-GUID `disputeId` still gets 403, not 400. Checks run 401, 403, then 400 (FR-24, AD-8, AD-10);
- a request with only `Authorization: Bearer <token>` and no cookie gets 401, because customer routes accept only the cookie scheme (AD-8).

Sources: Microsoft Learn, *Policy-based authorization*; ASVS 5.0 V8.2.1 (function-level access) and V8.3.1 (enforced at a trusted service layer).

### C2 [story] Ownership on the list, cursor tampering included (if missed: medium)

Criterion 1 says the list reads "through the ownership filter", but no criterion tests the list against another customer's data. Criterion 5 covers the detail only. Add:

- Customers A and B have disputes interleaved by `CreatedAtUtc`, one pair sharing an instant. Every page of A's list holds only A's disputes, and B's rows never change A's `nextCursor`.
- A cursor that encodes the `(CreatedAtUtc, Id)` of B's dispute gets 200 with only A's rows after that position. The answer is the same whether that position belongs to B or to no dispute.
- `?customerId=<B>` and a customer-ID header are ignored, as `ListTransactions_CustomerIdInQueryAndHeader_StillReturnsTheLinkedCustomer` proves for transactions.

State in the story that the cursor is a position, not a capability. Ownership comes only from the filter (AD-11), so the cursor needs no signature.

Sources: EF Core, *Global query filters*; ASVS 5.0 V8.2.2 (data-specific access, IDOR/BOLA).

### C3 [story] Decoded cursor bounds: a non-UTC instant is a 500 today (if missed: medium)

A cursor that is valid base64url and decodes to a well-formed pair such as `2026-10-01T10:00:00+02:00|<guid>` passes criterion 2's listed cases. Npgsql 10.0.3, the pinned version, then throws when it writes that parameter. Its resource string reads "...to PostgreSQL type 'timestamp with time zone', only offset 0 (UTC) is supported", which I checked in the installed `Npgsql.dll`. The request would end as a 500. State and test:

- a decoded instant with a non-zero offset gets 400 `validation` naming `cursor`;
- the instant is parsed in its exact round-trip form and the ID as an exact GUID, so trailing or extra content is 400;
- decoding uses `System.Buffers.Text.Base64Url`, as `TransactionCursor` does;
- every 400 body never echoes the submitted value (AD-3). The test asserts that the sent `cursor` string, and `abc` for `limit`, are absent from the body.

Unverified: that built-in minimal API validation enforces `[MaxLength(128)]` on a query-string parameter. `TransactionCursor` checks its length by hand. Criterion 2's 129-character case proves it either way.

Sources: Microsoft Learn, *Validation in minimal APIs*; RFC 4648 §5; ASVS 5.0 V2.2.1 (positive input validation) and V16.5.1 (generic errors).

### C4 [story] The privacy test checks every private field (Known pitfall, 3.8) (if missed: medium)

Criterion 4 names actor type, actor identity, SLA and due date. The pitfall requires the test to check every private field of the records the responses are built from. State and test:

- an exact allowlist of JSON property names for each shape: page, list item, detail, snapshot and timeline entry;
- a value scan of every list and detail body for these values:
  - from the `Disputes` row: `CustomerId`, `SlaDueAtUtc` (in the wire format) and the internal status `escalated`;
  - from every `StoredEvents` row: `ActorId` (the customer's own login `sub`, an operations `sub`, `worker:sla-sweep`, `worker:seeder`), the `ActorType` values `customer`, `operations` and `automation`, `TraceId`, and the `SlaWarningRaised` type and its data.

Any new Application record that holds the snapshot or the customer ID, such as a list-row projection, seals `ToString` as `StoredEvent` does (the pitfall's second half).

Sources: AD-13 (Customer wire view); OWASP Authorization Cheat Sheet (deny by default); ASVS 5.0 V15.3.1 (return only the required subset of fields).

### C5 [story] Identical 404: compare more than the body (if missed: low)

Criterion 5 compares the bodies with `traceId` removed. Also compare:

- the status, `Content-Type`, and the response header names and values, excluding `Date` and trace headers;
- that `detail` and `instance` never carry the requested ID (AD-3: errors never echo a value).

Use for B a dispute whose stream holds every stored event type, so the stored-event filter through the dispute is exercised on the detail read, not only the `Disputes` row.

Sources: RFC 9457; AD-11 (Not found); ASVS 5.0 V8.2.2.

### C6 [story] The unknown-row skip and the detail read never log stored event data (if missed: medium)

AD-22 says stored events are never logged or traced. State that:

- the skip in `StoredEventRow` checks `EventType` and logs nothing, or at most one `[LoggerMessage]` with the stored event `Id` and `EventType`;
- a known-type row whose `Data` fails to deserialise gives 500 `internal` with only `traceId`. The exception that `UnhandledExceptionHandler` logs then carries no `Data` value.

Test this as `StoredEventPrivacyTests` does for the raise: put a marker in the unknown row's `Data` and in a corrupt known-type row's `Data`, and assert that no captured log line, span attribute or response body holds it.

Sources: OWASP Logging Cheat Sheet (data to exclude); ASVS 5.0 V16.2 (log content) and V16.5.1.

### C7 [decision] Refused customer reads are not audited (if missed: low; human decides)

AD-14a audits customer refusals only for raise and withdraw. A 403 `linking-required` on the new GETs, or a 404 for another customer's dispute ID, writes nothing. ASVS 5.0 V16.3.2 asks for failed authorization attempts to be logged, and a run of 404s on foreign IDs is the enumeration signal. Two controls already make enumeration impractical: UUIDv7 IDs have 74 random bits (RFC 9562), and the gateway applies `limit_req` (AD-23). The options are:

- **(a)** Accept for v1 and record in AD-14a that customer reads are not audited.
- **(b)** Extend AD-14a with a customer `DisputeRead` `Denied` / `Rejected` entry through `AuditLog.Record`, which needs 2.8 merged.

I recommend (a).

## Already covered, no action

- **Response caching.** `Cache-Control: no-store` is set on every `/api` response (`SecurityHeaders`, `SecurityHeadersTests`).
- **Antiforgery.** The GETs are safe methods, and the group's antiforgery filter lets them through.
- **Filter bypasses.** The `IgnoreQueryFilters` bypass is limited by `OwnershipRulesTests`.
- **500 bodies.** A 500 carries only `traceId` (`UnhandledExceptionHandler`).
- **Core banking.** Neither read calls core banking (criterion 7), so no customer identifier crosses to the stub.
- **Response size.** `limit` caps a page at 50, and a timeline is bounded by the dispute lifecycle.
