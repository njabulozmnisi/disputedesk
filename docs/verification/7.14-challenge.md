VERDICT: SIMPLIFY

## Pre-mortem

- [story] A tab shows stale customer data after sign-out because an in-flight response repopulates a cleared query cache, or a mutation callback writes draft state after cleanup. Criterion 1 checks cancellation and the final cache, but not late completions; `ReviewScreen.tsx` has mutation success callbacks that invalidate queries and mark a draft submitted.
- [story] An idle tab signs out while another is active. `BroadcastChannel` activity reaches only listening tabs; a suspended or newly opened tab cannot recover earlier messages. A response timestamp alone is not a reliable shared session clock.
- [story] Failed sign-out leaves the person on a protected route or redirects them away from the promised start page. `SessionGate.tsx` sends a locally “anonymous” session to `/`, while a server session still exists when the antiforgery fetch fails.

## Simplest design

- [story] Keep one session-end operation: stop further customer requests, cancel and remove customer queries, reset the raise draft and submitted IDs, then show the appropriate screen. Call it for 401, local timeout and received tab-end messages; make sign-out invoke it **before** fetching its token, while retaining a narrowly scoped retry state on the start page. Test late responses and mutation callbacks against that operation. Do not introduce a second cache, storage layer, coordinator service or new route.
- [story] Use the existing response listener for local activity and one `BroadcastChannel` for cross-tab activity and end notices. Treat the browser timer as a privacy cutoff, not proof of server authentication; keep the server session authoritative. For the outage procedure, extend the existing runbook with read-only backlog checks and `docker compose start redpanda`, not a recovery command or row mutation.

## Assumptions

- [story] The story assumes a response means the server renewed the idle limit. AD-7 says renewal happens **on request**; a delayed response moves the browser’s 15-minute clock later than the server’s.
- [story] The story assumes a cleared session query can also drive the failed-logout start page. `SessionGate.tsx` currently derives navigation from that query, so the retry presentation needs an explicit rule that does not mistake a failed logout for server-confirmed anonymity.
- [story] The runbook assumes a fresh stack has no unrelated `Pending` rows. AD-17 says seeded disputes also produce outbox rows; the procedure must identify the outage’s rows or record a baseline before claiming its backlog drained.

## Standards

- [story] The proposed `activity`/`expired`/`signed-out` messages are application-specific, not an industry session protocol. That is acceptable over the standard [BroadcastChannel API](https://html.spec.whatwg.org/multipage/web-messaging.html#broadcasting-to-other-browsing-contexts), but the story should say they are best-effort tab notifications; the server remains the authority under [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html) and AD-7. Do not build a custom distributed session authority in the browser.

## Gaps

- [story] Criteria 1–4 need an assertion that late query responses and mutation callbacks cannot restore customer data or a draft, including a 401 racing sign-out and activity arriving after an end notice.
- [story] Criterion 2 needs a defined rule for a newly opened, suspended or restored tab that missed activity, and for delayed or out-of-order responses. Otherwise “no tab ends a session another tab is using” is not testable as an unconditional guarantee.
- [story] Criterion 3 needs explicit expected behavior for a token-fetch **401** versus a network failure, and for retry while the server session remains authenticated. Current `useSignOut.ts` routes a token-fetch 401 through the session-ended handler.
- [story] Criterion 4’s “no request made” cannot forbid a request already in flight in the receiving tab; specify **no new request initiated** and test the in-flight case.
- [story] Criterion 8 needs a bounded drain check, a baseline or identified dispute IDs, and a per-dispute ordering check. AD-17 promises at-least-once delivery with a handover exception to broker arrival order, so “events on the topic in per-dispute order” must be scoped to this ordinary single-relay recovery, not presented as a universal guarantee.
