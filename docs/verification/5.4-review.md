# 5.4 review

## Review of 5.4: seeded disputes for customers A and B in every status (high-stakes)

**Verdict: changes.** The production code is sound and I found no high-severity problem. The one blocking item is a test race, and it is the most likely cause of the builder's unidentified Seeding flake. As instructed, I did not run the suite. I reviewed only 5.4's own delta: `.../scratchpad/delta/5.4-delta-backend.diff` and `5.4-delta-other.diff`, with the code read in `.../scratchpad/delta/new54`.

### Pass 1: correctness

Every criterion has a test that would fail without the change:
- **AC1:** all seven of A's status/outcome pairs, `Version` equal to the stream length, and every mapped property plus the timeline compared with the replayed stream. Because the clock is not microsecond-aligned, this replay test is also what proves the microsecond cut.
- **AC2:** SLA demo due time and created time checked as stored values; transaction at least 11 days old.
- **AC3:** reuses `AssertSameNotFoundAsync`; the README says how to find B's dispute ID.
- **AC4:** counts, stored event ID = outbox ID, and actors. The already-migrated path is covered.
- **AC5:** the four `SeededLinksTests` cases extended, plus a new downgrade case. Without the `AddDisputes` check the downgrade test fails on the missing table. Zero audit rows and no metrics asserted.
- **AC6:** the actor test, the snapshot-equals-stub test, and the more-than-7-days test at both ends of the South African day.
- **AC7:** five invalid entries, error messages that hold only the position, readiness stays 503, the notes fixture test, and a counts-only log test.

Mechanics all check out:
- The second context is built exactly as `OutboxRelay` builds its own (`OutboxRelay.cs:180`). The registered options add nothing else, so the model and conventions match.
- `UseTransaction(CurrentTransaction?.GetDbTransaction())` joins EF's transaction when one is open. Inside it, each `SaveChanges` gets a savepoint, so each stream stays all or nothing.
- There is no `IgnoreQueryFilters` under `Seeding/` and no `!` in production code.
- Back-dated outbox rows get `NextAttemptAtUtc = OccurredAtUtc` (`CommitRows.cs:83`), so the relay picks them up at once, and per-dispute version ordering holds.

**About the flake.** I judge it a real isolation defect in a test, not a production ordering defect. `InvalidFixtureDisputesTests` creates an empty database and starts the host, so `DatabaseMigrator` starts migrating in the background. The test then immediately calls its own `MigrateAsync` on the same database, with no retry. Every existing two-migrator test waits for readiness first; this one can't, because readiness never comes. The two first migrations race on creating the history table and schema, before EF's lock exists. With Npgsql, the lock is a `LOCK TABLE ... IN ACCESS EXCLUSIVE MODE` taken inside a transaction (I confirmed the strings in Npgsql.EntityFrameworkCore.PostgreSQL 10.0.3). Concurrent `CREATE ... IF NOT EXISTS` in Postgres can fail with 23505 or 42P07. That would raise a `PostgresException`, and `Assert.ThrowsAsync<InvalidOperationException>` requires the exact type. This is consistent with "1 of 16, then green five times", but I have not reproduced it.

### Pass 2: simplicity

The design is the smallest that meets the criteria. It reuses the existing hooks, the second context copies the relay's construction, and there is one `SaveChanges` per dispute. It adds no new interface, writer, bypass, option or package. Moving the fixture records out of `Seeder` and having `SeedDispute` both plan and write each earn their place. The sync and async loops are duplicated, but EF requires both delegates and the link seeder already does the same. Every method reads on first pass. Making `NotFoundResponsesTests.AssertSameNotFoundAsync` internal is a test-only change outside Touches, and harmless.

### Standards check

Every mechanism the diff adds follows a cited, documented approach; there is no home-grown replacement:
- **Seeding:** `UseSeeding` / `UseAsyncSeeding` (https://learn.microsoft.com/ef/core/modeling/data-seeding).
- **Joining the migration's transaction:** `Database.UseTransaction` (https://learn.microsoft.com/ef/core/saving/transactions#cross-context-transaction); savepoints in it are automatic (same page, #savepoints).
- **Ownership:** global query filters (https://learn.microsoft.com/ef/core/querying/filters).
- **Strict fixture reading:** System.Text.Json `RespectRequiredConstructorParameters` / `RespectNullableAnnotations` and `JsonStringEnumConverter` with `allowIntegerValues: false` (https://learn.microsoft.com/dotnet/standard/serialization/system-text-json/required-properties).
- **Counts-only log line:** `LoggerMessage` source generator (https://learn.microsoft.com/dotnet/core/extensions/logger-message-generator).
- **South African time:** fixed UTC+02:00, the repo's AD-4 convention (`Disputability.cs:13`).
- **Microsecond cut:** plain tick arithmetic, the repo's existing pattern; .NET has no built-in for it.
- **Redelivery:** consumers deduplicate by CloudEvent `id`, per AD-17 (Idempotent Receiver, EIP).

### Security and data integrity

- Seeding only runs with `Seed:Enabled` on.
- Error messages and the log line hold no customer ID, note or dispute ID, and `SeedDispute.ToString` prints only the position.
- No raw SQL and no new dependencies.
- Integrity risk: none found. The lock question above affects a comment's accuracy, not the rows.

- The flake's root cause is inferred from the code, not reproduced.
- EF Core 10's seed-inside-lock behaviour on the fresh path; I couldn't read the source locally.
