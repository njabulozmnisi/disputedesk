## The two-permit edge: confirmed

I read the framework source at release/10.0 (copies are in `/private/tmp/claude-501/-Users-njabulomnisi-Projects-Dojo-DisputeDesk/77858989-3f5b-4d04-8184-f4d922dc16d1/scratchpad/sec63src/`).

- **The middleware asks twice.** In `RateLimitingMiddleware.TryAcquireAsync`, `CombinedAcquire` first calls `_globalLimiter.AttemptAcquire(context)`. If that lease is not acquired, it then calls `CombinedWaitAsync`, which calls `_globalLimiter.AcquireAsync(...)`. Only then does it reject.
- **The chain keeps the first permit.** `ChainedPartitionedRateLimiter.AttemptAcquireCore` and `AcquireAsyncCore` ask each limiter in order. On a failure they dispose the leases already taken.
- **Disposing does not give the permit back.** In `SlidingWindowRateLimiter`, a permit is booked into the current segment by `_requestsPerSegment[...] += permitCount; _permitCount -= permitCount`. Disposing the lease does not undo this. With `QueueLimit` 0, `AcquireAsync` grants at once while permits are left.

So a request the login limit rejects spends two IP permits. The exception is when only one is left: the second call is then rejected by the IP limiter itself. A request the IP limit rejects spends nothing. A quick GitHub search found no upstream issue. The Microsoft Learn page does not describe the two calls; only the source shows them.

**Security impact: low.** It does not weaken brute-force protection. The per-login limit (5) and the OTP lockout after 3 wrong codes are unchanged, and the IP limit is only stricter.

It does make denying linking to everyone behind one NAT cheaper. One login empties a shared IP's 20 permits in 13 requests (5 allowed, then 8 rejected) instead of 20. That exposure comes from the IP-first order of decision 3, not from the double count: with one permit per rejection, one login still empties the IP in 20 requests, and any 4 logins always can. Permits come back one segment (a minute) at a time. The gateway's `limit_req` (10 r/s, burst 20) does not prevent it.

**Options for you, all using documented mechanisms:**

- **A. Keep the IP-first chain and change the wording.** FR-8, architecture.md line 159 (AD-12) and criterion 1 would say a login-rejected request spends IP permits (two, because the middleware calls `AttemptAcquire` and then `AcquireAsync`). Cite the middleware source, since Learn does not document this. No code change; the test already pins two.
- **B. Put the login limiter first.**
  - What it fixes: a login-rejected request spends no IP permit, so one login can take at most 5 of an IP's 20 per window. Denying a NAT then needs 4 logins.
  - What it costs: an IP-rejected request spends two login permits. A real user retrying behind an exhausted NAT uses up their own 5 and can then be login-limited for up to a window after the IP recovers.
  - What else changes: it reverses decision 3, and the supervisor's deliberate break (swap the order, expect the test to fail) must be rewritten.
  - Source: Microsoft Learn, Rate limiting middleware, chained limiters.
- **C. Per-endpoint policies instead of a global chain.** The IP limiter would be the `GlobalLimiter` and the login limiter a named `AddPolicy`, applied with `RequireRateLimiting` on the linking group. This does not change the count: the middleware always runs the global limiter before the endpoint limiter, in both calls, so the same two permits are spent.
  - What it does add: `RequestRejectionReason` tells which limiter rejected, so a policy's own `OnRejected` could audit the right partition, and the `LinkingRateLimitMetadata` marker could go.
  - Source: Microsoft Learn, Rate limiting middleware, `AddPolicy` and `RequireRateLimiting`.
- **D. A wrapper limiter that spends one permit.** Possible, but home-made where a standard exists (at least a medium finding under the security checklist). I agree with the builder not writing it.

Timing-based limiter types do not help either. Fixed window and token bucket also keep their permits when a lease is disposed, and a concurrency limiter has the wrong meaning.

## The checks you asked for

- **Both linking routes are limited.** Group metadata (`LinkingRoutes.cs`, `WithMetadata`) covers start and verify. The limiter matches the routed endpoint, so an upper-case path is limited (tested). Other routes get `GetNoLimiter`.
- **401 and 403 take no permit.** `UseRateLimiter` comes after `UseAuthentication` and `UseAuthorization` (`Program.cs:77`). The test sends 25 anonymous and 25 linked requests, then all 20 IP permits are still there; the builder's break of moving the limiter first fails it. A 400 (malformed body or missing antiforgery token) takes a permit, as the story says. The login partition is the `sub` of the cookie policy's principal.
- **Retry-After is the full window.** It is `Math.Ceiling(window.TotalSeconds)`: 900 in production and 60 with the test window, both tested.
- **Only the first rejection per window is audited.** A dedicated `MemoryCache` with `SizeLimit` 10,000, `Size` 1 per entry, each entry expiring one window after it is set. The window test proves re-auditing after expiry; see finding 3 for the gap.
- **The built-in metric is used and exported.** The `MeterListener` counts 6 rejections tagged `global_limiter`, and the test waits for OpenTelemetry to export `aspnetcore.rate_limiting.requests`.
- **The options are checked at start-up.** `ValidateOnStart` covers both sides of every bound (0/1 and 1000/1001 permits; 0, negative and 1 h + 1 s windows; 0/1 and 60/61 segments; segments that are not whole seconds). Each error names the key, never its value. `ApiFactory` raises the permits to 1000 for the other suites.
- **The 429 body is generic.** It has the exact field set listed in finding 8, and both limits return the same body (tested).
- **ClientIp comment:** it now names story 6.6 and the trusted network (6.6 is merged).
- **ClaimAsync:** it requires `Attempts < LinkingChallenge.MaxAttempts` (3). `Job_ChallengeLockedByThreeWrongCodesBeforeTheClaim_ClaimsNothingAndSendsNoSms` proves it, and the builder's break of removing the condition fails it.
- **No personal data in logs.** The audit-failure log has only `Action`, with no exception attached (tested). The audit row holds the login `sub` as actor and the client IP, with no customer ID and no ID number, the same as 6.5's `LinkingRateLimited`. Nothing is added to traces or events.
- **Pre-build points:** every remaining point in 6.3-challenge.md, 6.3-prebuild-review.md and 6.3-prebuild-security.md (S3, S4, S5; `Retry-After`; the options; the cache; the limiter details) is met. The forwarded-header points (S1, S2, S6) moved to 6.6, which is merged. Headers and CSP are unchanged.

Pass. The null-IP partition finding is closed by `NotLinkingPartition` (a non-ASCII key no IP or OIDC `sub` can equal) and its test; the IP-half audit test and the nits are closed. The delta adds no new issue; headers, CSP, packages, audit, the 429 body and logging are unchanged. Secret scan (whole uncommitted change) clean; Semgrep 1.181.0 0 findings.

QA O1 (the limiter runs before the antiforgery endpoint filter, so a forged-token request spends the signed-in login's permits): low, no action for v1. It needs the victim's session cookie, which `SameSite=Strict` keeps off cross-site requests; the worst case blocks that victim's own linking for one window and bypasses nothing. Reordering would need a non-standard antiforgery middleware or a limiter in a filter (ASVS 5.0 V3.3.2, V3.5.1, V2.4.1).
