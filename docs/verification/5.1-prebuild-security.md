# Pre-build security read: 5.1

Security (pre-build), base `8134305`. One high (S1), three `[decision]` points (S1, S2, S10). Already covered: the cookie gets 401 on the operations route and the bearer gets 401 on a customer route, both without a redirect; wrong issuer, audience or signature and an expired token get 401 with `WWW-Authenticate: Bearer`; a missing role and an unmapped `sub` get 403; a successful read writes `DisputeRead` `Succeeded`; operations see `SlaWarningRaised`; Scalar is behind `Scalar:Enabled`; `clientCredentials` is declared on the operations routes only. `provision.sh` already creates the machine user with `ACCESS_TOKEN_TYPE_JWT` and all four role keys. `Microsoft.AspNetCore.Authentication.JwtBearer` 10.0.14 exists on nuget.org, published by Microsoft, the same patch as OpenIdConnect.

| # | Sev | Finding |
|---|---|---|
| S1 | high | [decision] A pre-filled client secret reaches every visitor of `/scalar/`. Scalar.AspNetCore 2.18.3 renders its configuration, including `ClientCredentialsFlow.ClientSecret`, inside an inline `initialize(...)` script. The page is `AllowAnonymous`, and AD-26 turns Scalar on in the AWS demo. Anyone who opens the page there gets a credential with all four roles over every customer's dispute. A secret delivered to a browser is no longer confidential (RFC 6749 §2.1, §10.1; ASVS 5.0 V13.3.1). The 2026-10-27 decision ("local stand-in") conflicts with AD-26 ("on in the AWS demo"). Recommended: Scalar never pre-fills the secret. It pre-fills only the client ID and token URL, and the person enters the secret from `zitadel-clients.json`. Alternative: pre-fill only where a local-only setting allows it, with a test that the AWS configuration serves no secret. With either option, the Api need not hold `Zitadel:OperationsTools:ClientSecret` at all (least privilege). |
| S2 | medium | [decision] A fixed CSP hash cannot match Scalar's inline script. The script embeds per-environment values (token URL, client ID, and the secret, which `provision.sh` regenerates), so AD-26's "Scalar's script by hash" in a static nginx template breaks. Scalar 2.18.3 renders a `nonce` attribute (it reads a `Scalar.Nonce` value; the builder verifies this in the source). That nonce would have to come from the Api, which is an exception to AD-23 (nginx owns the headers). Whichever option is chosen, `script-src` never gains `'unsafe-inline'` or `'unsafe-eval'` (ASVS 5.0 V3.4.3; CSP Level 3 hash-source and nonce-source). |
| S3 | medium | [story] Scalar shares the customer SPA's origin. Any script on `/scalar/` can call the customer API with the session cookie and fetch the antiforgery token. The `/scalar/` CSP stays `script-src 'self'` plus the hash or nonce, `connect-src 'self' <auth origin>` and nothing else, and keeps `object-src 'none'`, `frame-ancestors 'none'`, `base-uri` and `form-action`. The location defines its own CSP, so nginx drops the inherited `add_header` lines; it must include the other headers again, and `infra/smoke.sh`'s exactly-once header loop must cover `/scalar/` (OWASP HTTP Headers Cheat Sheet). A separate origin for the API viewer goes in `docs/production-path.md`. |
| S4 | medium | [story] Prove scheme pinning across all endpoints, not one route. Extend `EndpointAuthorizationTests`: for each endpoint, combine its `IAuthorizeData` through `IAuthorizationPolicyProvider` and assert the schemes are exactly `JwtBearer` under `/api/v1/operations/` and never include `JwtBearer` elsewhere. Also assert the default authenticate scheme stays `Cookies`, so the fallback and default policies stay cookie-only. Map the operations group on `apiV1`, not under `MapCustomerRoutes()`: combining with `Linked` would merge both schemes and add the antiforgery filter. No `ForwardDefaultSelector` or policy scheme (AD-8 Rejected). Add one HTTP case: a bearer token on a linking-group or default-policy endpoint (`/api/v1/bff/antiforgery`) gets 401 (Microsoft Learn, *Authorize with a specific scheme*; ASVS 5.0 V8.3.1). |
| S5 | medium | [story] A customer's ID token authenticates on the operations routes. Zitadel puts the project ID in the `aud` of ID tokens, and the BFF ID token crosses the browser in the logout redirect (AD-7). Issuer, audience and signature therefore all pass, and only the missing role and unmapped `sub` refuse it. The builder checks Zitadel's access-token `typ`: if it is `at+jwt`, set `TokenValidationParameters.ValidTypes = ["at+jwt"]` (RFC 9068 §4; ASVS 5.0 V9.2.2). Otherwise, state that the actor mapping is the backstop, and add a test: a token shaped like the ID token, from the same issuer and audience, with a customer `sub` and `dispute.read`, gets 403. |
| S6 | medium | [story] Audit gaps. (a) A 404 read records `DisputeRead` with `Rejected`, actor and requested ID. FR-25 says "a rejected operations attempt after authentication (403, 404 or 409) is written to the internal audit log", and NFR-SEC-10 says "every operations read". Criterion 4 audits only success, and 5.2 covers only its own actions' 404s, so this 404 is never audited. (b) Say who records `Denied` for a 403 on the read route: here, or in 5.2's result handler, whose criterion 5 names "actions" only. (c) Save the audit entry before the body is returned, so a failed save is a 500 with no dispute data (fail closed, as for `SignIn`, AD-7). Sources: ASVS 5.0 V16.3.2; OWASP Logging Cheat Sheet. |
| S7 | medium | [story] List every field the operations response returns. Build it from typed records through an explicit mapping, never by serialising a `StoredEvent` record or `StoredEvents.Data`: `DisputeRaised` holds `CustomerId`, and the snapshot holds `Direction`, `Kind` and `State`. Timeline entries carry `actorType` and no `actorId`; for customer actions the `actorId` is the customer's login `sub`. Following the 3.8 Known pitfall, a privacy test asserts the body contains no seeded `CustomerId`, no customer `LoginSub`, no operations `sub` and no `TraceId` (FR-30 "no personal details beyond the snapshot"; ASVS 5.0 V14.2.6). |
| S8 | medium | [story] Complete the token validation cases in criterion 2. Add `alg: none`; HS256 signed with a symmetric key (algorithm confusion); a token without `exp`; `nbf` in the future; an unknown `kid`. Pin `ValidAlgorithms` to what Zitadel's discovery advertises (RS256; verify `id_token_signing_alg_values_supported`). Keep `ClockSkew` at its documented default. Take `RequireHttpsMetadata` from the existing `Zitadel:RequireHttpsMetadata` (true by default, false only in local Compose), and make `ProjectId` `[Required]` with `ValidateOnStart` (ASVS 5.0 V9.1.1, V9.1.2, V9.1.3, V9.2.1, V9.2.3, V10.3.1). |
| S9 | low | [story] 403 must come before 404. Criterion 3's no-role and unmapped tokens call an unknown dispute ID as well as a real one and get 403 both times, so a caller cannot probe which IDs exist (FR-24 order). The unmapped-`sub` token carries `dispute.read`, so only the actor mapping refuses it. Validate `Operations:Actors` on start: any value other than `operations` fails startup (AD-9 "exactly one actor type (`operations`)"; ASVS 5.0 V10.3.3, since one issuer is pinned the `sub` is unique). |
| S10 | low | [decision] AD-9 falls back to the `urn:zitadel:iam:org:project:roles` claim. | S11 | low | [story] Scope of the ownership bypass. The handler uses the named `IgnoreQueryFilters([AppDbContext.OwnershipFilter])` on both `Dispute` and `StoredEventRow`, never the parameterless form, which would also drop future filters. The architecture test accepts both forms, so tighten its regex. Move the Notes' AD-11 reference rule into a criterion: `Disputes/` or `Transactions/` must not reference `Operations/` or `Sla/`. | S12 | low | [story] Scalar options: `DisableTelemetry()`, `DisableDefaultFonts()` (CDN fonts), no `WithProxyUrl` (a proxy would see the secret and tokens), and persistent authentication left off (otherwise the token sits in the app origin's `localStorage`). `Scalar:Enabled` is `false` in `appsettings.json`. `MapOpenApi()` goes behind the same switch. `ApiReferenceTests` and `EndpointAuthorizationTests` switch from `Development` to the setting. |
| S13 | low | [story] Error details and telemetry. Set `JwtBearerOptions.IncludeErrorDetails = false`: the default echoes `error_description` with the reason for the failure, and RFC 6750 §3 makes it optional (ASVS 5.0 V16.5.1). IdentityModel `ShowPII` stays false. Extend the AD-20 telemetry check to the operations read: no seeded customer ID or account reference, and no `Authorization` value, in logs or spans. |
| S14 | low | [story] Provisioning. The "file is current" check in `provision.sh` must also require `Operations.Actors[<OPS_ID>] == "operations"`. Otherwise an existing file keeps no mapping and every operations call gets 403; that fails closed, but the supervisor check would fail. Record the machine user's access-token lifetime (verify Zitadel's default) and `private_key_jwt` (RFC 7523) for real tools in `docs/production-path.md`. |

If it does not, tokens are minted from the system clock. |
