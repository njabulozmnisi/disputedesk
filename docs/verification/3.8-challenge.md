VERDICT: RETHINK

## Pre-mortem

- [decision] A deployment encounters a database that already applied `AddDisputes`. Rewriting that migration under the same ID leaves its old `TimelineEntries` schema in place, while the new code expects `StoredEvents`. The story acknowledges this for local volumes, but AD-22 also requires migrations to remain compatible with the previous release. Decide explicitly whether this is an unreleased-schema reset or requires a forward migration.
- [story] A save failure is mistaken for a safe retry. `AppDbContext` currently takes pending changes before saving and clears its tracker only for mapped unique violations; criterion 6 must cover *every* save exception in both synchronous and asynchronous paths.

## Simplest design

- [story] Keep one pending-event list on `Dispute`; use the same `Apply` cases for creation and replay. In the existing `SaveChanges` path, guard insert-only records, add a stored row and an outbox row only for published types, then let EF commit the tracked read model with them. Build the customer timeline from the supplied stream using one allowlist. No event-store service, second concurrency token, timeline table, or separate audit row is needed.

## Assumptions

- [decision] The migration can be rewritten because only disposable development databases have applied it. The story says local volumes must be recreated; AD-22 says migrations stay compatible with previous-release code. Those statements need a deployment-status decision.
- [decision] Raise refusals can wait until 3.4. The story says so, but architecture AD-14a assigns raise-refusal auditing to 3.8, while a later architecture note assigns it to 3.4. Set one owner before building.

## Standards

- [decision] Replacing an already-applied migration under its existing ID is not a safe migration path. If that schema has been deployed, use an additive forward EF Core migration rather than editing applied history: [EF Core, Managing migrations](https://learn.microsoft.com/ef/core/managing-schemas/migrations/managing). If it has never been deployed, document the reset exception and its scope.
- [story] No other proposed mechanism needs a new standard: the single-save transaction, query filter, change-tracker clear, and private-to-integration-event mapping have documented approaches in the story’s references.

## Gaps

- [story] Criterion 7 says to commit **each** event type, but this story adds no aggregate methods that can append four status changes or an SLA warning. Specify how those commit tests create legitimate pending events, or defer those commit assertions to the stories adding the methods; retain mapping tests here.
- [story] Criterion 11 calls the timeline “built from the replayed stream,” while criterion 1 removes the aggregate’s timeline. State that replay returns dispute state and the customer view receives the **same ordered stored-event stream** separately; otherwise an implementation could silently reconstruct state but omit timeline entries.
- [story] Criterion 2 needs malformed-stream cases: empty stream, missing or duplicate version, a first event other than `DisputeRaised`, and an unknown `EventType`. Specify whether loading fails rather than returning a partial dispute; a customer allowlist hiding an event must not make corrupted state look valid.
