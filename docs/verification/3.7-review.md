**Findings, by severity:**

1. **medium**: `frontend/src/app/RootLayout.tsx:40-45` and `frontend/src/app/usePageHeading.ts:18-22`.
   - **Issue:** "Is this the first screen?" is a callback that answers true once, and the effect calls it. That effect is not safe to run twice.
   - Under StrictMode, which `main.tsx` uses, React runs effects twice in development. The first run uses up the "first screen" answer and the second run focuses the `h1`. So in the dev server the first Tab no longer reaches the skip link, which breaks criterion 6.
   - React documents this as a bug pattern: <https://react.dev/learn/synchronizing-with-effects#how-to-handle-the-effect-firing-twice-in-development>. The repo already tests in StrictMode (`renderApp({ strictMode: true })` in `raiseTelemetry.test.tsx`).
   - The builder lists this as an assumption, but it is a defect.
   - **Fix:** make the check give the same answer on repeat runs. For example, the shell keeps a ref to the first screen's `h1` element. `usePageHeading` stores its own heading there when the ref is empty and skips focus while it is that element. StrictMode's second run sees the same DOM node, and a route change mounts a new `h1`, so focus still moves on a route change. This also keeps today's handling of a first-load redirect such as `/` to `/transactions`. Add a `routing.test.tsx` case for the first Tab with `strictMode: true`.

2. **low**: `frontend/src/features/disputes/history/DisputesScreen.tsx:71-85`.
   - **Issue:** after a failed Load more, `idsBeforeLoadMore` stays set. A later full refetch that brings in a new dispute would then move focus to it and announce "1 more dispute loaded". The same happens when a loaded page holds only unknown statuses.
   - This is rare, because `refetchOnWindowFocus` is false, and `TransactionsScreen` has the same pattern.
   - **Fix:** clear the ref when `fetchNextPage` settles with an error.

3. **low**: criterion 6's third clause ("EXPERIENCE.md … in the same change") is not in the diff because the guard blocked it.
   - The main checkout's working tree already has the skip-link line at `docs/ux/EXPERIENCE.md:189`. It does not mention the new first-load rule: "the first screen of a page load leaves focus alone".
   - **Fix:** the supervisor adds that half-sentence. QA carries the e2e updates the builder listed, in `spa-transactions.spec.ts:113` and around `:287`, and in the `dispute-raise.spec.ts:237-238` comments.

**Nits:**
- `routing.test.tsx`, "leaves focus on the h1 … after a route change": the final check only says the skip link does not have focus. Assert where focus actually is instead (inside `main`).
- `DisputeRow.tsx:25` widens `reasonCopy` with `as Partial<typeof reasonCopy>`. This is a safe widening, not an escape. An `Object.hasOwn(reasonCopy, dispute.reason)` check would avoid the cast.

2. **low, `idsBeforeLoadMore` left set after a failed or row-less Load more: closed.**
   - `DisputesScreen.tsx` clears the IDs in two places:
     - line 87, after an `await` on `fetchNextPage` that settles with `isError`;
     - line 76, in the effect, once the page has settled, whether or not a row was shown.
   - The effect skips while `isFetchingNextPage` is true (line 75).
   - The `describe.each` test (`DisputesScreen.test.tsx` lines 286-325) covers both cases, and the builder broke each case and saw its test fail.
   - Can a genuine Load more lose its focus or announcement? I checked this against the installed `@tanstack/query-core` 5.105.0 source:
     - **A re-render before the request starts.** `announce` gets a new identity on every `LiveRegionProvider` render, so an unrelated re-render could run the effect. That needs `isFetchingNextPage` to read false while the IDs are set and the request has not started. It cannot happen:
       - `fetchNextPage()` dispatches `type: 'fetch'` synchronously (`query.ts:825-835`).
       - `useBaseQuery` computes the result on every render with `observer.getOptimisticResult`.
       - So any render after the click reads `isFetchingNextPage` true, even though the listener notification waits for `setTimeout(0)` (`notifyManager.ts`).
       - `loadMore` sets the IDs and calls `fetchNextPage` in the same synchronous step, so no render can fall between them.
     - **Success.** One `success` dispatch sets the new data and `fetchStatus: 'idle'` together. The effect therefore sees the new rows in the same render in which `isFetchingNextPage` turns false, then focuses the first new row and announces.
     - **A stale clear on error.** The error clear runs in a microtask after the `await`. The button only becomes pressable again after the deferred notification renders, which is later. So a second Load more cannot start before the first one's clear has run.
     - **Retry after a failure.** The IDs were cleared, the second press sets them again, and the success path then runs as normal. There is no test for retry followed by success. The logic is direct, so I list it only as an optional nit.
