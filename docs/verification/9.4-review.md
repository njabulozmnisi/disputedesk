## Findings

### High

**H1. A backslash-newline line continuation bypasses the force-push deny, the subagent's `gh` writes and the agent push deny.** `.claude/hooks/guard.py:49, 58, 71, 84`

Every Bash pattern stops at `\n` (`[^;&|\n]`). Bash, however, removes a `\`-newline pair before it splits words (bash manual, *Escape Character*: the pair "is treated as a line continuation (that is, it is removed from the input stream and effectively ignored)").

- **Main session.** `git push \`, newline, `  --force …` gets no decision, and git forced the update (A6, A7). This breaks criterion 4's "every other command … is denied to the main session".
- **Subagent.** A multi-line `gh api -X PUT …/rulesets/1 --input main.json` gets no decision (B4). So does `gh pr \`, newline, `merge` (B5). This breaks criterion 5. Multi-line `gh api` is the usual way to write these ruleset and settings calls, so the gap is in a form agents actually write, not an exotic one. It is also exactly the threat the story's Notes name: an agent that changes the ruleset.
- **Agent push deny.** The unchanged agent push deny is bypassed the same way (F1).

Fix (rule diff, re-approved): in `check_bash`, match against the command with each `\`-newline pair removed, as bash removes it: `command.replace("\\\n", "")`. Keep `re.fullmatch(STACKED_FORCE_PUSH, …)` on that same text. Add A6, A7, B4, B5 and F1 to `guard.test.sh`.

### Medium

**M1. `FORCE_ARGUMENT` misses force forms git accepts, one of them the short-option cluster criterion 4 names.** `.claude/hooks/guard.py:50`

- `(^|\s)-[A-Za-z]*f` does not match `-4f` or `-6f` (`-4` is `--ipv4`), and git forced the update (A1, A2).
- git's parse-options accepts any unambiguous long-option prefix. `--mirr` mirrored the remote (A3). `--forc` is rejected as ambiguous, and `--force-w` is already caught by `--force`.
- `\+feature/9.4` and `""+feature/9.4` reach git as `+feature/9.4`, and git forced the update (A4, A5).

Only the main session is exposed, since a subagent is denied every push, and the ruleset still refuses a force push to `main`. Still, criterion 4's "short-option cluster containing f" is not met.

Fix:
- `-[A-Za-z0-9]*f` for clusters;
- `--mi` as a prefix (`--mirror` is git push's only long option starting `--mi`, git-push(1));
- `[\\'\"]*\+` for the refspec;
- one test case per form.

**M2. `gh api` reads only the first `-X`, and only a `-X` standing alone.** `.claude/hooks/guard.py:85, 143`

- `gh api -X GET -X DELETE repos/o/r/rulesets/1` sends `DELETE` (gh 2.97.0, `GH_DEBUG=api`: pflag keeps the last value), and it gets no decision for a subagent (B3).
- `gh api -iXPOST …` sends `POST` (a shorthand cluster) and gets no decision either (B6).

Criterion 5's Inputs say a subagent is denied "a method named by `-X` or `--method` … other than `GET`".

Fix: write is true when any `-X`/`--method` value found is not `GET` (`re.finditer`, not the first `re.search`), with `-[A-Za-z]*X` accepted for a cluster. Add B3 and B6 as cases.

**M3. A subagent's closed `gh` list misses options before the group.** `.claude/hooks/guard.py:58`

`gh_command` requires the group straight after `gh`. Yet `gh -R <owner>/<repo> pr merge 5 --squash` and `gh --repo … pr create …` both run: gh 2.97.0 resolves the subcommand past them, while an unknown flag in the same place is rejected. Both get no decision for a subagent (B1, B2).

Inputs names options "between" the group and its subcommand, but the closed list exists to deny these commands whatever the option order. `-R` is the option the story itself cites.

Fix: allow options between `gh` and the group, `\bgh\s([^;&|\n]*\s)?{group}\s([^;&|\n]*\s)?({subcommands})(?![\w-])`. This fails closed on a read that names a group word. Add B1 and B2 as cases.

**M4. The `DEPLOY_ENABLED` ask is exact-case and CLI-only.** `.claude/hooks/guard.py:67`

Under the human decision of 2026-11-05 (criterion 5's And, Notes), setting or deleting the variable asks the main session, because it switches deploy on merge. Two forms that change the same variable get no decision:

- `gh variable set deploy_enabled --body true` (C1). GitHub's naming rules for configuration variables make names case-insensitive; from the docs, not verified live.
- `gh api -X PATCH repos/<o>/<r>/actions/variables/DEPLOY_ENABLED -f value=true` (C2).

The deploy ask already covers the API form of a dispatch (`/actions/workflows/…deploy…/dispatches`), so the variable's ask is inconsistent with it.

Fix:
- `(?i:DEPLOY_ENABLED)` in the `gh variable` pattern;
- an ask on `/actions/variables` with `(?i:DEPLOY_ENABLED)`, or on any `/actions/variables` write;
- C1 and C2 as cases.

### Low

**L1.** The regexes ignore shell quoting and indirection. `.claude/hooks/guard.py:49, 84`
- A `;` inside a quoted value ends the scan. `git -c user.name='a;b' push --force …` is none/none (A8, A9).
- A force or mirror set through `-c` config or an inline alias is not seen (A10 to A12).
- `-X GET` inside a quoted field value hides a write (B7).
- A variable or a script written under an agent's own paths (`scripts/`) and then run hides any command.

These forms are not ones an agent would write by mistake. They sit with the Notes' accepted limit of a single-maintainer guard. If the guard ever has to resist a hostile agent, the standard tool is POSIX shell tokenising (Python's `shlex`); put that in `docs/production-path.md` rather than here.

**L2.** `gh workflow run <numeric workflow id>` gets no ask in the main session (C3). `gh run rerun <id>` of a `main` run, which re-runs `publish` and the deploy job, is neither asked nor denied to a subagent (C4). `.claude/hooks/guard.py:65`. Both predate this story. Criterion 5 keeps today's deploy ask, and `gh run` is outside the closed list. Candidate for the epic's lows.

**L3.** The main session is denied a commit message or pull request body that names a force form. `git commit -m "… push with --force …"` and `gh pr create … --body "… git push --force …"` are deny/deny (E1, E2), because the text reads as push arguments. This fails closed, and the same was true before. Relevant to criterion 8: 9.4's own pull request body will likely describe the guard. The supervisor should use `--body-file` and `git commit -F`.

**L4.** Subagent false positives that fail closed:

- a graphql read with `-f` (D2), which is consistent with Inputs (`-f` without `-X GET` is a write);
- `git merge-base …` (E7), from the unchanged agent deny's `merge\b`.

**L5.** Story text that Sofia should update:
- The story's Supervisor checks list `gh variable set DEPLOY_ENABLED --body true` under no decision/denied. Criterion 5 and the human decision make it ask/denied. The builder followed the decision and recorded the conflict.
- Criterion 7 and Build facts' Touches name six rule files, but the approved patch also changes `.claude/skills/build-story/SKILL.md` and `.claude/skills/verify-story/SKILL.md` (break and run-breaks wording outside 9.4's scope, accurate against `scripts/run-breaks.sh`). ### Attack on the delta

I ran 54 cases (`rev-cases/delta-cases.jsonl`) on v2 and on v1. I confirmed real behaviour with gh 2.97.0, from an empty directory against an unreachable host with `GH_DEBUG=api` (`rev-cases/real-gh.sh`).

What holds:
- **The stacked exact match on the un-normalised text.** After the join, any quote or backslash left in the text fails the match. The characters the match allows are all ones bash passes on unchanged, so a full match is exactly what bash runs.
  - J4 (`\\`, then a newline and a second command) gets deny/deny.
  - J7 (a trailing continuation) gets none/deny, and bash runs the same words.
  - J6 (a backslash-newline inside single quotes, which bash keeps) gets deny/deny. v1 got none/deny there.
  - J5 (the stacked form split over two lines with indentation) fails closed, deny/deny. The supervisor writes the form on one line.
- **The positional gh parsing.** It follows cobra's subcommand lookup (`stripFlags`): an option without `=` takes the next word unless it is boolean, and gh's root and groups have no boolean flags except help. The guard gives no decision to `gh -- pr merge` or `gh pr -- merge` (P1, P2), but gh refuses both as unknown commands, so they are not gaps.
- **The any-non-GET rule.**
  - `-X GET … --method PUT` is denied (M6). v1 missed it.
  - `-qX` fails closed (M5).
  - The reads M1, P8 and P9 get none/none.
- **The case-insensitive `DEPLOY_ENABLED`.** It holds in both the CLI and the API form. An environment-level variable (M4) cannot flip deploy, because `ci.yml`'s `deploy` caller job (line 470) has no environment, so it needs no ask.
- **The main session's flow.** Every step of criteria 2 and 3 and of the scratch chain (P3 to P17) gets no decision in the main session. The subagent denies hold.

### Findings

#### High

- **R3-H1. Text fed to a shell is not read** (`.claude/hooks/guard.py:199-207`, `SHELL_RUNNERS` at line 73). The verifier found it in round 3, and I reproduced it.

#### Medium

- **R3-M1. The program and its subcommand are found too narrowly** (`.claude/hooks/guard.py:170-176` `program`, `:211-219` `git_subcommand`, `:164-167` `is_separator`). Each cause below is a regression from v3:
  - **The first word named `git` or `gh` is taken as the program**, so a wrapper's option value with that name hides the real call. `env -u gh git push --force …` reads as a gh call, and `env -u git gh pr merge 5` as a git call (E1 to E4, E9).

    - read every word named git or gh as a possible program (fail closed);
    - add `--attr-source` to `GIT_VALUE_OPTIONS`;
