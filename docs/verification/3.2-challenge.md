VERDICT: RETHINK

### 1. Pre-mortem
- A 201 dispute, its stored event and its outbox row commit, but storing the completed key fails afterward. A retry then gets `already-disputed` rather than the original 201. This is possible with the current [`RaiseDisputeHandler`](backend/src/DisputeDesk.Application/Disputes/RaiseDispute/RaiseDisputeHandler.cs), which calls `SaveChangesAsync` before returning a response to an endpoint filter.
- A timed-out request continues working, or cancellation prevents key cleanup. The architecture assumes the 30-second timeout makes takeover safe, but [ASP.NET Core request timeouts](https://learn.microsoft.com/en-us/aspnet/core/performance/timeouts?view=aspnetcore-10.0) cancel `RequestAborted`; they do not stop execution automatically.
- A failed unique-index save leaves tracked rows that a later save attempts to insert again. [`AppDbContext`](backend/src/DisputeDesk.Infrastructure/Persistence/AppDbContext.cs) currently detaches `Added` rows, while the story leaves its effect on the tracked key and any `Modified` rows undecided.

### 2. Simplest design
Keep the per-customer unique key row, lease and 24-hour expiry. Parse the structured header, fingerprint the validated request, and atomically claim or take over the row. For a successful raise, **prepare the exact 201 response before the commit**, then save the dispute, its stored event and outbox row and the completed key in one EF Core transaction; a lost-lease update must abort that transaction. Store specified 4xx responses under the lease separately, and release failures under the lease.

The story needs a concrete change to the handler’s commit boundary; an endpoint filter cannot make its current, already-completed save atomic merely by attaching a key row afterward. Avoid a general-purpose idempotency framework or a new interface. Resolve the recovery choice before building: keep the current targeted detach only if tests prove the subsequent 409 save is safe, or use a fresh context for that save rather than clearing unrelated tracked changes.

### 3. Assumptions
- **“30 seconds means no live takeover” is unproved.** Timeout cancellation is cooperative, and [`Program.cs`](backend/src/DisputeDesk.Api/Program.cs) does not yet register or run request-timeout middleware. Database work and cleanup must also have explicit cancellation behavior.
- **“Canonical validated request” has one meaning.** Neither [AD-16](docs/architecture/architecture.md) nor the story specifies whether JSON property order, ignored extra properties, or equivalent representations of `note` and `expectedAmount` produce the same fingerprint. The request model currently accepts unmapped JSON properties.
- **A 5xx always means nothing committed.** That does not follow if an exception occurs after the handler’s save. Releasing such a key would turn a retry into a different response.

### 4. Standards
- Use the documented [`AddRequestTimeouts` / `UseRequestTimeouts` / `WithRequestTimeout` mechanism](https://learn.microsoft.com/en-us/aspnet/core/performance/timeouts?view=aspnetcore-10.0), and pass `RequestAborted` through work that must stop. `WithRequestTimeout` alone does not establish a deadline; an unhandled timeout defaults to **504**, not the story’s 503 release example.
- Use [EF Core transactions](https://learn.microsoft.com/en-us/ef/core/saving/transactions) for the all-or-nothing success write. A lease-qualified [`ExecuteUpdateAsync` affected-row check](https://learn.microsoft.com/en-us/ef/core/saving/execute-insert-update-delete#concurrency-control-and-rows-affected) is documented, but must be in that same transaction; it does not join `SaveChanges` automatically. The key’s quoted header syntax and 400/409/422 distinction should remain tied to the [Idempotency-Key draft](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/) and [RFC 9651](https://www.rfc-editor.org/rfc/rfc9651).

### 5. Gaps
- Specify the fingerprint’s fields and normalization, whether the 255-character bound applies to the **decoded** string, and how duplicate headers, escaped characters and non-ASCII input are handled.
- Specify the exact replayed body, including whether a stored ProblemDetails `traceId` is the original request’s; test byte-equivalent status, body and `Location` rather than only status and row counts.
- Test a forced failure **between the dispute save and key completion**, cancellation at the timeout, and a takeover racing a late completion. These distinguish atomicity from ordinary sequential replay.
- Clarify whether deterministic 400 responses after body validation, notably the expected-amount rule, are stored. Criterion 4 names only 404, 409 and 422; the existing handler can return that 400 after reading the transaction.
- Decide the tracked-row recovery question in the story’s Notes. It is an explicit open decision, so the story does not yet meet `AGENTS.md`’s definition of ready.

## Human decision (2026-10-28)

AD-16 stands; the RETHINK points are taken as clarifications, recorded in the story Notes and in AD-16: built-in request timeouts (504 is released), `LeaseId` as an EF Core concurrency token on the one save, `ChangeTracker.Clear()` plus lease-conditional `ExecuteUpdateAsync`/`ExecuteDeleteAsync` for the 4xx store and 5xx release, every handler 4xx stored, and a fingerprint over the re-serialized validated request with a byte-for-byte replay.
