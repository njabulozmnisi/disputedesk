VERDICT: SIMPLIFY

## Pre-mortem
- [story] A customer retries a timed-out submit with a changed body under the same key and receives `idempotency-mismatch`. The backend hashes the validated request, so the draft must be frozen for every retry.
- [story] The five `idempotency-in-progress` retries finish without a result, but criterion 2 says to keep the spinner and never says what happens next. That can leave the customer unable to tell whether a dispute was submitted.
- [story] Browser instrumentation records a transaction ID in a URL attribute, or the two named spans export without enough correlation to measure time from opening the screen to the 201 response.

## Simplest design
- [story] Keep the form and draft in memory across the two routes. Build one immutable request from the transaction row and validated fields; mint a quoted UUID key on entering review, and reuse that request and key for every submit retry. Changing the form starts a new draft.
- [story] Use the generated mutation, existing mutator, problem-type helper, and query keys. Add the required Form and `RadioGroup`; do not add a second HTTP client, persistence layer, or generic retry framework. Use standard OpenTelemetry web instrumentation for `/api` propagation and two explicit raise spans.

## Assumptions
- [story] The form can obtain `accountRef` as well as `transactionId`: the current `RaiseDisputeRequest` requires both, although criterion 1 does not say where the form gets the account reference.
- [story] Losing a draft on reload is acceptable: EXPERIENCE.md explicitly keeps values in memory, not storage. It does not, however, specify what a reload after an uncertain submission should tell the customer.
- [story] A badge replaces the already-disputed hint: EXPERIENCE.md’s copy deck says the badge **is** the treatment, while criterion 8 also asks for “alreadyDisputed reason text.” Choose one; the existing hint deliberately returns no text for that reason.

## Standards
- [story] No invented mechanism is required. Keep the key as the [Idempotency-Key draft](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/) specifies—an [RFC 9651](https://www.rfc-editor.org/rfc/rfc9651) Structured Field String—and use [W3C Trace Context](https://www.w3.org/TR/trace-context/) through OpenTelemetry instrumentation rather than a hand-written `traceparent` injector. Specify URL-attribute sanitisation because the raise route contains a transaction ID.

## Gaps
- [story] Criterion 2 needs a terminal state after the fifth in-progress response, including whether Retry remains available with the same request and key.
- [story] Criteria 1 and 6 need explicit tests for `expectedAmount` as a decimal **string** (0.00 permitted, fewer than the transaction amount, no more than two decimals), clearing it when the reason changes, and routing backend field errors from review back to the corresponding form fields. Binding failures without named `errors` need the form-level error described in the story notes.
- [story] Criterion 3 omits the raise route’s 404 and 504 responses, and does not say whether a 409 `already-disputed` or 422 `not-disputable` refreshes the transaction row as EXPERIENCE.md requires.
- [story] Criterion 5 names spans but not the observable evidence for SM-1 and SM-2: define how one screen open is counted, how its timestamp is correlated with the eventual 201, and how the exported attributes are checked for transaction IDs and other personal data.

## Resolution

Sofia, 2026-10-30. Every point is `[story]` and is folded into the stories; 3.6 is split into 3.6 (raise and review screens), 3.10 (row badges) and 3.11 (browser spans).

- Frozen draft and mismatch: 3.6 criterion 5 (one immutable request and key per draft; equal request keeps the key, a changed one gets a new key).
- No terminal state after five in-progress resends: 3.6 criterion 6 ("We couldn't confirm…" with Try again, same request and key).
- URL attribute and SM-1/SM-2 correlation: 3.11 criteria 1, 3 and 4 (fetch instrumentation only, open recorded once from the parent route's `onEnter`, submit span linked to the open span, query stripped, in-memory exporter test).
- Simplest design (memory-only draft, generated mutation, no second client): 3.6 criteria 5 and 6, Boundaries.
- `accountRef` source: 3.6 criterion 1 and criterion 5 (from the cached row); reload loses the draft and redirects (criterion 1).
- Badge versus `alreadyDisputed` text: the badge alone (3.10 criterion 2).
- Standards: RFC 9651 key and W3C Trace Context through OpenTelemetry instrumentation (3.6 criterion 5, 3.11 criterion 1).
- Gaps: `expectedAmount` as a decimal string with boundary tests (3.6 criterion 2), clearing on reason change (criterion 2), 400 errors back to 4a and the form-level binding error (criterion 4), 404 and 504 and the refetch after 409 and 422 (criteria 6 and 8), SM evidence (3.11 criterion 3).
