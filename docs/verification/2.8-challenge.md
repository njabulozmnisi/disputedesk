## Pre-mortem
- [story] Sign-in audit rows say `Succeeded` although no session was established: `OnTicketReceived` precedes the cookie handler’s session write. Test a failed session-store write, or define `Succeeded` as “OIDC ticket accepted,” not “browser signed in.”
- [story] Sign-out loses its `id_token_hint` after the cookie session is deleted. The current endpoint reads the token before deletion; the replacement must preserve it for the OIDC handler and test the actual end-session redirect.
- [story] A failed audit save or identity-provider redirect leaves sign-out only partly complete. Specify which failures block cookie deletion and which cannot be made atomic with the provider.

## Simplest design
- [story] Add one Application `Audit.Record` method that adds the existing row using a caller-supplied instant; use it at the OIDC ticket event and before local session deletion. Use the built-in OIDC sign-out handler with its signed-out callback, set the authenticated fallback policy, and mark only genuinely public mapped endpoints anonymous. Keep the existing antiforgery filter. No custom end-session URL builder, new schema, audit interface, or extra endpoint is needed.

## Assumptions
- [story] “Every sign-in” means successful code-flow tickets, not failed callbacks: the proposed hook is `OnTicketReceived`, while failures currently go through `OnRemoteFailure`.
- [story] A linked customer is resolved at sign-in by querying `CustomerLinks`; the ticket does not contain a customer ID (AD-10). Test both linked and unlinked logins, including the actor ID.
- [story] OIDC sign-out will retain the ID token after cookie sign-out. That does not follow from the proposed sequence; make the token handoff explicit and assert it in the test.
- [story] Production and Development have the same mapped endpoints. `Program.cs` currently maps OpenAPI and Scalar only in Development, so enumerate and assert each environment separately.

## Standards
- [story] The current hand-built end-session query in `BffEndpoints` is the mechanism to **replace**, not reuse. Use ASP.NET Core’s [OIDC handler for sign-out and callback routing](https://learn.microsoft.com/aspnet/core/security/authentication/configure-oidc-web-authentication) and check its emitted parameters against [RP-Initiated Logout 1.0](https://openid.net/specs/openid-connect-rpinitiated-1_0.html). The fallback policy and public-endpoint opt-outs are likewise [documented ASP.NET Core behavior](https://learn.microsoft.com/aspnet/core/security/authorization/policies#default-and-fallback-policies).
- [story] Endpoint enumeration is a project-specific *test*, not a replacement authorization mechanism. Keep the framework fallback policy as the enforcement.

## Gaps
- [story] Resolve the stated unknown-route question before building: fallback authorization makes an anonymous unmatched route 401, while existing `ProblemDetailsTests` and `SecurityHeadersTests` expect 404. Assert anonymous 401 and authenticated 404, including the appropriate problem shape and headers.
- [story] Criterion 3 does not say how the retained ID token reaches the OIDC handler after cookie sign-out, or what happens when audit persistence, session deletion, or provider discovery fails. Add observable expectations without promising atomicity across the database and identity provider.
- [story] Criterion 2’s “no token, access token or email in any log line” needs a bounded capture assertion for the callback and failure paths. In particular, the existing `OnRemoteFailure` logs `Failure.Message`; the criterion does not establish that this message is safe.
- [story] Criterion 4 mixes “every endpoint names a policy” with a deliberately unannotated test endpoint. Specify that enumeration covers production mappings in both environments and the fallback probe is isolated. Assert explicit metadata and an anonymous 401 separately; either check alone misses a regression.
