# Pre-build security read: 5.5

Security (pre-build), base `8134305`, with the working-tree story and `architecture.md`. No high; one `[decision]` (S2).

To check Scalar.AspNetCore 2.18.3's actual behaviour, a throwaway host in the scratchpad served `/scalar/` with the story's options, and its `scalar.js` bundle was read. The scratchpad host was `/private/tmp/claude-501/-Users-njabulomnisi-Projects-Dojo-DisputeDesk/77858989-3f5b-4d04-8184-f4d922dc16d1/scratchpad/scalarprobe`.

Already covered:
- The inline script's configuration holds no credential unless one is configured.
- `DisableTelemetry()` renders `"telemetry":false`.
- With no `WithProxyUrl`, the reference layout sends requests directly and uses no proxy. Scalar's `proxy.scalar.com` default applies only to its `web` layout.
- Persistent authentication defaults to off (`"persistAuth":false`). The auth store writes to `localStorage` only when it is on.
- The bundle has no `eval` or `new Function`, so `script-src` needs no `'unsafe-eval'`.
- The request path is percent-encoded into the inline script (`'%2Fscalar%2F'`), so the path cannot inject into it. The query string does not change the script.
- The switch fails closed. It is `false` in `appsettings.json`, gives 401 or 404 when off, and nginx then only forwards to the Api.
- Scalar's place on the customer origin was accepted in 5.1 S3. A separate viewer origin is a production-path line in 7.6.

| # | Sev | Finding |
|---|---|---|
| S1 | medium | [story] **Agent Scalar is on by default on local hosts.** Add `DisableAgent()` and `DisableMcp()` to criterion 2's options. Scalar 2.18.3 turns the agent (AI chat) on when it is not disabled and either the page's host is local (`localhost`, `127.0.0.1` and similar, so the Compose stack qualifies) or a key is set. The agent keeps its own workspace with `persistAuth: true` and defaults to `https://proxy.scalar.com`. This breaks criterion 2's "token in page memory only, never in `localStorage`", because that relies on `persistAuth` being false. The agent would also send the operations document and its requests to a third party. `connect-src 'self'` blocks the traffic, but the supervisor check expects no CSP violations, and the only thing stopping the data leaving is the CSP itself. The test asserts that the served configuration holds `"agent":{"disabled":true}` and `"mcp":{"disabled":true}` (both seen in the probe). Sources: Scalar.AspNetCore XML docs (`DisableAgent`, `DisableMcp`); ASVS 5.0 V14.2 (sensitive data not sent to third parties). |
| S2 | low | [decision] **The declared `clientCredentials` scheme invites typing a client secret into the browser.** Scalar 2.18.3 shows Client ID and Client Secret fields for it, and its Authorize button posts `grant_type=client_credentials` with the secret from the page to `tokenUrl`. `connect-src 'self'` blocks that post, because the token URL is on the identity origin. So the secret cannot leave and no token comes back, but the page still asks for a secret on the customer origin. That works against the 2026-10-30 decision's intent (RFC 6749 §2.1, §10.1: a secret in a user agent is not confidential), and a click produces the CSP violation the supervisor check rules out. Recommended: the document declares only `bearer`. Real tools find the token endpoint through OIDC discovery and the README (7.7). This also drops the runtime `tokenUrl` transformer and the build-time stand-in issuer. Alternative: keep the scheme as decided and apply S3. |
| S3 | low | [story] **Make bearer the scheme Scalar shows first.** If `clientCredentials` stays, list `bearer` first in each operations security requirement and set Scalar's preferred scheme to `bearer` (`AddPreferredSecuritySchemes`; the builder checks the rendered key). That way the paste field is what an operator sees first. This option changes the inline script, so it goes into the one fixed hash. |
| S4 | low | [story] **The fixed hash matches only the `/scalar/` page.** The inline script embeds the request path: `/scalar/` renders `'%2Fscalar%2F'` and `/scalar/v1` (Scalar's `{documentName}` route) renders `'%2Fscalar%2Fv1'`. Each path therefore has a different hash, and `/scalar/v1` loads blank under the CSP, which fails closed. State in the story that `/scalar/` is the one supported URL. The hash test requests exactly `/scalar/`, and nginx forwards the path unchanged, with no rewrite and no PathBase or `X-Forwarded-Prefix` (CSP Level 3 hash-source). |
| S5 | low | [story] **Say which headers a 429 on the Scalar locations gets.** The server-level `error_page 429 @rate_limited` applies inside the new locations, and `@rate_limited` sends the SPA's CSP. That policy is stricter (no hash) and right for a JSON body. Add to the story that a 429 on the Scalar locations is the unchanged `@rate_limited` response, with each header once. The Scalar CSP is not added to it, and no second named location is created. If `infra/smoke.sh` checks a 429, it checks one on `/scalar/` too (OWASP HTTP Headers Cheat Sheet; RFC 6585). |
| S6 | low | [story] **What criterion 4's style rule should say.** Scalar 2.18.3 adds its whole stylesheet while the page runs, as `<style id="scalar-style">`. Its content is fixed per version, and Scalar can take a nonce for it from `<meta property="csp-nonce">`, which AD-23 rules out. CodeMirror uses constructable stylesheets, which `style-src` does not govern. CSP Level 3 hashes do cover a `<style>` element added by script, so being added at runtime does not by itself require `'unsafe-inline'`. A test cannot hash that stylesheet, though, without pulling it out of `scalar.js`. `'unsafe-inline'` on `style-src`, for the Scalar locations only, is the simplest option to explain and is acceptable. `img-src`, `font-src` and `connect-src` stay `'self'`, which closes the usual ways injected CSS sends data out, and `script-src` stays hash-only. State two things in the story: `style-src` never holds both a hash and `'unsafe-inline'` (CSP ignores `'unsafe-inline'` when a hash is present, so the page would lose its styles), and the hash test also asserts that `script-src` holds no `'unsafe-inline'`. |
| S7 | low | [story] **Prove the token stays out of `localStorage`.** Criterion 2's "never in `localStorage`" can only be proved in a browser. The integration test asserts that the served configuration holds `"persistAuth":false`. The supervisor check adds a step: after pasting the token and sending a request, `localStorage` holds no value containing the token. |
| S8 | low | [story] **Keep the anonymous runtime document free of configured values.** When the switch is on, anyone can fetch `/openapi/v1.json`. Criterion 2's "no configured value" covers only the page. Extend it so the runtime document holds the issuer only inside `tokenUrl`, and holds no `Operations:Actors` sub, no `Zitadel:ProjectId` and no client ID. `scopes` is `{}`, with no Zitadel project-audience scope that embeds the project ID (OpenAPI 3.1 OAuth Flow Object; ASVS 5.0 V13.4). |
| S9 | low | [story] **Gateway scope and what a script on `/scalar/` can reach.** Use an exact `location = /openapi/v1.json`, not an `/openapi/` prefix, so the gateway forwards only the one document. On the reach: a script running on `/scalar/` can do everything the customer SPA can with the session cookie, since it can fetch the antiforgery token. In an operator's browser it can also read the pasted bearer token from that page's memory. Any other same-origin page could read it too, by opening `/scalar/` and reading its DOM. The controls are the hash-only `script-src`, the Scalar bundle served from `'self'` and pinned in the NuGet package (2.18.3), and a document generated by the server with no user content rendered as HTML. Add a Notes line: a `Scalar.AspNetCore` upgrade reruns the security stage as well as the hash test. |

## Resolution

Sofia, 2026-10-30. Story 5.5 is refined to six criteria. The human settled S2 and the style rule on 2026-10-30: the document declares only the `bearer` scheme (decision 1), and `style-src 'self' 'unsafe-inline'` holds on the Scalar locations only, never with a style hash (decision 2); AD-26 records both.

- S1, Agent Scalar and MCP: criterion 2 adds `DisableAgent()` and `DisableMcp()`, and its test asserts `agent.disabled` and `mcp.disabled` true.
- S2, the `clientCredentials` scheme: settled by decision 1. The document declares only `bearer`; the runtime `tokenUrl` transformer and the build-time stand-in issuer are dropped. Real tools find the token endpoint through OIDC discovery and the README (7.7).
- S3, bearer first and the preferred scheme: dropped by decision 1 (one scheme; criterion 2 sets no preferred scheme).
- S4, the hash matches only `/scalar/`: criterion 6 requests exactly `/scalar/`; criterion 4 forwards the path unchanged with no rewrite, PathBase or `X-Forwarded-Prefix`; a Boundaries line names `/scalar/` the one supported page path.
- S5, headers on a 429: criterion 5 (the unchanged `@rate_limited` response, SPA CSP, each header once, no second named location; `infra/smoke.sh` checks a 429 on `/scalar/`).
- S6, the style rule: criterion 5 and decision 2; criterion 6 asserts `script-src` holds no `'unsafe-inline'` and `style-src` holds no hash.
- S7, the token out of `localStorage`: criterion 2 asserts `persistAuth` absent or false; a supervisor check reads `localStorage` after pasting and sending a request.
- S8, no configured value in the runtime document: criterion 2 extends the check to `/openapi/v1.json` (no issuer at all now, no `Zitadel:ProjectId`, no actor sub, no client ID). The `scopes` part is dropped by decision 1.
- S9, gateway scope and reach: criterion 4 uses an exact `location = /openapi/v1.json`; a Notes line says a `Scalar.AspNetCore` upgrade reruns the security stage as well as the hash test, and names the controls.
