# 8.12 security review (High-stakes: operations authorisation, 2026-11-05)

Patch `8.12.patch` on base `6e0cca6`, built on the M1, read in a throwaway copy (removed afterwards). Production change: `OperationsOptions` becomes `string[] AllowedClients = []` bound from `Operations:AllowedClients`; `OperationsActorHandler` refuses a blank `sub` and then requires an ordinal match; the `Actors` map, `MapsOnlyToOperations` and its start-up validator are deleted; `provision.sh` writes and checks the list; comments in `AuthorizationResultHandler`, `OperationsActorRequirement` and `CurrentOperationsActor`. Pass: no high or medium findings.

## Checked against the pre-build read (epic-8-prebuild-wave3.md, Security read 8.12)

- **Deny by default.** `AllowedClients` defaults to `[]`; a missing section, `{}` and `[]` bind empty (`Options_NoListConfigured_BindAnEmptyList`), and an empty list gives 403 with one role and with every role (`ReadDispute_EmptyList_Returns403ForTheOnceListedSub`). Roles are still required: `RequireRole` still chains `RequireAuthenticatedUser().RequireRole(role).AddRequirements(new OperationsActorRequirement(action))` on the JwtBearer scheme only, so a listed `sub` without the role is still 403. OWASP Authorization Cheat Sheet (deny by default, least privilege); ASVS 5.0 V8.2.1, V8.3.1.
- **Exact ordinal match.** `AllowedClients.Contains(sub, StringComparer.Ordinal)`; a `sub` differing only in case, or by a trailing space, gets 403 (theory, three cases). No trimming or normalising anywhere.
- **Null or blank `sub` refused before the lookup.** `string.IsNullOrWhiteSpace(sub)` returns before the list is read; the test configures the list as `["", " "]` so only that check can refuse, with a token whose `sub` claim is removed (`FakeZitadel.AccessToken` puts `sub` in the `Claims` dictionary, so `Remove("sub")` does drop it), `""` and `" "`.
- **No `Operations` section in any `appsettings*.json`.** Only `appsettings.json` exists and it has none; `AppSettings_HoldNoOperationsSection` globs `appsettings*.json`, so a future `appsettings.Development.json` is covered. No `Operations__*` environment variable in `docker-compose.yml`, `.github/` or the Terraform. `Program.cs` adds the clients file, then environment variables and the command line, so only an operator-set variable could add or overwrite an index (Microsoft Learn, "Configuration in ASP.NET Core", bind an array).
- **Provisioner current check is exact array equality.** `jq -e --arg ops "$OPS_ID" '.Operations.AllowedClients == [$ops]'`, the same `$OPS_ID` the write passes as `$opsUserId`. Re-run here with jq 1.7.1 on nine shapes: only `["<id>"]` is current; the old `Actors` shape, two entries, another ID, `[]`, `["<id> "]`, a scalar string, `{}` and invalid JSON are rewritten. Inside the `if` condition a jq error (exit 5) does not abort under `set -euo pipefail` (checked). The rewrite regenerates both secrets on the existing path; secrets still reach jq over stdin, the file stays 0400 and owned by the app user, and the Api starts only after `provision` completes (`service_completed_successfully`).
- **Old-shape clients file fails closed.** If the Api ever read a file still in the `Actors` shape, `AllowedClients` binds empty (the binder ignores keys with no matching property; `BinderOptions.ErrorOnUnknownConfiguration` defaults to false), so every bearer caller gets 403. In Compose the provisioner rewrites it first; the builder's Docker check proved the rewrite and sign-in plus the operations read afterwards. No test pins the bind of the old shape (L1).
- **Denied entry.** `RecordDeniedAsync` is unchanged apart from its comment: `AuditLog.Record(db, action, AuditResult.Denied, new Actor(ActorType.Operations, sub), time, disputeId)`; the `sub` comes from `HttpContext.User` (JwtBearer principal only); no token, other claims or headers are recorded or logged. `OperationsDeniedAuditTests` unchanged. ASVS 5.0 V16.3.2 (failed authorization logged), V16.2.5 (no sensitive data logged).
- **JwtBearer validation unchanged.** `ConfigureJwtBearer` and `FlattenProjectRoles` untouched: issuer, audience (project ID), lifetime, signature, `RS256` only, `IncludeErrorDetails = false`, project-only role flattening. ASVS 5.0 V9.1.1, V9.2.3.
- **Standards.** Options pattern (Microsoft Learn, "Options pattern in ASP.NET Core"), policy-based authorization with a requirement handler (Microsoft Learn, "Policy-based authorization in ASP.NET Core"), role-based authorization (Microsoft Learn, "Role-based authorization in ASP.NET Core"), allowlist deny by default (OWASP Authorization Cheat Sheet). No home-grown security mechanism: the handler is the framework's documented `AuthorizationHandler<TRequirement>` and the list is a plain options array.
- **Removed start-up validation.** Dropping `ValidateOnStart` removes no protection: every value the old validator refused now has no meaning, and any malformed list (blank entries, a scalar, unknown keys) can only refuse callers. Matches the story's Boundaries.

## Observations (not findings)

- A token without a `sub` is refused and its `Denied` entry records actor ID `""`; this is unchanged behaviour (`RecordDeniedAsync`, documented in its comment), not introduced by this story.
- `e2e/tests/operations-read.spec.ts:65` still reads `.Operations.Actors[operationsSub]`; after this change it throws rather than passes, so it cannot hide a regression. It is QA's change (criterion 5).
- `OperationsEndpoints.cs` XML comments, emitted into `openapi.json`, still say "a mapped token sub"; a wording drift in the published contract, left by the story's no-openapi-change boundary. For the reviewer.
- The provisioner platform tests remain text assertions (the file's existing approach); the exact-equality behaviour is proved by the hand runs above and the builder's Docker check, not by a test that executes jq.
