## Pre-mortem

- [story] A refused raise is audited more than once after a failed or repeated request. The handler’s audit save and the existing idempotency filter’s storage of a 4xx are separate writes; criterion 9 needs a test for a failure between them, not only a completed-key replay.

The handler uses the ownership-filtered replay loader, validates the trimmed note after a successful load, saves once, and on a named version-index violation reloads and decides once more. Return the existing `CustomerView` mapping; the timeline and outbox mappings already recognize `DisputeWithdrawn`. No new state machine, repository, event mapper or response shape is needed.

## Assumptions
- [story] The optional note belongs on the withdrawal timeline item, not in `DisputeResponse.Note`: `CustomerView` currently maps that top-level field from the original raise and maps a withdrawal note only into its timeline entry. State this expectation in criterion 1.
- [story] `withdraw_age` means seconds from `Dispute.CreatedAtUtc` to the successful withdrawal’s event instant, and `disputedesk.dispute_actions` counts successful actions only. Criterion 8 does not say either; both affect test assertions and dashboards.
- [story] A valid GUID identifies the resource even when the JSON body is invalid. The documented 404-before-400 order can cover a well-formed body with an overlong note, but binding failures may return 400 before the handler loads anything. Bound that promise to cases the endpoint can actually bind.

## Standards
- [story] Criterion 6 cites EF Core’s concurrency-conflict guidance as though this save raised `DbUpdateConcurrencyException`. This code maps PostgreSQL’s named unique-index failure from `DbUpdateException` to `UniqueViolationException`; specify that path and use versioned-stream optimistic concurrency, without adding an EF row token. [EF Core concurrency](https://learn.microsoft.com/en-us/ef/core/saving/concurrency); [event sourcing](https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing).
- [story] The logging note leaves a choice between suppressing expected conflicts and merely documenting error-rate noise. Specify which *identified EF Core event IDs* may be filtered and test that unrelated save failures remain visible; do not suppress every `DbUpdateException`. [EF Core logging filters](https://learn.microsoft.com/en-us/ef/core/logging-events-diagnostics/simple-logging#filtering).

## Gaps
- [decision] Resolve AD-15’s second-clash promise: a change that causes the second clash can make the single reloaded status stale. Either permit another read solely to report the latest status, or change the architecture’s “current status” guarantee to the last observed status.
- [story] Specify the withdraw request shape and bounds beyond note length: whether an omitted body, `null` note, unknown properties, malformed GUID and empty GUID are accepted or rejected, and their error precedence. Add tests for 500 versus 501 UTF-16 code units **after trimming**, including whitespace-only notes.
- [story] Criterion 9 should assert that a refused withdrawal of another customer’s dispute records no `DisputeId`, whereas an owned closed dispute does. Criterion 8 should assert metric values and tags, not just instrument existence.
