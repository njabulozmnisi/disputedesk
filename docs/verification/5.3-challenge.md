## Pre-mortem

- [story] **The Worker claims disputes but changes none.** `AppDbContext` has a customer ownership filter, and the Worker has no current customer. The existing `DisputeReplay.LoadDisputeAsync` therefore cannot load a claimed stream without an explicit, narrowly scoped filter bypass.
- [story] **A batch fails or produces duplicate work.** A claim lock must remain held through replay and commit; a version clash must roll back and re-evaluate the latest stream. The story tests two sweeps but does not test either failure path.
- [story] **Catch-up makes the Worker appear hung.** Repeated 50-dispute batches can keep a loop busy beyond the 90-second sweep-heartbeat threshold unless the heartbeat is refreshed during catch-up.

## Simplest design

- [story] Use one hosted service with the existing `TimeProvider`: claim up to 50 **IDs** with parameterised PostgreSQL `FOR UPDATE SKIP LOCKED`, replay their streams with a scoped ownership-filter bypass, invoke `Escalate` or `RecordSlaWarning`, and save through the existing commit path before releasing the transaction. Process overdue claims first, then warning claims; repeat batches for catch-up. Claiming tracked `Dispute` rows and attaching separately replayed instances would introduce an EF tracking conflict. No second scheduler, leader election, repository layer, publish path, or concurrency token is needed.

## Assumptions

- [story] **Warning lead time is undecided.** The story explicitly calls it an open human decision, while criterion 5 depends on “within the lead time.” Record a positive, testable value below seven days before building; the seeded open disputes are specified to remain more than seven days from due.
- [story] **A short claim batch means catch-up is complete.** With `SKIP LOCKED`, another Worker can temporarily hold eligible rows, so a short batch means only that no more rows were claimable *then*. The next scheduled sweep must still pick them up.
- [story] **Every batch fits the heartbeat window.** Neither the story nor AD-18 bounds replay-and-save duration for 50 disputes; the 90-second health threshold does not establish that bound.

## Standards

- [story] No new scheduling or locking mechanism is warranted. Use [.NET `PeriodicTimer` with `TimeProvider`](https://learn.microsoft.com/en-us/dotnet/api/system.threading.periodictimer.-ctor#system-threading-periodictimer-ctor(system-timespan-system-timeprovider)), [EF Core transactions](https://learn.microsoft.com/en-us/ef/core/saving/transactions) and [named query-filter bypass](https://learn.microsoft.com/en-us/ef/core/querying/filters#using-multiple-query-filters), plus PostgreSQL [`FOR UPDATE SKIP LOCKED`](https://www.postgresql.org/docs/current/sql-select.html#SQL-FOR-UPDATE-SHARE). The heartbeat file is already an explicit AD-25 decision; do not invent another health protocol.

## Gaps

- [story] Criterion 2 needs a concurrent-claim test that holds overlapping transactions open and asserts one stored escalation and one outbox row per dispute. Two sequential sweeps do not prove `SKIP LOCKED` prevents double claims.
- [story] Add cases for an operations action racing the sweep, an already manually escalated/resolved/withdrawn dispute, a failed commit followed by a sweep, and a version clash followed by replay. FR-26 explicitly requires re-evaluation after a version race.
- [story] Criterion 5 needs exact warning-window boundaries, including “at due” (escalation without warning), and a test that replay reproduces `SlaWarningRaisedAtUtc`. Criterion 6 needs an assertion for stale *and* fresh heartbeat files and a defined point at which the escalation counter increments—after a successful commit, not merely after invoking the aggregate.
