## Security checklist (security-story), applied to the design

- **AuthZ: who reaches `main`.** The ruleset (9.3) still gates `main`: no bypass actors, the two gates pinned to the app, an up-to-date branch, code scanning, no force push. 9.4 changes only the paths around it:
  - the no-prompt merge form, which cannot check the base, so P7's base-`main` check is a written step only;
  - the force form to `feature/*`, which no ruleset protects (P5, P6);
  - `gh` writes that can change the settings, secrets or variables (P7);
  - the running guard, which is weaker than the approved rule today (P1).

  OWASP Top 10 CI/CD Security Risks: CICD-SEC-1 (insufficient flow control) and CICD-SEC-2 (inadequate identity and access management).
- **Secrets.** The owner token stays inside `$(…)` and is never echoed. A subagent can still read it (P15). `gh secret set` is unguarded (P7b).
- **Input validation.** The guard is the boundary for the story ID, the pull request number, the SHA, the branch and the path. P5, P6 and P14 bound them.
- **Supply chain.** No package, action or gh extension is added.
- **Data, audit, headers, BFF, linking.** Not touched.
- **Standards.** Each mechanism is documented (GitHub flow, auto-merge, retargeting, git-push lease options, `git rebase --onto`, Claude Code `PreToolUse` hooks). The guard's argument matching is the one hand-written part, and that is unavoidable for a `PreToolUse` hook. Bounded as P5 to P7 say, it still fits Boundaries' two sentences.
