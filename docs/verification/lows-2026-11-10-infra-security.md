## (a) provision.sh lock-down: correct

- **Scope.** The filter `or(userOrganizationId, resource.instance, resource.organizationId, resource.projectId)` uses the field names in `internal_permission/v2/query.proto` (`ResourceFilter` oneof: `instance`, `organization_id`, `project_id`, `project_grant`). `query.go` maps them to `NewMembershipOrgIDQuery` (org members of DisputeDesk) and `NewMembershipProjectIDQuery AND NewMembershipNotGrantedSearchQuery` (project members, excluding project-grant members). `PROJECT_ID` is set before the section. If it were ever the string `null` (CreateProject read with `jq -r`, a pre-existing line), role creation at l.179 fails the run first.
- **No new denial of service.** Only an administrator (`org.member.write` or `project.member.write`) can make someone a member of the DisputeDesk organization or project, so an anonymous visitor cannot place an `INITIAL` human in the widened scope (compare H1 in the earlier record). Foreign organization owners stay out of scope.
- **Not a finding: project-grant administrators remain out of scope.** That means a `PROJECT_GRANT_OWNER` on a grant of the DisputeDesk project to another organization. None exists, and only an administrator can create one. Check 12's unscoped `ListAdministrators` (line 1) and sweep C (`project.grant.added`, `project.grant.member.added`) would show one. It would also reach no operations action, because the Api accepts only `Operations:AllowedClients`. The README's wording, "on the DisputeDesk organization or project", is accurate.
- **`ORG_ID` with `jq -er`.** A missing or null `resourceOwner` now fails under errexit (top-level assignment). This closes L3. ASVS 5.0 V16.5.3.
- **Empty `GetUserByID` answer.** `jq -r` prints nothing for an empty body, and the `case` now accepts only `true` and `false`, so anything else logs and returns 1. A `{}` or `{"user":null}` answer already failed, because `has` on null raises a jq error. The control fails closed on every answer shape I checked. ASVS 5.0 V16.5.

## (b) MAILPIT_SEND_API_AUTH: correct; delete through the UI login accepted

- **The Send API refuses the UI login once this is set.** `sendAPIAuthMiddleware` (server.go l.302-340): when `auth.SendAPICredentials != nil`, the request must match those credentials. Otherwise it gets a 401 and never falls through to the UI check. A match sets `skipUIAuthKey`, so the Send login does not need the UI login either. `MP_SEND_API_AUTH` is read in `cmd/root.go` l.287 through `SetSendAPIAuth`, which uses the same htpasswd parser as `MP_UI_AUTH`. The bound `^[A-Za-z0-9]{1,32}:[A-Za-z0-9]{32,128}$` excludes whitespace, which Mailpit treats as a separator between credentials, and excludes the `$`/`{` hash prefixes. The builder's gateway test shows this end to end: UI login 401, Send login 200.
- **Handling of the secret** is the same as `MAILPIT_UI_AUTH`: an SSM SecureString under the instance's path (the IAM `GetParametersByPath` on `${ssm_path}/*` covers the new name), checked against the bound before any docker call, written to `.env` mode 0600, and never printed. If the secret is missing, the deploy stops at `deploy.sh` l.69, and Compose's `:?` stops too. Mailpit v1.32.0 has no option to switch the Send API off, so a separate login that is never handed out is the documented approach (Mailpit runtime options, "Send API"). ASVS 5.0 V8.2.1 and V13.3.1.
- **SMTP is still unreachable from outside.** This diff does not change it: AWS compose `ports: !reset []`, the AWS gateway's only Mailpit upstream is `mailpit:8025` (no 1025 in `templates-aws/nginx.conf.template`), and the security group is unchanged. No relay is configured. `POST /api/v1/message/{id}/release` dials an empty relay host and fails. Chaos is off (`chaos.Enabled` is false without `--enable-chaos`), so `PUT /api/v1/chaos` refuses.
- **Delete still uses the UI login.** `DELETE /api/v1/messages` and `/api/v1/search`, tag edits and read-status changes are all behind `middleWareFunc` with the UI credentials. That is acceptable for the shared synthetic demo inbox (P50 and the 2026-11-10 decision). The effect is availability: a reader can delete other visitors' OTP or reset mails. No security check relies on the inbox, because compromise evidence comes from Zitadel's events in check 12.
- The supervisor's later README change (a standalone command that creates only `MAILPIT_SEND_API_AUTH`, without `--overwrite`) does not change any finding. Without `--overwrite`, `put-parameter` refuses an existing name, so the command cannot replace a live secret.

## (c) Check 12, sweeps C and D: reliable for their purpose, with two lows

What I verified:
- **Endpoints and fields.** Admin `ListEvents` (`POST /admin/v1/events/_search`, `events.read`), with request fields `asc`, `limit`, `eventTypes` and `aggregateTypes`. Response fields are `events[].editor.userId`, `.aggregate.id`, `.type.type` and `.creationDate` (`event.proto`). The aggregate types `org`, `instance`, `project`, `user`, `usergrant`, `execution` and `target` match each repository's `AggregateType`. All 28 event-type names match the repository constants. D uses Admin and Management `ListProviders` (`result`), Management `ListActions` (`result`), and Action v2 `ListTargets` (`targets`) and `ListExecutions` (`executions`).
- **Paging.** The server caps `limit` at 1000 (`maxLimit`). With `asc: true` the oldest come first, so the `>= 1000` error is the right fail-closed condition.
- **Editors.** An event's editor is `authz.GetCtxData(ctx).UserID`, and `contextWithInstanceSetupInfo` sets none. `eventstore.push` stores `c.creator` as given (`cmd/setup/40/02_func.sql`), so setup events have an empty editor. v2 `CreateProject` adds project members only when the request lists admins, and the provisioner sends none, so there is no `project.member.added` from the provisioner. The filter's precedence is correct.
- **Local run of the filter on sample events.** Expected events give `[]`. A `user.pat.added` from another editor, an `instance.smtp.config.changed` from the provisioner, and an unlisted type with an empty editor are each printed. The expected lines `[]` and `[0,0,0,0,0]` are what `jq -c` and `jq -sc .` print.
- **What "setup" means.** It covers any event with an empty editor, which is setup or an anonymous request. So C sees only authenticated editors. An organization left over from H1 (registered anonymously) is classed as setup, but lines 1 and 2 catch it. The provisioner's allow-list would hide actions by someone holding its PAT. That is outside the threat model, because the PAT never leaves the instance and is root on its own. `user.machine.secret.updated` is a hash-algorithm update, not a new secret. If it ever shows up, it is a false alarm sent to a human, not a gap.

### L1: mail-provider changes not covered (low)

`eventTypes` holds `instance.smtp.config.added` and `.changed`, but v4.20.0 also has `instance.smtp.config.http.added`, `instance.smtp.config.http.changed` and `instance.smtp.config.activated` (`internal/repository/instance/smtp_config.go` l.14-21). An administrator taken over through the inbox before the lock-down could add an HTTP email provider and activate it. Every later reset and verification mail would then go to their endpoint and never reach Mailpit, and line 4 would still print `[]`, because D does not count mail providers.

Fix: add those three types to the query. If FirstInstance emits `instance.smtp.config.activated` with an empty editor, add it to `expected.setup` (setup calls `prepareAddAndActivateSMTPConfig`; I did not confirm the event). Alternatively, add `POST admin/v1/email/_search` to D and require exactly one provider: the setup one, with host `mailpit:1025`. Also, `project.application.changed` and `.reactivated`, `project.grant.changed`, `project.grant.member.changed` and `user.grant.reactivated` are missing. Each needs an object that check 12 already shows as absent or as provisioner-owned, so adding them is optional. ASVS 5.0 V16.2 (security events logged and reviewed). This is low because it is a detection gap in a check a human runs, not a control.

### L2: C and D fail open on the answer's shape (low)

`rpc` uses `--fail-with-body`, so on an HTTP error curl writes the error JSON to stdout. Each jq then reads that body and gets `.events // []` = `[]` or `.result | length` = `0` (reproduced locally). A 200 answer with a renamed field gives the same result, and so does a wrong aggregate-type name, which silently filters out that aggregate's events.

- If ListEvents fails, errexit stops the script before D runs, so only four lines print and the mismatch is visible.
- If the **last** D call fails, stdout is exactly `[0,0,0,0,0]`. The failure shows only as curl's stderr line and a non-zero exit status.
- C's `[]` cannot tell "no events returned" from "all events expected". This is the same pattern as round-0 M1.

Fix, in the style of provision.sh's postcondition: in C, require the answer to contain the setup `user.pat.added` and the provisioner's `user.grant.added`, and raise `error(...)` if either is missing. In D, use `jq -e` with a shape check, for example `if has("details") then (.result // []) | length else error("unexpected answer") end` for v1 and `has("pagination")` for v2. Or use `--fail` instead of `--fail-with-body` there, so an error body never reaches jq. Also state that the exit status must be 0. ASVS 5.0 V16.5.
