## Pre-mortem
- [story] A month later, a rejected or failed API request is cached despite criterion 7 passing: its tests cover 429 and 502, but not other gateway-generated failures. The requirement says **every** `/api` response has `no-store` ([PRD](docs/prd/prd.md), NFR-SEC-7).
- [story] A query marker appears in gateway logs during a rate-limit rejection. Criterion 6 changes access logs, but explicitly leaves the error log unchanged; the proposed “gateway’s log holds none of the markers” assertion does not distinguish them.
- [story] An HTTP request to exactly `/api` is redirected by CloudFront and served as the SPA by nginx: the proposed `/api/*` behaviour and existing `location /api/` do not cover that exact path.

## Simplest design
- [story] Keep one path-only access-log format in both templates; one identity-header include that preserves Zitadel’s CSP; the specified CSP, HSTS and charset changes; and the same API-error handling in both gateways. Test access logs separately from error logs. No new logging service, header framework, or edge scripting is needed.
- [decision] Resolve the scope of “every `/api` response” before building. Adding `no-store` only to named 429/502 handlers is simple but does not meet NFR-SEC-7; adding it indiscriminately to proxied responses conflicts with AD-23’s rule that the Api owns that header ([architecture](docs/architecture/architecture.md), AD-23).

## Assumptions
- [story] The three CloudFront default domains have no DisputeDesk-served descendants, making `includeSubDomains` acceptable. This is stated in the story, but mocked Terraform plans cannot establish what will be served after deployment; retain it as an explicit deployment assumption.
- [story] Three `curl --parallel` bursts of 60 will reliably cause a 429. Concurrency improves the current sequential probe, but request count alone does not establish an arrival rate on every host; the test should report its observed result rather than claim host-speed independence.

## Standards
- [story] The proposed header, charset, logging, error-page and viewer-protocol mechanisms are documented nginx, CSP, HTTP and CloudFront mechanisms; no invented mechanism is necessary. For the API-error design, use nginx’s documented [`error_page`](https://nginx.org/en/docs/http/ngx_http_core_module.html#error_page), [`add_header` inheritance](https://nginx.org/en/docs/http/ngx_http_headers_module.html#add_header) and [`proxy_intercept_errors`](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_intercept_errors) behavior rather than assuming a header on two named handlers covers every failure.

## Gaps
- [decision] Criterion 7’s universal wording and its two-status test disagree with NFR-SEC-7 and AD-23. Decide and document which component owns `no-store` on gateway-generated API errors, then test the agreed scope—including `/api`—without duplicating the Api’s header.
- [story] Criterion 6 should assert **access-log** contents, not all `docker logs`, and specify how rejection/error-log entries are excluded. Its stated error-log deferral otherwise makes the marker assertion unreliable.
- [story] Criterion 5 needs an explicit expected result for `http://<APP_HOST>/api` or an explicit exclusion. Its post-deploy checks exercise only paths beneath `/api/`.
- [story] “Every response” in criterion 1 needs a boundary: the gateway tests cannot prove headers on CloudFront-generated responses, including the HTTP 403 introduced by criterion 5. Specify HTTPS responses produced or proxied by nginx, or make edge-generated responses a separately decided requirement.
