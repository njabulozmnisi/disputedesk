## Findings

- **F1 (5.2 regression, fixed in e2e, QA-owned).** `e2e/tests/scalar-reference.spec.ts` located the operations route in Scalar with `/Test Request.*operations/` and the last `disputeId` link. With three more operations routes in the OpenAPI document both matched several elements (strict-mode violation). Now it picks the read (the first of the last four links in the group) and the button `Test Request (get /api/v1/operations/disputes/{disputeId})`. Re-run on customer B's data: 5/5 pass. Copied to the main checkout. The builder should know the spec depends on the order read, start-review, escalate, resolve in the Operations group.
- **F2 (not 5.2, environment): customer A's 20 disputable transactions run out in the full suite.** `outbox-relay-failure-paths.spec.ts` (needs 4 left, 3 left) and `transactions.spec.ts` (needs one) failed on A's supply. 16 of A's 20 were used before the 5.2 spec started, and the 5.2 spec raises on customer B only (it never touches A). Not run on main without 5.2 to compare, so "pre-existing" is inferred from the count. Suggest the tester or the seed gives A more transactions, or specs share a raise helper that spreads over A and B.
- **F3 (observation, no action needed for the story): a lost version clash is logged at `fail:` level by EF Core** (`Microsoft.EntityFrameworkCore.Update[10000]`, 23505 on `UQ_StoredEvents_DisputeId_Version`, detail redacted, no data). It appeared twice, once per HTTP race below. The handler maps it to the retry and the response is correct. If log alerting keys on `fail:`, this will page on every race.
- **F4 (observation, pre-existing, customer BFF): one `Unhandled exception on POST` logged by `UnhandledExceptionHandler`** for an `AntiforgeryValidationException` caused by "Unexpected end of request content" (a truncated body, most likely from the ZAP scan). Customer route, not touched by 5.2.

## Criteria walked live

Spec: `e2e/tests/operations-actions.spec.ts` (44 tests, in the tree and in the main checkout). Database facts through `qa_readonly`. Token from `scripts/operations-token.sh`; four more throwaway machine users (no role, `dispute.read` only, all roles but unmapped) are created by the spec in Zitadel with the stack's admin PAT read from the bootstrap volume.

### 1. FR-24 cells (all 15, on the live stack)

Every cell ran through the real route and the observed result equals the PRD table.

| From | start review | escalate | resolve |
|---|---|---|---|
| submitted | 200 -> underReview | 200 -> escalated | 409 `disputeStatus` submitted |
| underReview | 409 `underReview` | 200 -> escalated | 200 -> resolved |
| escalated | 409 `escalated` | 409 `escalated` | 200 -> resolved |
| resolved | 409 `resolved` | 409 `resolved` | 409 `resolved` |
| withdrawn (by owner) | 409 `withdrawn` | 409 `withdrawn` | 409 `withdrawn` |

Each 200 was checked for: the strict camelCase body with exactly `createdAt, disputeId, disputedAmount, expectedAmount, outcome, reason, status, timeline, transaction`; equality with the following operations read; last timeline entry `actorType` `operations` with the right `fromStatus`/`toStatus` and the stored event's instant (digit for digit); stored event type (`ReviewStarted`, `DisputeEscalated`, `DisputeResolved`), next version, `ActorType` `Operations`, data holding only `fromStatus` and `toStatus` for start review and escalate; `Disputes` row status and version equal to the event's; no audit row added. Each 409: problem type `action-not-allowed`, extension `disputeStatus` (no `customerStatus`, no `status` clash), stored events and outbox unchanged, exactly one new audit row `{Action, Rejected, Operations, sub, CustomerId null, DisputeId}`.

Extra: resolve with unknown properties (`extra`, `status`) is accepted; start review sent with a JSON body or a `text/plain` body ignores it (no note stored).

### 2. Roles, 401, 403 (and ordering)

- No token, malformed token: 401 with bare `WWW-Authenticate: Bearer`, problem type `unauthorized`, no row, before 400/404/415 (a `[]` body and a `text/plain` body with no token are 401).
- Session cookie alone, and cookie plus a valid antiforgery header (CSRF does not reach these routes): 401, no `Location`, no row.
- Tokens with no role, `dispute.read` only, and every role with an unmapped `sub`, on all three action routes and the read, for a real and an unknown ID: 403 `forbidden`; real and unknown bodies equal apart from `traceId`; nothing changed on the dispute.
- 403 comes before 400 and 415 (bad JSON, `[]`, `text/plain`, `not-a-guid` all 403 for a refused token).
- Unlinked customer C on a customer route: 403 `linking-required`, no row. A bearer on a customer route: 401 with no challenge, no row.

### 3. Inputs and check order (resolve)

- Binding failures give 400 `validation` before the lookup, on a known and an unknown ID, no field named, input not echoed, no audit row: malformed JSON, `[]`, JSON `null`, no body, `"outcome": 1`, `["upheld"]`, `"upheld, rejected"`, `"maybe"`, `"Upheld"` (PascalCase refused), `"note": 5`. `text/plain` body: 415 `validation`, no row.
- Well-formed bodies: unknown ID gives 404; known ID gives 400 naming `outcome` (missing, null) or `note` (missing, null, whitespace only, 501 units, 501 units ending in a surrogate pair), on an Under review and on a Resolved dispute (never 409); no row. A 500-unit note (498 plus a surrogate pair) padded with spaces is accepted and stored trimmed.
- `not-a-guid`: 400 naming `disputeId` without echoing it, for each action, no row.
- Unknown ID: 404 `not-found`, equal to the customer 404 apart from `traceId`, no echo of the ID, one `Rejected` row per action with `DisputeId` = the requested ID.

### 4. Version clash (live HTTP races; the interceptor cases are integration-only)

- Two simultaneous resolves on one Under review dispute: statuses `[200, 409]`; the 409 has `disputeStatus` `resolved`; the stream is `DisputeRaised, ReviewStarted, DisputeResolved` (one resolve), the stored note is the winner's, two `status-changed` outbox rows, exactly one `Resolve`/`Rejected` row.
- Resolve against the owner's withdraw on one Under review dispute: statuses `[200, 409]`; three stored events; the loser's 409 carries the reloaded status (`withdrawn` for the resolve, customer status `resolved` for the withdraw), whichever side won.

### 5 and 6. Audit

- `Denied`: one row per 403, action = route (`StartReview`, `Escalate`, `Resolve`, `DisputeRead`), `ActorType` `Operations`, `ActorId` = the token's `sub` (mapped or not), no customer ID, `DisputeId` = route value (real or unknown) and null for `not-a-guid`. The cookie plus an unprivileged bearer records the bearer's `sub`, never the customer's. The read route's 403 is now audited (5.1 changed).
- `Rejected`: one row per 404 and 409 with the dispute's (409) or requested (404) ID, no customer ID. No row for any success, 401, 400 or 415.
- Operations audit rows hold no outcome, note or customer ID.

### 7. Events and customer timeline

- Outbox: `disputedesk.dispute.status-changed.v1`, CloudEvent `specversion` 1.0, `id` = stored event ID, `subject` = dispute ID; data equals exactly `{disputeId, fromStatus, toStatus, action, actorType: "operations", occurredAt, disputeVersion}` plus `outcome` on resolve only; `occurredAt` equals the stored event's instant. No `sub`, no note in any payload. Trace parent present on each row.
- Topic: all outbox rows of four acted disputes (including the 7 status-changed events) on the topic once each, key = dispute ID.
- Customer detail after the actions: start review shows `{action: startReview, actor: theBank, customerStatus: underReview, note: null}`; escalation shows `underReviewPrioritised`; resolve shows `{action: resolve, actor: theBank, customerStatus: resolved, note: "We've reversed this debit."}` (trimmed) and top-level `outcome` `upheld`/`rejected`. The body holds no `sub`, `Operations`, `actorId` or `traceId`.
- Customer cannot withdraw the resolved dispute: 409 `action-not-allowed` with `customerStatus` `resolved`. Another customer reading the dispute: 404, no data.

### 8. Metrics and telemetry

- Aspire dashboard, Table view, last hour: `disputedesk.dispute_actions` has only the labels `action` (escalate, resolve, startReview, withdraw) and `actor_type` (customer, operations); operations total 12 = startReview 5, escalate 2, resolve 5, matching the database exactly although the run made dozens of refused calls (refusals, the clash loser and 400s added nothing). `disputedesk.disputes.resolved`: 5, labels only `outcome` (rejected, upheld) and `sla_escalated` (`false`).
