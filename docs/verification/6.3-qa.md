## Other checks

- **`ClaimAsync` for a locked challenge.** With D's lock held, a start was accepted (202) and its job waited. Three wrong codes on the blank challenge gave 422 (2 left), 422 (1 left), 409 `linking-locked`. After the lock was released the job stopped with exactly one `LinkingOtpSent` `Rejected` row (D's customer ID, client IP present) and no `Succeeded`; the challenge row still had 3 attempts, no OTP, no send stamp; the SMS count to D did not change. No SMS for a locked challenge.
- **Database.** Rate-limited requests wrote no `LinkingStart` row and no challenge. Audit rows exist only for linking and refused actions.
- **Events.** The topic held 18 records (the fixture's disputes) before and after seven requests including two rate-limited ones: nothing is emitted. The topic holds none of D's details or the logins' subs.
- **No personal data.** The Api log, the dashboard's spans and logs, and the topic held none of D's ID number, cellphone, account number or any OTP HMAC, and none of the nine throwaway logins' subs. The only Api log lines on the rate-limit path are the framework's; the limiter logs only on a failed audit save (not provoked).
- **Order of checks (observation O1).** The limiter runs before antiforgery validation, so a request with a forged or missing antiforgery token takes a permit from the signed-in login (a 400 took one, in line with the story: "a 400 does"). A cross-site forger needs the session cookie to be sent, which `SameSite` prevents; no action asked.
- **Not walked on the stack.** Permits returning segment by segment (needs 1 minute or more of real window; the window cannot be shortened on the stack without rebuilding, left to `RateLimitWindowTests`), IPv6 /64, the first-rejection cache `SizeLimit`.

## Conflicts and open items

- **C1 (for the supervisor).** With 6.3 merged, the committed `linking-start`, `linking-verify` specs (and the 6.5 block) cannot run on the stack as configured: they send more than 5 requests from one login and more than 20 from one address. The story's "Touches" has no compose or e2e change. This QA used a throwaway override outside the tree. A decision is needed: an `e2e` Compose override file (or documented env) that raises the limits, with the 6.3 spec as the only run on the production limits.
- **C2.** The e2e data budget (S1) still fails two `dispute-withdraw` tests on a fresh database.
- **C3.** Enabling the queue-capacity variable breaks `linking-verify`'s D tests in the same run (D's hourly cap); the 6.5 block and the 6.2 spec need separate fresh databases or the cap needs resetting between them.
