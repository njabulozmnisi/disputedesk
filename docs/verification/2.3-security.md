## What holds

The customer comes only from `CustomerLinks` by the session's `sub`. The session cookie holds only a random key; the ticket is server-side and its principal comes only from the validated ID token (`MapInboundClaims = false`, no userinfo), so a client cannot add or change claims. A `customerId` query field, an `X-Customer-Id` header and a `sub` equal to another customer's ID all fail to switch customers. The cursor is escaped and the customer ID travels in a header taken from the database; core banking accepts only the resolved customer's own transaction IDs, and another customer's cursor gets the same 400 as an unknown one. The seeder needs an explicit `Seed__Enabled` and a read-only fixtures mount; a seeding race hits the unique index and retries. No customer ID reaches spans or logs.

| # | Severity | Finding | Resolution |

| 1 | Low | Customer data responses had no `Cache-Control: no-store`; a shared device could keep the transaction JSON in the browser cache | Fixed: the Api sets `no-store` on every `/api` response |

| 5 | Info | No API-level test for a cursor carrying another customer's transaction ID | Fixed: test added |
