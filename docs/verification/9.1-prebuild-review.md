## Findings

1. [story] medium. **The moved install scripts are no longer linted.** Verify (:21) says actionlint and shellcheck pass. But actionlint lints only `.github/workflows/*.yml` (`ci.yml:351`), and it does not shellcheck a composite action's `run:` steps. I checked this locally with actionlint 1.7.12, the version CI pins: an unquoted `$VAR` in a scratch composite action's `run:` was not reported, the same line in a workflow `run:` was reported as SC2086, and `actionlint action.yml` treats the file as a workflow and fails. The `shellcheck` step lints only `infra/**/*.sh` and `scripts/*.sh` (`ci.yml:356`). So criteria 4 and 5 move about 20 linted lines out of every lint, and Verify passes without covering them. Fix: GitHub's own composite-action example puts the script beside `action.yml` and runs it through `github.action_path` (*Creating a composite action*). Each action runs `install.sh` from its own folder, with `shell: bash`, and the `shellcheck` step's pathspec gains `.github/actions/*/*.sh`. Alternatively, state the gap as a `shortcut:` with its limit. Either way, name the choice in criteria 4 and 5 and in Touches.
2. [story] medium. **The `codeql` matrix's combined result is asserted with no source and no check.** Inputs (:24) say `needs.codeql.result` is "the matrix's combined result". GitHub Docs (*Contexts*, `needs.<job_id>.result`; *Workflow syntax*, `jobs.<job_id>.needs`; *Running variations of jobs*) list the four values but never say how a matrix's legs combine. `fail-fast: false` (`security.yml:61`) lets one leg fail while the other succeeds, and that is the case the gate must catch. The only Security check is `exit 1` in `vulnerable-packages`. Fix: add a Supervisor check in which one leg only fails (for example `if: matrix.language == 'csharp'` on an `exit 1` step) and `security-passed` fails naming `codeql: failure`. Label the combined-result rule "observed, not documented" in Inputs.
3. [story] medium. **The docs-only Supervisor check (:81) passes before the change, and as written it is not docs-only.** `ci-changes.sh:29-36` already returns `code=true` for every event that is not a push, so a docs-only pull request runs every job on today's `ci.yml`. The check cannot fail without the change. Also, a throwaway branch that carries 9.1's workflows opens a pull request to `main` that holds all of 9.1's code changes, not only `docs/glossary.md`. What the change removes is the skip on a docs-only **push**, and the diff proves that removal structurally. Fix: replace the check with a structural assertion that fails on today's file. In `ci.yml` no job has `if:` or `needs:` except `publish` and `ci-passed`, and `security.yml` likewise except `security-passed`. If a runtime check is kept, it targets `story/9.1` rather than `main`, so its diff is only the glossary.
4. [story] medium. **"The gate needs every check job" is an invariant the design relies on, and nothing enforces it.** After 9.3 the two gates are the only required checks (ad-012 clause 2). A check job added to `ci.yml` or `security.yml` later and left out of the gate's `needs` would then never block a merge, and nothing would fail. This is the 3.8 pitfall: an invariant a decision relies on is enforced in code and proved by a test. Fix: add one `floor-guard` step. For each workflow it fails unless the gate's `needs` equals every job but `publish` and the gate itself. yq 4.54.1 and jq 1.7 are preinstalled on `ubuntu-24.04` (actions/runner-images, `Ubuntu2404-Readme.md`); the builder confirms the yq expression. Add a Supervisor check that adds a dummy job, so the step fails naming it.
5. [story] low. **The gate's job list should exist once.** Criterion 2 passes the results through `env` but does not say how. Hand-written per-job variables are a second list that can drift from `needs`, and a job left out of `env` is never checked. Fix: one variable, `NEEDS: ${{ toJSON(needs) }}`, read with jq, so the script checks every entry of `needs` (the *Contexts* `needs` example shows that object's shape). Then the list lives only in `needs`, and finding 4's check covers it.
6. [story] low. **Nothing proves the `cancelled` result.** The checks cover `failure` and `skipped`. Fix: add a Supervisor check that runs `gh run cancel` on a throwaway pull request's CI run while `e2e` runs. `ci-passed` still runs, because `always()` runs "even when canceled" (*Expressions*), and fails naming each cancelled job. This also shows why the story is right to choose `always()` over the `!cancelled()` that the *Expressions* page recommends in general: a gate skipped in a cancelled run would report a skipped check, and *Troubleshooting required status checks* counts `skipped` as a successful status.
7. [story] low. **The Trivy action has no Supervisor check.** Compose has one. Fix: change one character of the SHA-256 in `install-trivy/action.yml`; `trivy` fails at the checksum and `security-passed` names `trivy: failure`.

## Standards check (each mechanism, checked in GitHub Docs on 2026-11-05)

- `pull_request` runs on `refs/pull/<n>/merge`. *Events that trigger workflows*: verified. The page also says no `pull_request` run starts while the pull request has a merge conflict, which matters for 9.3, not here.
- A skipped job reports success; use `always()` with `needs` for a required check that depends on other jobs; `success`, `skipped` and `neutral` all satisfy a required check. *Troubleshooting required status checks*: verified, and it backs criteria 2 and 3.
- `needs.<job_id>.result` takes the values `success`, `failure`, `cancelled` and `skipped`. *Contexts*: verified. How a matrix's legs combine is not documented (finding 2).
- `always()` returns true even when the run is cancelled. *Expressions*: verified (see finding 6).
- In a composite action, `shell` is required when `run` is set, each step has its own `env`, and `github.action_path` is available. *Metadata syntax* and *Creating a composite action*: verified.
- Untrusted input goes through an intermediate environment variable. *Secure use*: verified. The needs results are not untrusted, so the rule is used here for consistency, which is fine.
- No home-grown mechanism. Each gate is the documented aggregate-job pattern, and each local composite action is GitHub's documented reuse form.
- Each part can be explained in a sentence or two.
