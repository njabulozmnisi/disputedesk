### Pass 1: correctness, on the points you named

**The transaction and the lock**
- In `LinkingJobSteps.ClaimUnderCustomerLockAsync` (around lines 125–160), the job's own `AppDbContext` opens the transaction with `BeginTransactionAsync(budget)` at the default Read Committed. Its first statement is `OtpSends.LockCustomerAsync`, which runs `SELECT pg_advisory_xact_lock(@p0, @p1)` with two `int` parameters: namespace 6005 and the first 4 bytes of the SHA-256 of the customer ID.
- Then come the cap count, `ISimSwapCheck`, the budget check and the claim, and `CommitAsync(None)` before `SendAsync`.
- The lock is held from the first statement until commit or rollback:
  - On the capped and SIM-swap-failed paths, an explicit `RollbackAsync(None)` runs before the audit save. This is needed, otherwise the audit would join the open transaction and be rolled back with it.
  - On the claim-returned-0 path, it commits and then audits.
  - On an exception or a cancelled budget, the `await using` disposal rolls back before the outer catch runs.
- No retrying execution strategy is configured, so a user-started transaction is allowed.
- By design (AD-12) the lock and one pooled connection are held during the SIM-swap call. This is bounded by the budget (60 s at most) and by 4 workers.

**What the parallel test proves**
- In `LinkingSendCapTests` (lines 94–116), the first job to take the lock is held at the SIM-swap check, which sits between its count and its claim. The test then waits until 3 jobs are waiting on an advisory lock (`pg_locks.granted = false`), releases the hold, and asserts 1 send and 5 `LinkingSendCapped`.
- If the lock is removed, the waiter check times out. With the count moved outside the transaction (the builder's break), the test sees 4 sends.
- Each test Api has its own database (`LinkingApi.StartApiAsync` uses `CreateMigratedDatabaseAsync`), so probes filtered to the current database are not affected by parallel tests.
- `Job_CustomerLockHeldPastTheBudget` proves that the lock wait runs under the budget and ends in `LinkingStart Failed`. `Job_WhileSending` proves that no lock and no idle-in-transaction connection exists during the send.

**Every claim counts, and the release**
- `ReleaseAsync` no longer clears `OtpSentAtUtc`. The count is LINQ (`OtpSentAtUtc > now - 1h`) and carries the story's `// shortcut:` comment.
- The criterion 1 test covers 2 delivered sends plus 1 released one, from 3 logins and 2 IPs, and the 4th start is capped: still 202, the audit has customer D, `capped` is counted, and the SIM-swap check is not called.
- The edge test seeds at a microsecond-aligned instant: 3600 s later the start sends, 3599 s later it is capped.
- 6.1's two release tests now expect `OtpSentAtUtc == clock.NowAsStored`, on a clock that is not microsecond-aligned (Known pitfall 3).
- The `LinkingRestartTests` change (holding the job at core banking instead of the SIM-swap check) is sound. The job is still held before its claim, the assertions are unchanged, and the test now also covers a claim that returns 0 inside the lock.

**The 429**
- The new `ErrorKind.RateLimited` maps to 429 in `ErrorResults.StatusCodeFor`, the single error-to-HTTP mapping. `LinkingErrors.QueueFull` has code `rate-limited`.
- The endpoint returns `Results<Accepted, ProblemHttpResult>` with `.ProducesProblem(429)`. No `Retry-After` is set anywhere.
- The test asserts that a matching and a non-matching start get the same body (minus `traceId`), that neither has `Retry-After`, and that neither is queued (5 core-banking calls).
- `ErrorTests`, `ProblemDetailsTests` and `ProblemCatalogueTests` are all updated.

**The audit when the `LinkingRateLimited` save fails**
- The second save runs on `CancellationToken.None`. If it fails, it logs one error line with only the challenge ID and the action, and the response is still the 429. The test proves this with `FailAuditInsertInterceptor.OnlyAction`.
- The session ticket store uses its own scope, so the failed entry left in the request's context is never saved again.

**Unexpected exceptions**

- The test throws an `InvalidCastException` whose message contains the ID number, from the SIM-swap fake and from the core-banking fake. It asserts the audit, that nothing is claimed, that no lock is left held, that the log has only the challenge ID and the exception type, and that the next start sends.

1. **Budget bound, verifier criterion 5: closed.**

2. **Two-key probe, review low: closed.**
   - `LinkingDatabase.cs:20` filters on `classid = 6005 AND objsubid = 2`. This matches the PostgreSQL `pg_locks` docs: a two-key advisory lock shows `objsubid` 2, and a bigint (one-key) lock shows 1. A one-key lock built as `(6005L << 32) | key` also shows `classid` 6005, so `objsubid` is the column that tells the two forms apart. The builder broke the lock exactly that way.
   - The renamed test, `Job_HoldsTheTwoKeyCustomerLockAtTheSimSwapCheckAndNoLockAndNoOpenTransactionWhileSending` (`LinkingSendCapTests.cs:151-170`), now proves the lock's form. It holds the SIM-swap call and asserts exactly 1 granted two-key lock there.
   - That point is inside the transaction, after `LockCustomerAsync`, so the assertion is deterministic (`LinkingJobSteps.cs:128-141`).
   - Each Api gets its own database (`CreateMigratedDatabaseAsync`), and the probe filters to `current_database()`. Parallel tests cannot raise the count above 1.
   - It then releases the check and asserts 0 locks and no open transaction while the SMS is sent.
   - Before the fix, this test could not fail against a one-key lock. The builder reports both it and the parallel test failing against the one-key break.
3. **Bounds in one place, review low: closed.** All four bounds are constants grouped above the properties in `LinkingOptions.cs:11-17`. `Validate` uses them both in its conditions and in its interpolated messages, and the tests keep the literal expected text, so a drift fails a test. `TotalSeconds` of 1 and 60 prints with no decimal separator in any culture.
4. **`OtpSentAtUtc` doc, security L1: closed.** `LinkingChallenge.cs:30-34` now says the value is the job's start instant (AD-4's single clock reading), at most one `Linking:Budget` before the claim, so the hourly window can be short by up to one budget. It is a doc-only change.
5. **Nits: closed.**
   - `RecordAsync`'s parameter is now `context` (`LinkingJobSteps.cs:192-201`).
   - `ClientAddressStartupFilter` has a settable `Address`, and the duplicate class is deleted.
   - `ThrowNext` is now the set-only method `ThrowOnNextCall(Exception)`.
   - `WaitIfHeldAsync` has its 6.1 name back. I confirmed that b3c9dbf's `LinkingFakes.cs:82` uses the same name and signature (`protected async Task WaitIfHeldAsync(CancellationToken)`), so 6.2's fakes build unchanged.
