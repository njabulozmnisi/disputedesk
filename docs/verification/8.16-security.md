## Placeholders cannot add JSON structure in envs/dev

- Every placeholder is inside a JSON string, so `JsonDocument.Parse` reads each unrendered template; `IamNames.ReadPolicy` pins the top-level keys to exactly `Version` and `Statement` and `Version` to `"2012-10-17"`. No template holds a `%{` directive.
- `templatefile()` does not JSON-escape a value (HashiCorp, *templatefile Function*), so a value with a `"` would change the document's structure. Each value that reaches a template is bounded before it does: `aws_region` (allowlist of four), `ssm_path` and `dataprotection_ssm_path` (`^(/[A-Za-z0-9_.-]+)+$`), `github_repository` (`^[A-Za-z0-9-]+/[A-Za-z0-9._-]+$`), both GitHub IDs (digits), `account_id` (STS caller identity), and the ARNs of resources Terraform creates (KMS key, instance, SSM document, OIDC provider, state bucket from the validated bucket name). None can hold `"` or `\`. See finding L1 for where that bound lives.

## The one-time OIDC check (infra/terraform/README.md, step 8)

- Checked against GitHub's REST reference, *Get the customization template for an OIDC subject claim for a repository* (`GET /repos/{owner}/{repo}/actions/oidc/customization/sub`): the 200 response is `use_default` (required), `include_claim_keys`, `use_immutable_subject` and `sub_claim_prefix`, so the endpoint and the two fields the README names exist. `gh api repos/<owner>/<name> --jq '.owner.login, .owner.id, .name, .id'` reads the right fields. GitHub's *OpenID Connect reference* confirms the immutable format `repo:OWNER@OWNER-ID/REPO@REPO-ID:ref:refs/heads/BRANCH`, that repositories created after 2026-07-15 use it, and that a rename or transfer moves to it, which matches the README's re-run triggers and its "configuration, not a token" limit.
- The check fails closed in every case: the trust is `StringEquals` on the exact subject, so any mismatch the check misses ends at `AssumeRoleWithWebIdentity`, never at wider access. See L2 for one field the check leaves out.

## Service-reference client (criterion 5)

- `SocketsHttpHandler` with `AllowAutoRedirect = false`, `UseCookies = false`, `Credentials = null`, `ConnectTimeout` 10 s; `HttpClient.Timeout` 30 s per request, body included; at most 2 retries of an idempotent `GET` (RFC 9110, section 9.2.2) on connection failure, request timeout and 408/429/500/502/503/504, with 1 s and 2 s back-off; one 5-minute `CancellationToken` deadline over the whole fetch, which names the interrupted URL. Default TLS certificate validation (no validation callback). Every URL is built from the fixed HTTPS base and a service prefix that already passed the action bound `^[a-z0-9-]+$`, never from a URL in the index (`Fetch_ValidFiles_...` serves an index with a foreign `url` and asserts it is not requested), so the reference cannot steer a request (OWASP SSRF Prevention Cheat Sheet: no redirects, no URL from the response). A 3xx is not followed or retried; any failure or wrong shape fails the test naming the URL; offline, the fixture fails, never passes.
- The one header is `User-Agent: DisputeDesk-PlatformTests`, a product token (RFC 9110, section 10.1.5), needed because the reference answers 403 without one; `ServiceReferenceFetchTests` asserts the request headers are exactly `User-Agent`. This is the builder's recorded conflict with Inputs ("no extra header"); a User-Agent carries no credential and curl sent one in 7.16, so it is not a finding.
- Mechanisms: `HttpClient`/`SocketsHttpHandler` (Microsoft Learn, *SocketsHttpHandler.ConnectTimeout*, *AllowAutoRedirect*); ASVS 5.0 V12.3.1 and V12.3.2 (TLS for outbound connections, certificate validated), V1.3.6 (outbound requests to an allowlisted destination only).
- Observation, not a finding: the response body is not size-capped (`MaxResponseContentBufferSize` keeps its default); the destination is one fixed AWS host over validated TLS and the 30 s timeout bounds the read, the same as 7.16's curl.

## Findings

- **L1 (low). The no-quote guarantee for template values lives only in the root module.** Before this story `jsonencode()` escaped every value, so no caller could change a policy's structure. Now `templatefile()` inserts values as they are, and the modules (`deploy-role`, `compute`, `observability`) declare `ssm_path`, `dataprotection_ssm_path`, `github_repository`, the IDs, `aws_region`, `account_id`, `kms_key_arn` and `instance_arn` with no `validation`; only `envs/dev/variables.tf` and `bootstrap/main.tf` bound them. Demonstrated in `terraform console`: `instance-policy.json.tftpl` rendered with `ssm_path = "/x\", \"*"` decodes to `Resource ["arn:…:parameter/x", "*", "arn:…:parameter/x", "*/*"]`, a widened grant. envs/dev cannot pass such a value, so nothing is exploitable today, but the modules are kept for a second environment (D8), whose root would have to repeat the validation. The README and the story's Notes state the rule ("a value that could would need `jsonencode()`"); the bound is not enforced where the template is. Countermeasure: move the existing validation blocks (or a no-`"`-or-`\` condition) onto the module variables that reach a template. Standard: ASVS 5.0 V1.2 (injection prevention: output encoding or validation at the point of use); HashiCorp, *templatefile Function* (use `jsonencode` for values that are not known-safe).
- **L2 (low). The one-time OIDC check does not ask for `use_default`.** GitHub's reference says `include_claim_keys` changes the `sub` (and the immutable `repo` segment stays even then), so a repository or organisation subject template would make the deploy job's `sub` differ from `…:ref:refs/heads/main` while `use_immutable_subject` is `true` and `sub_claim_prefix` matches. The README's check would pass and the first deploy would then fail at `AssumeRoleWithWebIdentity`. Fail-closed, so availability, not access; the story's criterion 7 names only the two fields. Countermeasure: add "`use_default` is `true`" (no custom claim template) to step 8. Source: GitHub, *OpenID Connect reference*, "Customizing the subject claims"; REST, *Get the customization template … for a repository*.
- Not a finding, for the reviewer: `infra/terraform/README.md` says "The mocked Terraform tests pin each rendered policy", but the compute trust policy (`ec2.amazonaws.com`, `sts:AssumeRole`) is pinned by none; it has no placeholders and was shown identical above. `deploy_role.tftest.hcl`'s header still says "written with jsonencode" (the builder's own assumption; the story forbids editing the test files).
