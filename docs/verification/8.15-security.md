# 8.15 security review (Feature, security flag: the seeder becomes AD-11's third named ownership-filter bypass, 2026-11-05)

Patch `8.15-only.patch` applied with `git apply --3way --binary` (clean) to a throwaway worktree at `origin/main` `ac5aa88`, removed afterwards. Change: `Seeder.SeedAsync` and `Seeder.Seed` check each fixture dispute on the migrating context with `IgnoreQueryFilters([AppDbContext.OwnershipFilter])`; `SeedDispute.Matches()` gains the customer ID predicate; `ContextFor` (the per-customer `AppDbContext` and `CurrentCustomer`) is deleted; the architecture rule allows the one file `DisputeDesk.Infrastructure/Seeding/Seeder.cs` besides `Application/Operations/` and `Worker/Sla/`, the customer-feature namespace rule adds every project's `.Seeding` namespace, and a new rule bans `new AppDbContext`/`new CurrentCustomer` in `Seeding/`; one new integration test (`SeederOwnershipTests`, both paths). Pass: no high or medium findings.

## Checked

- **The bypass sits only in the three named places.** `IgnoreQueryFilters` in production source is now only in `Application/Operations/ReadDispute/ReadDisputeHandler.cs`, `Application/Operations/Actions/OperationsActionHandler.cs`, `Worker/Sla/SlaSweep.cs` and `Infrastructure/Seeding/Seeder.cs:60` and `:104`. Every use names the filter (`"Ownership"` or the constant `AppDbContext.OwnershipFilter`, which is `"Ownership"`), and the ban on the parameterless form still holds. No other file gains a bypass. EF Core named query filters, disabled by name (<https://learn.microsoft.com/ef/core/querying/filters>). ASVS 5.0 V8.2.2, V8.3.1.
- **The bypass cannot match another customer's dispute.** Both seeder queries pass `SeedDispute.Matches()`, which is now `dispute.CustomerId == customerId && dispute.AccountRef == accountRef && dispute.TransactionId == transactionId`. The customer ID comes from the fixture file, resolved in `PlanOne` from a linked fixture customer whose account holds the transaction. It never comes from a request. The bypass only feeds an `AnyAsync`/`Any` boolean: no row from another customer is loaded, tracked, returned, logged or modified. A miss adds a new `Dispute` raised for the fixture's own customer, so nothing seeded can attach to an existing dispute. When another customer holds the same `(AccountRef, TransactionId)`, the unique index refuses the insert with a `UniqueViolationException` and the dispute is not skipped silently. `SeederOwnershipTests` proves this for `SeedAsync` and `Seed`. The behaviour matches the old filtered per-customer context, which saw only the customer's own rows, so the change has no regression. The builder's break (drop the predicate) makes both cases fail with "No exception was thrown". The verifier runs and records that break; I did not repeat it here. ASVS 5.0 V8.2.2.
- **The architecture rule allows exactly one file and covers the Seeding namespace.** `IsInBypassPlace` compares the path relative to `src/` with `DisputeDesk.Infrastructure/Seeding/Seeder.cs` for exact ordinal equality. The folder rules are unchanged prefix matches. The sample-path theory rejects `Infrastructure/Seeding/SeedDispute.cs`, `Infrastructure/Linking/LinkCustomer.cs` and `Application/Seeding/Seeder.cs`. A partial `Seeder` declared in another file would therefore still fail the rule. The builder's breaks (a bypass in `Infrastructure/Linking/`, and a bypass in a new `Seeding/SeedLookup.cs`) both fail `ProductionSource_IgnoreQueryFilters_AppearsOnlyInOperationsSlaAndTheSeeder`. `BypassNamespaces` adds `{project}.Seeding` and `DisputeDesk.{project}.Seeding` for every project, so `Disputes/` and `Transactions/` cannot reference `DisputeDesk.Infrastructure.Seeding`. The sample-line theory covers the using directive, the short form and a fully qualified member access, and rejects `Vendor.Infrastructure.Seeding`. No customer-feature file references a Seeding namespace today. ASVS 5.0 V15.2 (architectural controls), V8.3.1.
- **No context per customer, so the bypass is visible.** `ContextFor` and every use of it are gone. `Seeding/` now builds no `AppDbContext` and no `CurrentCustomer`. The migrating context is the one EF Core passes to `UseAsyncSeeding`/`UseSeeding` (`SeedRegistration.cs:20-25`, unchanged; <https://learn.microsoft.com/ef/core/modeling/data-seeding>). It has no current customer, so without the named bypass its filter matches nothing. Moving the bypass from an implicit per-customer identity to an explicit named place keeps the rule checkable by the architecture test.
- **The write path is unchanged.** Each dispute still goes through `AppDbContext.SaveChanges`/`SaveChangesAsync` (AD-14). `AddRowsForDisputeChanges` writes the stored event and outbox rows with the dispute, and stored events and audit entries stay insert only. Per stream, each `SaveChanges` is one savepoint inside the migration transaction when one is held (<https://learn.microsoft.com/ef/core/saving/transactions#savepoints>). A failed save clears the change tracker.
- **No personal data in logs or errors.** The only log lines are counts (`Seeded {Count} customer links`, `Seeded {Count} disputes`). Fixture errors name only the position (`SeedDispute.Invalid`, AD-20). `SeedDispute.ToString` stays sealed to the position. The new failure path throws `UniqueViolationException`, whose message is the generic `DisputeErrors.AlreadyDisputed` message. The inner Npgsql exception's `Detail` (the key values) is redacted by default: the repo sets no `Include Error Detail`, and `EnableSensitiveDataLogging` stays off outside tests. ASVS 5.0 V16.2.5.
- **Reachability is unchanged.** Seeding runs only at migrate time behind `Seed:Enabled` (on in `docker-compose.yml:272` and the demo `infra/aws/compose.yml:150`, both unchanged), not on a request path. No endpoint, header, cookie, policy or antiforgery change.
- **Standards.** The change adds no new security mechanism. It uses EF Core's documented named-filter bypass and seeding delegates and the existing Roslyn syntax-tree architecture rules. Nothing is home-grown.
