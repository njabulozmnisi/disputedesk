## Pre-mortem

- [decision] The cookie change ships without an architecture decision: [AD-24](docs/architecture/architecture.md) explicitly says OIDC correlation and nonce cookies keep handler defaults, while criterion 1 requires configured names. Resolve that contradiction before building.
- [story] A sign-out audit times out and logout fails instead of redirecting. The current `RecordSignOutAsync` excludes `OperationCanceledException` from its failure handler; the proposed five-second cancellation will take that path unless it is handled as an audit failure.
- [story] Two instances create different keys on an empty ring and cannot immediately read each other’s cookies. [Microsoft’s key-management guidance](https://learn.microsoft.com/aspnet/core/security/data-protection/implementation/key-management?view=aspnetcore-10.0) says processes cache key rings independently and normally refresh from shared storage approximately every 24 hours. The stipulated test must report a failure, not be made to pass by weakening the exchange check.

## Simplest design

- [story] Configure the two OIDC cookie builders and RS256 on the existing handler; disable redirects on both existing primary HTTP handlers; give only the specified audit saves independent five-second cancellation; and count a new 409/422 at the filter boundary without counting a stored replay. Keep the existing Data Protection registration and add the two evidence tests. No audit queue, retry loop, key-refresh code, new metric tags or extra configuration is warranted.
- [story] Keep successful dispute commits on the request token. `RaiseDisputeHandler` and the action handlers currently separate refusal saves from successful commits, so changing their whole-handler token would needlessly change success behavior.

## Assumptions

- [story] The local sign-in assertion assumes the new unprefixed cookie settings work over HTTP, but `ApiFactory.CreateBrowser` uses **HTTPS** and explicitly notes why its cookie tests do so. Existing sign-in tests alone do not prove the `http://localhost` clause.
- [story] The two-instance test assumes concurrent sign-ins actually overlap first key creation. Starting hosts together and issuing two sign-ins does not establish that overlap; synchronize the first protect operations or otherwise prove the race was reached.
- [story] The five-second audit bound assumes database cancellation promptly stops a blocked save. Assert both the observed cancellation and an elapsed-time bound, rather than only supplying a token.

## Standards

- [story] No new custom mechanism is needed. Use the handler’s documented [correlation](https://learn.microsoft.com/dotnet/api/microsoft.aspnetcore.authentication.remoteauthenticationoptions.correlationcookie) and [nonce](https://learn.microsoft.com/dotnet/api/microsoft.aspnetcore.authentication.openidconnect.openidconnectoptions.noncecookie) cookie builders, [ValidAlgorithms](https://learn.microsoft.com/dotnet/api/microsoft.identitymodel.tokens.tokenvalidationparameters.validalgorithms), [primary HTTP handlers](https://learn.microsoft.com/aspnet/core/fundamentals/http-requests), and [bounded cancellation](https://learn.microsoft.com/dotnet/standard/threading/cancellation-in-managed-threads). In particular, do not introduce a custom key-refresh mechanism to override [Data Protection’s documented management](https://learn.microsoft.com/aspnet/core/security/data-protection/implementation/key-management?view=aspnetcore-10.0).

## Gaps

- [story] Criterion 5 needs an explicit timeout-as-failure assertion: **session row absent, redirect unchanged, error logged with trace ID**. Its current “save fails or exceeds the bound” wording can pass a database-error test while missing the cancellation exception.
- [story] Criterion 4 leaves successful operations reads using the request token in `ReadDisputeHandler`, although the PRD requires an audit entry for **every** operations read. Decide whether disconnect durability covers those successful reads too; the present criterion only exercises a rejected read.
- [story] Criterion 8 does not define whether repeated `idempotency-mismatch` and `idempotency-in-progress` requests each count as a new answer. Unlike a completed-key replay, neither is a stored response; specify the expected increments and test them.
