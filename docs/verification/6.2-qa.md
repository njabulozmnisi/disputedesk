## Standards

- RFC 9110: 204 with no body; 422 for a well-formed wrong code (§15.5.21) and 409 for the lock (§15.5.10); 401 before 403 before 400; `Cache-Control: no-store` on every verify answer, success and problem.
- RFC 9457: 400, 401, 403, 409 and 422 are `application/problem+json` with the catalogue `type`, `status`, a `traceId`, and `attemptsRemaining` as the 422 extension member.
- RFC 6265bis: no verify answer sets or renews a cookie, so the session cookie keeps the attributes it was given at sign-in and its value did not change.
- OWASP Authentication Cheat Sheet (generic responses, lockout) and Session Management Cheat Sheet: every kind of challenge gives the same status, body and headers; the lock holds against the correct code; the session key is server-minted and unchanged. Response timing is not measured here (the security agent owns it).
- OWASP Logging Cheat Sheet and POPIA: no OTP, HMAC or personal data in logs, spans, metrics, the topic or other columns.
- Observation, not a finding: a login with no challenge row writes one `LinkingOtpIncorrect` audit row per post (5 posts, 5 rows), so such a login grows the audit table only as fast as the gateway's `limit_req` (10 a second, burst 20) allows until the per-login limit of story 6.3.
- Observation: the fresh-database start logs EF Core errors for `__EFMigrationsHistory` and `DataProtectionKeys` ("relation does not exist") before the migrations run; unrelated to 6.2 and present on every fresh start.
