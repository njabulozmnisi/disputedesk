## Findings
1. **Low: reason names are matched case-insensitively.** `"reason":"Unrecognised"` returned 201 and created a dispute (TXN-A-0027). The story says any value other than the six names gets 400. Harmless to data (stored as `unrecognised`) but the contract is looser than documented. Decide: tighten the shared converter, or document case-insensitivity.
2. **Low: timestamps in the raise response use `+00:00`.** `createdAt` and `timeline[].occurredAt` read `2026-10-28T09:37:24.0686813+00:00`; AD table (architecture line 384) says "RFC 3339 UTC with `Z`". Fix item 1 covered the event only. `transactionDate` from story 2.3 behaves the same, so this is a shared-options matter. Valid RFC 3339, so not a functional defect.
3. **Info: binding failures say only "Bad Request".** Unknown `reason`, number-typed `expectedAmount`, malformed JSON give 400 `validation` with no `errors` member naming the field, unlike the data-annotation failures. Valid under RFC 9457; the SPA in 3.6 cannot highlight the field.
4. **Info: sub-microsecond precision.** Event `time` and response `createdAt` carry 7 fractional digits; PostgreSQL stores 6 (`.109067` against `.1090676`). Not visible to consumers beyond rounding.
5. **Info, pre-existing:** the gateway and API both emit `X-Content-Type-Options` and `Referrer-Policy` (two different `Referrer-Policy` values on one response). Not from 3.1.
