### Findings, by severity

1. **Medium.** `backend/tests/DisputeDesk.Api.IntegrationTests/Operations/OperationsActionConcurrencyTests.cs:134-157`, `Resolve_TwoClashes_...`, does not prove criterion 4's "no further decision attempt, the status as last read".
   - The second armed event moves the stream to Withdrawn. A third replay-and-decide would also refuse with 409 `withdrawn` and one `Rejected` row.
   - So a handler that retries a third time instead of reading the `Disputes` row passes this test. The comment at line 150 ("A third attempt would have committed") is false.
   - **Fix:** arm the second clash so a third attempt would succeed, for example `DisputeEscalated(Escalated → Escalated)` at version 4 with row status `Escalated`. The test then expects 409 `disputeStatus: escalated` and a stream that ends at version 4. Alternatively, count commands: exactly two replay reads (`ORDER BY s."Version"`) and one `Disputes` read. Correct the comment either way.

2. **Low.** `backend/src/DisputeDesk.Api/Operations/OperationsEndpoints.cs:358-362` uses `AcceptsMetadata([], ...)` to route any content type to the resolve endpoint. This is the builder's decision. I accept it, on conditions.
   - **Why it is needed:** routing's 415 rejection endpoint has no metadata, so the cookie-only fallback policy (`BffAuthentication.cs:55`) answers a bearer caller with 401 before any 415.
   - **Alternatives:**
     - (a) A fallback policy that also authenticates JwtBearer: AD-8 already rejected this option.
     - (b) Reading the body by hand: the story forbids custom body reading.
     - (c) Special-casing the rejection endpoint in `AuthorizationResultHandler`: hidden, harder to explain.
   - **Why this one:** it is the smallest choice, explainable in one sentence, and uses the framework's own metadata type. "Last metadata wins" is documented behaviour of `EndpointMetadataCollection.GetMetadata<T>`.
   - **The weak point:** "an empty content-type list means accept anything" is a detail of `AcceptsMatcherPolicy`'s source, not something I could find on Microsoft Learn. I could not verify it from docs.
   - It is pinned by `Resolve_TextPlainBodyWithNoTokenOrARefusedToken_Returns401BearerOr403Before415` and `Resolve_TextPlainBody_Returns415ValidationAndWritesNoRow`, and `openapi.json` still lists `application/json` for resolve.
   - **Condition:** record the workaround and its source (aspnetcore `src/Http/Routing/src/Matching/AcceptsMatcherPolicy.cs`) under AD-8, so it is a decision and not a hidden trick.

3. **Low.** A wrong HTTP method on an operations path gives a 405 rejection endpoint that hits the same cookie fallback: 401 with no `Bearer` challenge.
   - This already existed in 5.1 for the read route. 5.2 adds paths where a `GET` reaches it.
   - Don't widen 5.2 for it. Add a line to `docs/production-path.md` or open a follow-up story, and answer the builder's open question that way.

4. **Low (nit).** `backend/src/DisputeDesk.Domain/Disputes/Dispute.cs:192-199` against `:302-304`: the file now stamps events two ways. Withdraw inlines the `with { DisputeId, Version, OccurredAtUtc, ActorType, ActorId }`; the three new methods use the generic `Stamped<TEvent>`. Use one style in the file, either `Stamped` in `Withdraw` too or inline everywhere.

5. **Low (nit).** The three operations actions are mapped by three switches:
   - `OperationsActionHandler.ToAuditAction`
   - `DisputeWire.ToWire` (existing)
   - `DisputeActionMetrics.WireName` (`DisputeActionMetrics.cs:213-220`)

   `WireName` only re-derives the camelCase name. `RecordOperationsAction` could take the label string from the endpoint, as `RecordWithdrawn` hard-codes `"withdraw"`. This is optional.

6. **Low (for security).** `AuthorizationResultHandler.cs:172` and `OperationsActionHandler.RefuseAsync` save the audit row with the request's cancellation token. A client that disconnects mid-request cancels its own `Denied`/`Rejected` row. This is the same as 5.1's read, so it is cross-cutting: either use `CancellationToken.None` for audit saves or record it in `docs/production-path.md`.

7. **Info (process).** The `disputeStatus` wording in `docs/problems/action-not-allowed.md` is applied on main (uncommitted), not in the worktree. Make sure it goes into 5.2's commit.

### Pass 2: simplicity
The design is the smallest that meets the criteria:

- One result handler, extended rather than duplicated.
- The policy builder helper `RequireRole` removes four copies of the same chain.
- The thin `StartReviewAsync`/`EscalateAsync`/`ResolveAsync` wrappers each carry their own binding signature and documentation, so they earn their place.

Nothing belongs in production-path beyond findings 3 and 6.

- **One result handler:** Customize the behavior of AuthorizationMiddleware.
