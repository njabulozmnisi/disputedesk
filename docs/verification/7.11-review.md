### Pass 1: correctness

**The switch is exact.** `main.tsx:14` reads `if (import.meta.env.VITE_BROWSER_TELEMETRY !== 'off') startTracing();`. That meets the input rule "exactly `off` turns tracing off; unset, empty or any other value leaves it on". Values on both sides of the boundary are tested: `off` is off, and `undefined`, `''`, `on`, `false`, `OFF` and `off ` are on. A trim or lower-case change fails the `OFF` and `off ` cases. The supervisor's check (compare against `'false'`) makes the off test fail: `'off' !== 'false'`, so `startTracing` runs and `not.toHaveBeenCalled()` fails.

**The tests reset OpenTelemetry's global state, so they can fail.** I checked `@opentelemetry/api` in `node_modules`:
- `trace.disable()` unregisters the global and replaces `_proxyTracerProvider` with a fresh proxy that has no delegate. `propagation.disable()` and `context.disable()` unregister theirs.
- After that, the probe in `trace.getTracer('test').startSpan('probe').isRecording()` gets a NonRecordingSpan. If the app wrongly called `startTracing`, `setGlobalTracerProvider` would succeed again and the probe would record.
- `setup.ts` leaves its fetch instrumentation active. Because the propagator was disabled, that leftover cannot add a `traceparent`. A wrongly registered propagator would add one, so the traceparent assertion is real.
- A wrong start would also re-wrap `fetch` with a new instrumentation. The test force-flushes any provider `startTracing` returned, so a wrong export would reach MSW inside the test.
- The test imports the real `main.tsx` after `vi.resetModules` and spies on the real `startTracing`, rather than testing a helper. It tests the shipped guard.

### Findings (one batch, none blocks approval)

1. **Low, `frontend/src/telemetry/browserTelemetrySwitch.test.tsx:22-23`.** The branch `if (value === undefined) vi.unstubAllEnvs(); else vi.stubEnv(...)` is not needed. The installed Vitest 5.0.5 types accept `string | undefined` (`node_modules/vitest/dist/index.d.ts:804`). `unstubAllEnvs()` also does not truly unset the variable: if the shell or a future CI or Docker step exports `VITE_BROWSER_TELEMETRY=off`, the "unset" case fails. For the criterion "Given the variable unset", the plainer and more exact version is a single `vi.stubEnv('VITE_BROWSER_TELEMETRY', value);`.
2. **Low, `browserTelemetrySwitch.test.tsx:25-27, 31-34`.** Each `await import('@/main')` mounts a full app with `createRoot`. RTL's `cleanup()` does not unmount it, and clearing `document.body` only detaches the container. So seven apps stay mounted, with their router and query client alive, for the rest of the file. Nothing fails today (the builder reports 451 passing). If a later screen refetches after `resetHandlers`, it would hit an unhandled request. No change is needed now; it is worth one line under the reviewer's known pitfalls if it ever bites.
3. **Low, `docs/verification/7.11-build.md:59`.** The standards entry for `trace.disable` / `context.disable` / `propagation.disable` cites the general page https://opentelemetry.io/docs/languages/js/. It should cite the API reference, for example https://open-telemetry.github.io/opentelemetry-js/classes/_opentelemetry_api.TraceAPI.html#disable. The test also relies on MSW life-cycle events (`server.events.on('request:start')`, https://mswjs.io/docs/api/life-cycle-events), which the report does not cite.
4. **Nit, `frontend/src/vite-env.d.ts:1`.** `/// <reference types="vite/client" />` repeats what `tsconfig.json` already loads (`"types": [..., "vite/client", ...]`). It is Vite's documented template form and harmless.
