## Pre-mortem
- [story] Seeding fails or leaks ownership because the existing seeder uses a context with no `CurrentCustomer`; its dispute query filter then matches nothing. The story must specify how each customer's seeding context receives that customer without bypassing the filter.
- [story] The SLA demo escalates at the wrong time if its creation instant is calculated solely from the start-of-day anchor. Its due time must be calculated from the single clock reading taken when seeding starts.
- [story] A back-dated raise fails disputability if its fixture transaction occurred *after* the raise or falls outside the 90-day window at that instant. Fixture choices need to satisfy the aggregate's checks.

## Simplest design
- [story] Extend the existing fixture and EF Core seeding hooks. For each missing dispute, resolve its transaction snapshot and ordered action instants, set the owning customer on the seeding context, call `Raise` and the required aggregate actions, and save through `AppDbContext`. Check existence using the transaction's unique `(AccountRef, TransactionId)` key. Reuse the existing commit mapping; do not add seed-specific event writers, an API path, or a second ownership bypass.

## Assumptions
- [decision] `Automation` / `worker:seeder` remains an unconfirmed AD-14a assumption, explicitly open in the story. Settle it before build.
- [story] The story assumes a warning lead time below eight days, but story 5.3 says that lead time is undecided and builds *after* 5.4. The “first sweep leaves their streams as seeded” assertion cannot be guaranteed until that value is fixed.
- [story] “Once per fresh database” assumes successful seeding. The current hooks run after every migrate; a failure after some saves can leave a partial seed that the next run must complete without duplicating earlier actions.

## Standards
- [decision] The PRD and story promise each event is **published once**, while AD-17 explicitly provides **at-least-once** Kafka delivery, including possible duplicates after relay handover. Decide whether to change that requirement or the delivery architecture. Under AD-17, assert one stored event and one outbox row per published action, no new rows on restart, and consumer deduplication by CloudEvent ID/version—not exactly-once Kafka arrival ([Idempotent Receiver](https://www.enterpriseintegrationpatterns.com/patterns/messaging/IdempotentReceiver.html)).
- [story] No new seeding mechanism is needed: retain EF Core’s documented [`UseSeeding` and `UseAsyncSeeding`](https://learn.microsoft.com/en-us/ef/core/modeling/data-seeding), and use the existing context-data [global query filter](https://learn.microsoft.com/en-us/ef/core/querying/filters) rather than inventing a bypass.

## Gaps
- [story] Define fixture bounds and invalid-data behavior: unique customer/transaction references, eligible settled card debit, valid reason and outcome, note and amount limits, and strictly ordered action instants. An invalid reference or refused aggregate action must fail seeding visibly, not be skipped.
- [story] Criterion 4 conflates “each action has a stored event and, where published, an outbox row” with “each action commits separately.” Specify the required row counts and atomicity; separate saves are unnecessary.
- [story] Test the SLA demo with a fixed clock, including its creation and due instants. The “about 5 minutes later” supervisor check alone cannot establish the boundary, and an asynchronous sweep need not run at the exact due instant.
