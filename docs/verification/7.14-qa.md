### F1 (fail): customer data stays reachable in the JavaScript heap after the clean-up

Method: before the sign-out, three transaction IDs from the first page each appear once in a heap snapshot of tab 1; after the
clean-up (tab 1 on the start page, DOM clean) they still appear once, with their neighbouring strings (date, merchant, masked card).
A snapshot taken after `collectGarbage` holds only reachable objects. Retaining path of the strings (from the heap snapshot,
names only): `(GC roots)` → `Window` → `DOMTimer` → `ScheduledAction` → a closure → its context `this` (a TanStack Query object whose
`options` holds `getNextPageParam`) → the closure's scope → an array of the page's rows. So a pending timer holds a query (a query the
transactions screen's still-mounted observer re-created after `removeQueries`, see F2) whose options closure holds the old rows.

Timing over one run, two scenarios in parallel (A: sign-out in another tab, B: 401 in the same tab), same strings counted each time:

| Time after the clean-up | A | B |
|---|---|---|
| 2 s, 60 s, 4 min | still present | still present |
| 5 min 30 s | gone | still present |

Reading: A is released at the default `gcTime` of 5 minutes (TanStack Query's default; the SPA sets none). B was still present at
5 min 30 s; whether it clears later was not measured. Impact: the story's aim is that the tab's memory holds no customer data once the
session ends (ASVS 5.0.0 V14.3.1; criterion 1 "removes every query"). The DOM, the query cache and the mutation cache are clean, but a
heap dump or a debugger on an unattended machine still shows the first page of transactions for at least 5 minutes. The data is the
customer's own, the demo data is synthetic. Suggested direction for the builder (not verified): stop the observer re-creating the query
(unmount or unsubscribe the screens before `removeQueries`, or call `queryClient.clear()` after navigating), then re-run the heap check
above. A Vitest test cannot see this; the check needs a browser heap snapshot.

### F2 (low, criterion 4 literal): the receiving tab starts and aborts a request

Criterion 4: the tab shows the start page after `signed-out` "initiating no new request". Observed in tab 1 when tab 2 signed out: one
`GET /api/v1/transactions` is sent about 108 ms after the click (tab 2's logout POST goes out at about 102 ms), and tab 1 aborts it 1 ms
later (`net::ERR_ABORTED`; the gateway logs it as 499). The same happens on the 401 path: the originating tab sends and aborts
`GET /api/v1/transactions`, and the receiving tab `GET /api/v1/disputes`. No answer is received or stored (nothing restored; the DOM is
clean), but the request reaches the gateway while the server session may still be live. The new spec asserts "no answer arrives", which
is what holds today; if the builder removes the request it can assert "no request at all".
