## 1. Pre-mortem

- [story] The database-init tests pass without exercising the real database path. The current harness stubs `docker compose` but passes `docker run` through to a real PostgreSQL 18 container; a generic Docker stub would lose the TLS and role checks.
- [story] CI becomes unreliable after the three harnesses join the infra test step. The current database harness uses a Docker network and ordered first/later deploys, while the platform job has a 15-minute limit that already includes the gateway tests.

## 2. Simplest design

- [story] Use 8.7’s process helper and one temporary PATH directory. Run each deploy case against a fresh copy; for database cases, let only `docker run` reach the real Docker daemon. Keep first/later database checks in one ordered test or give each test its own setup. Parse Compose JSON with `System.Text.Json`; retain only the source checks that a rendered model cannot establish. No general command-mocking framework or second Compose parser is needed.

## 3. Assumptions

- [story] **8.7 is merged first.** The current infra test project has no process helper; the story’s `after: [1, 7]` is essential, not merely scheduling.
- [story] **The Docker tests can share the CI job safely.** `rds-init.test.sh` currently documents the `stack` lock, but the proposed `dotnet test` command has no lock or isolation rule.
- [story] **Rendered values prove required inputs.** They do not: replacing `${VAR:?…}` with a literal can leave the rendered value unchanged and make an input optional.

## 4. Standards

- [story] No new production mechanism is implied. Keep process execution on [`.NET ProcessStartInfo`](https://learn.microsoft.com/dotnet/api/system.diagnostics.processstartinfo.environment), test lifetime on [xUnit shared context](https://xunit.net/docs/shared-context), and merged-model assertions on [Compose `config --format json`](https://docs.docker.com/reference/cli/docker/compose/config/). A PATH stub is a test double, not a reason to invent a process framework.

## 5. Gaps

- [story] Criterion 4 says to retain `check-compose.sh`’s cases but asks for assertions only on the rendered model. That cannot prove its existing **exact input/reference sets** or that every reference uses `:?`; explicitly retain focused source-contract checks and missing-input renders.
- [story] Criterion 5 says “each bound’s edge” without defining edges for bounds with no finite upper limit, such as paths and the decoded HMAC key. Name the cases per input, including forbidden characters and the deploy-only `QA_DB_PASSWORD` and `RDS_MASTER_PASSWORD`, so “tested once” is measurable.
- [story] Criterion 1 does not say whether unexpected stub calls fail. Require them to fail visibly; otherwise a changed deploy command can receive a success-shaped response and escape the tests.
- [story] The boundaries forbid changing `deploy.sh` and `input-bounds.sh`, yet both contain comments naming the deleted harnesses. Permit comment-only reference updates, or explicitly record that documentation debt for the follow-on tooling fix.
