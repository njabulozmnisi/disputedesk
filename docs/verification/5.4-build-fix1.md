### Item 4: what EF Core 10's Migrator does
- **With migrations pending, the seed runs outside the lock and outside any transaction.**
  - `MigrateImplementationAsync` calls the seed delegate after the migration commands and before its own commit and lock dispose (Migrator.cs, lines 281-357).
  - But the command executor commits after each migration's commands (`commitTransaction: useTransaction`) and sets the transaction to null (MigrationCommandExecutor.cs, lines 264-270). After the last migration it starts no new transaction.
  - Npgsql's lock is `LOCK TABLE ... IN ACCESS EXCLUSIVE MODE` with `LockReleaseBehavior.Transaction`, and its lock object's `Dispose` does nothing. So the commit has already released the lock before the seed runs.
- **With no migration pending, the seed runs inside the migration transaction**, which holds the `LOCK TABLE`.
- **Sources:**
  - https://github.com/dotnet/efcore/blob/release/10.0/src/EFCore.Relational/Migrations/Internal/Migrator.cs
  - https://github.com/dotnet/efcore/blob/release/10.0/src/EFCore.Relational/Migrations/Internal/MigrationCommandExecutor.cs
  - https://github.com/npgsql/efcore.pg/blob/v10.0.3/src/EFCore.PG/Migrations/Internal/NpgsqlHistoryRepository.cs
  - The EF files are byte-identical at tag `v10.0.14`, the installed version. The Npgsql file is the same at `v10.0.3`, the installed version, and at `hotfix/10.0.4`.
- **Change:** only the comment. The `Seeder` summary now says idempotency on that path rests on the unique `(AccountRef, TransactionId)` index, one `SaveChanges` per stream, and the migrator's retry. AD-30 still needs the supervisor's correction.
