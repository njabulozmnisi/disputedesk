## Mechanisms checked (GitHub Docs fetched 2026-11-05; read-only GitHub API; no AWS command)

- **Environment subject.** *OpenID Connect reference*, "Filtering for a specific environment": the subject includes the environment name when the job references an environment (`repo:ORG/REPO:environment:NAME`); the `ref:` form is used "only if the job doesn't reference an environment". The `pull_request` form likewise applies only without an environment. "Immutable subject claims": `owner_id` and `repo_id` are always in the `repo` segment. The docs show the immutable form only with `ref:`, so `repo:<owner>@<owner-id>/<name>@<repo-id>:environment:dev` is the documented composition, not a quoted example. The first deploy proves it (the offline limit, accepted). Any `:` in a value becomes `%3A`.
- **Reusable workflows.** *Using OpenID Connect with reusable workflows*: a called job's token carries the caller's standard claims, with `job_workflow_ref` naming the called file. The example `sub` is `repo:octo-org/octo-repo:environment:prod`. *Reuse workflows*: "The job that calls the reusable workflow can't use the `environment` keyword." *Reusing workflow configurations*: a calling job takes only `name`, `uses`, `with`, `secrets`, `strategy`, `needs`, `if`, `concurrency`, `permissions` and `cache-mode`, so it has no `steps` (Sofia's two-job note is right). Permissions "can be only downgraded (not elevated) by the called workflow". The `github` context "is always associated with the caller workflow", so `github.ref` is `refs/heads/main` and `github.event_name` is `push` on the call path.
- **Environments.** *Deployments and environments*: a custom branch or tag rule "is matched against the `GITHUB_REF` of the workflow run". A `pull_request` run's `refs/pull/N/merge` needs its own rule to deploy, so `main` alone excludes pull requests, fork branches named `main` included. *Workflow syntax*, `jobs.<job_id>.environment`: "All deployment protection rules must pass before a job referencing the environment is sent to a runner." *Managing environments for deployment*: "Running a workflow that references an environment that does not exist will create an environment with the referenced name … the newly created environment will not have any protection rules." The same page gives the naming rules: names "are not case sensitive", "may not exceed 255 characters and must be unique". REST *Deployment environments*: `PUT …/environments/{environment_name}` with `deployment_branch_policy {protected_branches, custom_branch_policies}`, exactly one of them true; names are URL-encoded, and slashes are allowed. REST *Deployment branch policies*: `POST …/deployment-branch-policies` with `name` and `type` (`branch` or `tag`).
- **Expressions and contexts.** *Expressions*: "GitHub ignores case when comparing strings". *Contexts*: an unset variable reads as an empty string. `jobs.<job_id>.if` may use `github, needs, vars, inputs`, and `jobs.<job_id>.with.<with_id>` may use `github, needs, strategy, matrix, inputs, vars`. A job whose `needs` were skipped is skipped under the implicit `success()`.
- **Concurrency.** *Control workflow concurrency*: one running job and, by default (`queue: single`), one pending job per group, with a newer pending job replacing an older one. `queue: max` (up to 100 pending, in order) is now documented. The caller and the called job may not share a group with `cancel-in-progress: true`; with `false` and no group on the caller, the story is clear of that rule.
- **AWS.** IAM User Guide, *Create a role for OpenID Connect federation*, "Configuring a role for GitHub OIDC identity provider". If environments are used in workflows or OIDC policies, it "strongly recommend[s]" protection rules that restrict which branches and tags can deploy. IAM requires a `sub` condition that is not solely a wildcard. GitHub's *Configuring OpenID Connect in Amazon Web Services* gives the same advice.
- **actionlint 1.7.12** (the `floor-guard` pin), on a scratch sketch outside the repo:
  - A workflow with both `workflow_call` and `workflow_dispatch` defining `sha` lints clean. So do `environment` and `concurrency` on the called job, and a calling job with `needs`, `if: vars…`, `permissions` and `with` from `needs.publish.outputs.core-banking`.
  - It reports `needs.publish.outputs.apii` (`property "apii" is not defined`), so supervisor check 3 works.
  - It reports a missing required `with` input (`input "core-banking" is required`).
  - It rejects `queue: max` (`unexpected key "queue" for "concurrency" section`).
- **The live repository** (`gh api`, GET only): public and user-owned. It has no environments yet. `actions/oidc/customization/sub` returns `use_default: true`, `use_immutable_subject: true` and `sub_claim_prefix: repo:njabulozmnisi@4159607/disputedesk@1429584825`, which matches the subject shape the story pins. No workflow uses `pull_request_target` or `workflow_run`, and none references an environment today.

## Security checklist (security-story), applied to the design

- **AuthN/Z (who can assume the role).** Only a job that names `dev` gets the `environment:dev` subject (*OIDC reference*), and `dev`'s branch rule is matched against `GITHUB_REF` before the job reaches a runner. That leaves out pushes to other branches, `pull_request` runs (`refs/pull/N/merge`), fork branches named `main` and tags (`type: branch`). This is narrower than today: any job on `main` that asked for `id-token: write` can mint today's `ref:refs/heads/main` subject, while the new one also has to name `dev`.
  - What still matches: a job in any workflow file on `main` that names `dev`. Events whose `GITHUB_REF` is the default branch (`schedule`, `pull_request_target`, `workflow_run`) run `main`'s own file. None of the three workflows uses the last two.
  - P55's `job_workflow_ref` customisation remains the production step, and its text changes as Build facts say. Other public repositories may call a public reusable workflow, but the token then carries their repository, so the subject never matches.
  - The audience stays exact (`sts.amazonaws.com`).
- **Input validation.** The SHA and image references reach scripts only through `env` (criterion 2). Three layers bound them: the workflow's shape check (P1, P2), the SSM document's `allowedPattern`, and `deploy.sh`'s `within_bounds`. On the call path, inputs come from this repository's own `publish` job, not from a person.
- **Secrets and data.** No secret, token or personal data in outputs, notices or logs; the image references are public. No long-lived key (NFR-INFRA-4).
- **Supply chain.** No new package or action. `configure-aws-credentials` stays pinned by SHA (`e1253824…`, v6.3.0). Infra files change, so the builder runs `scripts/security-local.sh` (pitfall 7.5).
- **Headers.** Not touched.
- **Standards.** GitHub OIDC with environment protection rules, and the AWS IAM web-identity trust (sources above). OWASP Top 10 CI/CD Security Risks: CICD-SEC-1 (flow control: `dev` limited to `main`, the switch) and CICD-SEC-5 (pipeline-based access control: the credential scoped to one environment). No home-grown mechanism.
