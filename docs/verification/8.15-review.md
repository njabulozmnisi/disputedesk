## Pass 1: correctness

**Criterion 1** ("it queries the migrating context with `IgnoreQueryFilters(["Ownership"])`, matching the dispute's customer ID as well as its `accountRef` and `transactionId` ... so the bypass never widens the match"). Met. `Seeder.cs:60` and `:104` query `db.Set<Dispute>().IgnoreQueryFilters([AppDbContext.OwnershipFilter])` (the constant is `"Ownership"`, `AppDbContext.cs:23`) with `SeedDispute.Matches()`, which now adds `dispute.CustomerId == customerId` (`SeedDispute.cs:56-59`). It raises only what it does not find and saves once per stream (`:66-67`, `:110-111`). The writes run on the context EF Core passes to the seeding delegate, so they use its connection and, when no migration was pending, its transaction; EF Core makes each `SaveChanges` inside that transaction a savepoint. The class comment `Seeder.cs:19-22` gives the qualified wording the criterion asks for. The new test `SeederOwnershipTests` covers both `SeedAsync` and `Seed`, a theory over `synchronous`. It runs on its own database (`CreateMigratedDatabaseAsync`), as the pitfall on bulk updates requires, because it uses `ExecuteUpdateAsync`. It expects `UniqueViolationException` with `DisputeErrors.AlreadyDisputed`, and it fails without the predicate (run above).

**Criterion 2** ("`ContextFor` and every use of it are deleted, in `SeedAsync` and in `Seed`; the seeder constructs no `AppDbContext` and no `CurrentCustomer`"). Met. `ContextFor` and both call sites are gone, as are the `using`s it needed. Searching `backend/src` finds no `ContextFor` and no `new AppDbContext` / `new CurrentCustomer` in `Seeding/`. The builder added `SeedingSource_ConstructsNoAppDbContextAndNoCurrentCustomer` so the deletion has a test to fail. Its gap is L3.

**Criterion 3** ("the allowed places are exactly the folders `DisputeDesk.Application/Operations/` and `DisputeDesk.Worker/Sla/` and the one file `DisputeDesk.Infrastructure/Seeding/Seeder.cs`; the test is renamed for the three places and fails on a bypass anywhere else, another file in `Seeding/` included; the parameterless-bypass ban is unchanged; ... the customer-feature namespace rule also refuses a reference to `DisputeDesk.Infrastructure.Seeding` ... with a sample-line case for it"). Met. `IsInBypassPlace` (`OwnershipRulesTests.cs:170-174`) allows the two folders plus an exact match on `SeederFile`, not the `Seeding/` folder. The new sample-path cases cover `Seeding/Seeder.cs` true, `Seeding/SeedDispute.cs` false, `Linking/` false and `Application/Seeding/Seeder.cs` false. Both supervisor-check breaks fail. `BypassNamespaces` adds `{project}.Seeding`, which includes `DisputeDesk.Infrastructure.Seeding` and `Infrastructure.Seeding`. `BypassNamespaceReferences_SampleLine_...` proves it on a `using`, a short form and a fully qualified member access, with `Vendor.Infrastructure.Seeding` and `...Persistence` as negatives. `ProductionSource_ParameterlessIgnoreQueryFilters_IsAbsent` is unchanged.

**No weakened test in `OwnershipRulesTests`.** Every removed line is a rename with its replacement, or a helper that now takes a `SyntaxNode` root instead of a file path (so sample lines can be parsed). No `InlineData` case was dropped, no assertion was loosened, and `ProductionSource_NamedIgnoreQueryFilters_IsFoundInOperations` and `ProductionSource_OperationsNamespace_IsFoundInTheOperationsEndpoints` still prove that the scans read real calls.

**Criterion 4** ("they pass unchanged ... criterion 1's new test is the only addition"). Met. `SeededDisputesTests`, `SeedFixtureTests`, `InvalidFixtureDisputesTests` and `SeededLinksTests` are untouched and pass. `SeederOwnershipTests` is the only new seeding test. The extra architecture test (criterion 2's guard) sits outside the seeding tests the criterion lists.

**Order (Boundary "the order of seeding inside the migration transaction").** The seeder now walks `planned` in file order instead of `GroupBy` customer. For the unchanged fixture (`A x7, B`) the order is identical, and links still go before disputes. No finding.

**UseAsyncSeeding contract** (Microsoft Learn, Data Seeding): "always implement UseSeeding even if your application normally uses asynchronous APIs", and the code inside them "is protected by the migration locking mechanism". Both delegates stay registered unchanged (`SeedRegistration.cs:20-26`), both paths stay in step, and both seed through the context EF Core passes in. That is now closer to the documented sample than the per-customer context was.

**Commit path (AD-14).** Writes go through `AppDbContext.SaveChanges[Async]` (`AddRowsForDisputeChanges`), the same path the deleted per-customer `AppDbContext` used. Disputes already saved stay tracked as Unchanged with no pending events, so the "added or modified with none pending" guard does not trip. On a failure, `ChangeTracker.Clear()` runs and the exception propagates to the migrator, as it did before.

Not applicable: Location headers, ProblemDetails mapping, AD-15 reload (no endpoint, no update). There are no timestamp assertions in the new test, and no null-forgiving `!` in production code.

## Pass 2: simplicity

The diff is smaller than what it replaces: one loop per path instead of a grouped double loop and a context factory. The new code is plain and readable on first sight. The one helper with more cleverness than the rest is `CreatedTypeName` (resolving a target-typed `new()` through its variable declaration), and its gap is L3.
