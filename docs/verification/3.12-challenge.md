VERDICT: SIMPLIFY

## Pre-mortem
- [story] A status change during withdrawal leaves the dialog stranded: criterion 6 keeps it open on a 409 but also invalidates the detail query; the refetch can remove the open-only Withdraw button that owns the dialog.
- [story] A customer presses Escape while a withdrawal is pending. A later network failure cannot leave the dialog open with its note retained, as criterion 6 promises.
- [story] A 200 succeeds, but a failed detail refetch leaves the old open status on screen. Story 3.4 already returns the updated `DisputeResponse` in the 200 body.

## Simplest design
- [story] Parse the route ID before querying; render the generated detail query with existing badge, reason, masking and problem components. Keep the dialog mounted independently of the conditional Withdraw button, use the generated mutation, put its 200 response in the detail cache, and invalidate related queries. Refetch the detail for a 409 reporting `withdrawn`. No new status mapper, client, toast system or persistence layer is needed.

## Assumptions
- [story] The dialog can remain usable after the detail changes status. Evidence against it: criterion 4 renders its trigger only for open statuses, while criterion 6 requires both an open dialog and detail invalidation on a closed-status 409. Specify the component ownership and focus behavior.
- [story] All successful withdrawals can be displayed from a refetch. Evidence against relying on that: story 3.4 guarantees a 200 body equal to the subsequent GET, while a subsequent GET can fail.

## Standards
- [story] No invented transport or routing mechanism is needed: the specified [TanStack Router path parsing](https://tanstack.com/router/latest/docs/framework/react/guide/path-params) and [TanStack Query invalidation](https://tanstack.com/query/latest/docs/framework/react/guides/query-invalidation) are documented approaches. For the irreversible-action dialog, specify initial focus on **Keep dispute**, the least destructive action, following the [WAI-ARIA modal dialog guidance](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/); “focus moves into it” is insufficient.

## Gaps
- [story] Define whether Escape and “Keep dispute” are available while the mutation is pending. Otherwise the pending and failure criteria contradict each other; test Escape during a delayed request.
- [story] Define what happens when a non-`withdrawn` 409 refetch removes the Withdraw control, and test that the notice remains readable and closing the dialog puts focus on an existing element.
- [story] Test an unknown `reason` in the detail response. Inputs say out-of-contract enum values show no label, but criterion 3 tests unknown timeline/status values without covering the summary’s reason lookup.
- [story] Make the 200-body cache update and its failure fallback explicit, then test a successful POST followed by a failed GET: the screen must still show Withdrawn and must not offer Withdraw.

## Resolution

Product owner refine, 2026-10-30. Every point was `[story]`; all are folded into the story, no `[decision]` raised.

- Dialog stranded by a 409 refetch: the detail screen owns the dialog's `open` state, so it stays mounted when the refetch removes the Withdraw button (criterion 4); a supervisor break proves it (criterion 6's `resolved` notice).
- Escape during a pending withdraw: while pending, Escape does nothing (`onEscapeKeyDown` with `preventDefault`) and "Keep dispute" is `aria-disabled`; tested with a delayed response (criterion 4).
- 200 with a failed refetch: the 200 body is written into the detail cache with `setQueryData`; only the list and transactions are invalidated; a test answers the detail GET with 500 after the POST and still sees "Withdrawn", no button, focus on the `h1` (criterion 6). The 409-`withdrawn` path awaits the detail refetch before closing, and a failed refetch shows the problem notice because the query error is checked before its data (criterion 2).
- Initial focus: "Keep dispute", Radix `AlertDialog`'s default, per the WAI-ARIA APG modal dialog guidance for irreversible actions (criterion 4; `dispute-withdraw.html` note changed to match). This overrides the pre-build review's suggestion of the note.
- Non-`withdrawn` 409 after the refetch: the notice stays readable and a later close puts focus on "Withdraw dispute" if shown, else the `h1` (criterion 6).
- Unknown `reason`: renders no label, tested (criterion 2).
