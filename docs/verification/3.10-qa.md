## What the API can produce

Only `submitted` is reachable through the real API today (there is no withdraw endpoint and the operations actions are not built; `openapi.json` has only `POST /disputes` and `GET /disputes/{id}`). So the other four statuses, the out-of-contract `escalated` and the half-set pair are shown by editing the transactions response in the browser (`route.fetch`, then `route.fulfill`), over the real SPA, row layout and badge. That part is stubbed and the spec says so.

## Standards

- WCAG 2.2 SC 2.5.3 Label in Name: the name "Dispute status: {label}" contains the visible label; the prefix is visually hidden text.
- RFC 3986 section 2.1: the href percent-encodes `/`, `?` and `#`.
- RFC 9110 / RFC 9111: the list stays `Cache-Control: no-store` (checked by `spa-transactions.spec.ts`).

## Findings

- F1 (low, flake, not 3.10): `e2e/tests/dispute-detail.spec.ts:91` expects the new dispute's outbox row to be `Pending` right after the raise; the story 4.1 relay can already have sent it (`Received: ...raised.v1:Sent`), so the test races the relay. It failed once in the full run and passed on the re-run. 3.10 changes no backend. The test should accept `Pending` or `Sent`, or read the row before the relay can run; the e2e owner (QA) can make that change in its own pass.
- Data note: the e2e data is not reset between runs; each run of the new spec's first test raises one dispute, and `dispute-raise.spec.ts` needs about three disputable transactions per run. The spec skips with a message if none is left, and `down -v` restores them.
