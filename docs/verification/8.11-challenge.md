## Pre-mortem
- [story] A future enum query or header parameter accepts an unintended spelling: `DisputeDeskJson.Apply` configures JSON serialization, not minimal API query/header binding. The story promises coverage of all three input sources but tests only JSON bodies.
- [story] An undefined enum is written as a numeric-looking string. The proposed shared `CamelCaseNameOnlyEnumConverter<TEnum>.Write` uses `value.ToString()`, whereas the current shared converter delegates writing to `JsonStringEnumConverter` with integer values disabled.

## Simplest design
- [story] Use the existing exact-name converter behind one documented `JsonConverterFactory` in `DisputeDeskJson.Apply`; remove the property attribute and old factory. Preserve the current writer’s rejection of undefined values, and test the HTTP and shared options against the same valid and invalid names. Do not add a second validation layer or change `EnumSchemaTransformer`.

## Assumptions
- [story] “Every client already sends exact names” is supported for generated SPA types and the cited e2e requests, but does not establish what other deployed callers send. Treat rejection of their former PascalCase values as the acknowledged breaking change.
- [story] The story assumes an OpenAPI diff will display the new reading rule. The existing `Reason` schema already lists camelCase values; regenerating an unchanged document cannot demonstrate that casing is now rejected.

## Standards
- [story] A JSON converter factory is the documented approach for this JSON rule: [System.Text.Json custom converters](https://learn.microsoft.com/dotnet/standard/serialization/system-text-json/converters-how-to). It is **not** the framework mechanism for query/header binding; scope the criterion to JSON bodies, or separately specify and test the documented [minimal API parameter-binding mechanism](https://learn.microsoft.com/aspnet/core/fundamentals/minimal-apis/parameter-binding).

## Gaps
- [story] The inputs clause says required `null` receives a fieldless binding error. Existing tests show `reason: null` and `outcome: null` are *well-formed bodies* that receive field-named validation errors. Separate null/missing-property validation from invalid enum-string binding.
- [story] Criterion 3 requires no dispute, stored event, outbox row **or idempotency record**, but the cited binding test checks only key rows; make the persistence assertion cover the named rows. Also retain a positive `"wrongAmount"` raise test when replacing the existing two-case success test.
- [story] Criterion 6 says “any difference” in regenerated OpenAPI is reviewed, but gives no required observable contract result if there is no difference. Require an explicit recorded no-diff result rather than treating drift-check success as evidence that the behavioral change appears in the document.
