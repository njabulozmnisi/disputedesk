**Why item 6 is blocked.** A numeric code, malformed JSON and an empty body fail before minimal API validation and endpoint filters run. So there is no `errors` object that could name `code`. Microsoft Learn says so ("Endpoint filters don't run for body-reading failures"), and I checked it: all six unbindable bodies return `{"type":".../validation.md","title":"Bad Request","status":400,"traceId":...}` with no `errors`. AC5 asks for both "naming only `code`" and the built-in `AddValidation` mechanism, and the two can't both hold here. The ways out:
- **(a)** Read the verify body by hand (`HttpRequest.ReadFromJsonAsync`, DataAnnotations `Validator.TryValidateObject`, a 415 check, `.Accepts<VerifyOtpRequest>`). This replaces the built-in binding and validation on this route and duplicates the `[RegularExpression]` check.
- **(b)** Turn on `ThrowOnBadRequest` globally with an `IExceptionHandler`. That changes a platform-wide setting, and an empty body still carries no field name.
- **(c)** Amend AC5: unbindable bodies give 400 `validation` with no `errors`, as the start route already does.

I'd go with (c). I've left `VerifyOtpInputTests.Verify_BodyThatDoesNotBind_Returns400ValidationAndCountsNothing` as it was, rather than add a test that has to fail.

**What changed**
- **Item 3 (handler).** `RefuseAsync` now takes `bool lostConsume` instead of decoding `AuditAction.Linked`. A verify that loses the consume answers as before, records `Linked` `Rejected`, and doesn't count `locked`.
- **Items 1 and 2.** A new test `GateInterceptor` holds each consume `UPDATE` until the test opens it.
  - The parallel test now waits until all three counted attempts reach the gate, checks `Attempts == 3`, then releases them, so exactly one consumes.
  - Two new tests cover a later start superseding the challenge while a correct-code verify is held: on the first attempt it answers 422 with `attemptsRemaining` 2; on the third it answers 409 with no `locked` metric.
- **Item 4.** The echo checks now parse the body, remove `traceId`, and search the decoded names and string values.
- **Item 7.** The privacy test checks both HMACs, as hex and Base64, against every log line and span. The correct code's HMAC is found in exactly one row and one column, `LinkingChallenges.OtpHmac`.
- **Item 5** was out of this round, as the list said.

**Failing first**
- **Item 3, against the as-built handler:** the third-attempt test failed every time. The parallel test failed 2 runs in 3 (`["event=completed","event=locked"]`), depending on which counted attempt wins.
- **Item 1, consume conditions dropped:** all three consume tests failed (204 instead of 422 or 409).
- **Item 2, attempt cap dropped from the count:** the parallel test failed with `Attempts` 10 instead of 3.
- **Item 7, the submitted HMAC logged:** the privacy test failed on the log check.

**Checks:** build with no warnings; full suite 1,220 passed (one run, under the lock); race tests 10 out of 10 green; `dotnet format` verify, floor-guard and the secret scan all clean. No smoke check this round, as you asked.

Its consume rolls back, so the challenge really does lock on that attempt. This is where AC7's "loser records `Linked` `Rejected`" meets AC8's "the attempt that locks is `LinkingLocked`".
