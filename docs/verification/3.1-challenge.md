VERDICT: SIMPLIFY

## 1. Pre-mortem
- A valid-looking raise fails as 404 because the story accepts 1–64-character identifiers, but `CoreBankingClient.GetTransactionAsync` rejects anything outside its 1–32-character ASCII ID pattern before making a request.
- A foreign-currency transaction produces a dispute for the wrong amount: FR-14 requires the **ZAR billed amount**, while the core-banking transaction carries an amount and currency with no stated guarantee that they are ZAR.
- A save failure returns 500 after adding the dispute to the EF context; without a test that fails during database writes, the claim that the dispute, its stored event and its outbox row commit together is not demonstrated.

## 2. Simplest design
Use the existing customer-scoped `GetTransactionAsync(customerId, accountRef, transactionId)`, check for an earlier dispute and then disputability, and let `Dispute.Raise` apply the amount and note rules. Save the dispute and its `DisputeRaised` stored event once; the specified `SaveChangesAsync` override adds the outbox row, while the named unique index handles the concurrent loser. EF Core’s [default transaction for a save](https://learn.microsoft.com/en-us/ef/core/saving/transactions#default-transaction-behavior) needs no additional transaction wrapper. Do not add a repository, separate commit coordinator, or second event-writing path.

## 3. Assumptions
- **Identifier size:** The new 64-character bound assumes the core-banking adapter can look up those IDs; its current `IdShape` accepts at most 32. Align the contract and adapter, or document why 33–64-character values are accepted but necessarily return 404.
- **Money:** The story assumes the snapshot amount is the ZAR billed amount required by FR-14. The `Transaction` record also has a `Currency` field, so that assumption needs an explicit upstream guarantee or a defined response when it is false.
- **Location:** The story acknowledges that its 201 `Location` will not resolve until 3.3. That is a deliberate temporary exception to AD-5, not a reason to add the GET to this story.

## 4. Standards
No invented mechanism is necessary. Use .NET 10 [minimal API validation](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/validation?view=aspnetcore-10.0) for body bounds, EF Core [named query filters with matching required-navigation filters](https://learn.microsoft.com/en-us/ef/core/querying/filters#query-filters-and-required-navigations) for ownership, EF Core’s default save transaction for atomicity, and the specified [CloudEvents 1.0 structured format](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/spec.md) for the outbox payload. The `SaveChangesAsync` override is the architecture’s one custom commit hook; no further coordination layer is justified.

## 5. Gaps
- `expectedAmount` is called a **decimal** in the input table, but AD-4 and FR-14 require a **decimal string** on the wire. Specify the JSON type, malformed-string behavior, and maximum magnitude representable by `numeric(19,2)`; otherwise an oversized valid decimal can reach the database and become a 500 rather than 400.
- Criterion 6 should make the rollback test fail **during database persistence after an earlier insert**, then assert the dispute, stored event and outbox tables are empty. Merely throwing after an entity is added to the context does not test rollback.
- Criterion 9 needs to account for `CurrentCustomer.CustomerId` throwing when unset: the filter must use a safe per-context value to prove that “no current customer matches nothing,” rather than evaluating that getter.

VERDICT: RETHINK

## 1. Pre-mortem
- Raises fail or use an unbounded transaction-list scan: FR-13 permits only a transaction ID in the request, but the existing `ICoreBankingClient.GetTransactionAsync` requires both `accountRef` and transaction ID. No specified source supplies the account reference.
- Parallel raises produce a 500 instead of the required 409 if the losing insert’s unique-constraint exception is not mapped by constraint name.
- A 400 masks the promised 404 if automatic request validation runs before the transaction lookup.

## 2. Simplest design
Resolve the transaction through a **customer-scoped core-banking lookup by transaction ID**; decide ownership, prior dispute, disputability, then amount rules in that order. Build the aggregate and its `DisputeRaised` stored event, let one `SaveChangesAsync` override add the outbox row, and save once. EF Core already makes a single save atomic; an additional transaction wrapper is unnecessary [Microsoft Learn](https://learn.microsoft.com/en-us/ef/core/saving/transactions#default-transaction-behavior). Use the unique index as the race backstop. Do not add a repository, state-machine library, or second commit path.

## 3. Assumptions
- **Transaction lookup:** The story assumes the existing port can retrieve the transaction from its permitted request fields; its signature requires `accountRef`. Settle whether the port and stub change, or the request contract changes.
- **Immediate resource URL:** Criterion 1 requires a `Location` pointing to a dispute GET, but assigns that GET to story 3.3. This conflicts with architecture AD-5’s rule that every `Location` points to a real GET.
- **Dispute lookup scope:** The `(AccountRef, TransactionId)` unique index assumes those two core-banking identifiers remain stable for the lifetime of a dispute. The story does not state that guarantee.

## 4. Standards
No new mechanism needs to be invented. EF Core’s documented [named query filters and matching filters on required navigations](https://learn.microsoft.com/en-us/ef/core/querying/filters) cover ownership of disputes and their stored events; its [default save transaction](https://learn.microsoft.com/en-us/ef/core/saving/transactions#default-transaction-behavior) covers atomicity. The story should explicitly require those approaches rather than bespoke filtering or transaction coordination. CloudEvents structured JSON is already specified by AD-19; no custom event envelope is needed.

## 5. Gaps
- Define the raise body and bounds for **transaction ID, reason, and expected-amount string**, including malformed decimal, negative, excessive precision, and excess magnitude. Clarify whether an unknown reason gets 400 before or after a missing transaction gets 404.
- Specify how the endpoint preserves 404-before-400 for a *bound but invalid* body; authorization-before-binding alone does not establish that order.
- Specify the successful response shape and the availability of its `Location` target in story 3.1. Criterion 3 should assert the losing request’s problem slug and that **every row count remains one**, not just the two HTTP statuses.
- Clarify whether `TraceParent` is nullable when no incoming trace exists, and whether criterion 10 adds nullable `disputeId`/`customerStatus` fields to every transaction row or fields only to disputed rows.
