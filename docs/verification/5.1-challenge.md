## Pre-mortem
- [story] The operations read works in tests but fails through Scalar: the committed `openapi.json` is generated without a Zitadel issuer, while the token URL must point to the running environment’s auth origin. Specify how the runtime document gets that URL.
- [story] Reads succeed without a durable audit entry if the response is sent before `AuditLog.Record` is saved. Require the save to succeed before returning 200.
- [story] An existing machine user keeps stale role grants: `provision.sh` ignores a 409 rather than updating an existing authorization. A fresh-install assertion alone would miss this.

## Simplest design
- [story] Add one bearer scheme and one scheme-pinned `dispute.read` policy; use the existing named ownership-filter bypass in one operations handler. Read the dispute row and its stored events in version order, map a separate operations response, save one audit row, and return it. Use the built-in OpenAPI document and operation transformers rather than a second contract generator or a custom token parser.
- [story] Keep Scalar as a viewer, not a credential service. Do not embed the operations client secret in anonymously served HTML or configuration returned to the browser.

## Assumptions
- [story] The test token’s roles represent real Zitadel machine-user tokens. `infra/smoke.sh` checks roles, but the story does not require the integration test’s claims and audience to match a provisioned token.
- [decision] The story says Scalar’s client secret is a **local** stand-in, while AD-26 enables Scalar in the AWS demo. Decide whether the AWS viewer must obtain tokens; the current documents do not say how it does so without carrying that secret outside local runs.
- [story] “No personal details beyond the snapshot” may exclude notes: stored events include customer-authored notes, and the story does not specify whether the operations timeline returns them.

## Standards
- [story] A CSP `connect-src` allowance does not itself authorize a cross-origin token request; the identity origin must also permit that browser request. More importantly, client credentials are for confidential clients, so do not treat browser-held credentials as a production mechanism ([RFC 6749 §4.4](https://www.rfc-editor.org/rfc/rfc6749#section-4.4)).
- [story] No custom authentication or OpenAPI mechanism is needed: use [ASP.NET Core scheme-specific authorization](https://learn.microsoft.com/aspnet/core/security/authorization/authorize-with-a-specific-scheme?view=aspnetcore-10.0), [JWT bearer validation](https://learn.microsoft.com/aspnet/core/security/authentication/configure-jwt-bearer-authentication?view=aspnetcore-10.0), and [OpenAPI transformers](https://learn.microsoft.com/aspnet/core/fundamentals/openapi/customize-openapi?view=aspnetcore-10.0).

## Gaps
- [story] Criterion 4 specifies an unknown ID but not a malformed `disputeId`, the operations timeline’s exact fields and order, or how an unrecognized future stored-event type is handled. Define these so the response shape is testable.
- [story] “Each read” in FR-25 includes the 404 case, whereas criterion 4 asserts an audit entry only for a successful read. Specify the audit action and result for an authenticated unknown-ID read, and test audit-save failure.
- [story] Criterion 5 says “when `provision.sh` is read,” which proves neither an existing user’s grants nor a usable client-credentials token. Test provisioning and token acquisition, including a rerun against existing authorization.
- [story] Criterion 6 tests `/scalar/` but not whether its document and assets work with the switch enabled, or whether the token flow reaches the configured auth origin. Add a browser-level check without making CSP alone the success condition.

## Resolution

Sofia, 2026-10-30. Story 5.1 is refined and split; Scalar, its switch, the security schemes and the gateway CSP are story 5.5. The `[decision]` point was settled by the human on 2026-10-30.

- `[decision]` AWS viewer and the client secret: settled. Scalar never holds or pre-fills a client secret, locally or in AWS; `scripts/operations-token.sh` runs the client-credentials grant and a person pastes the token (5.1 criterion 7, 5.5 criterion 2; AD-26 amended).
- Token URL at runtime: 5.5 criterion 3 (a runtime document transformer from `Zitadel:Issuer`, a build-time stand-in issuer).
- Audit before 200: 5.1 criterion 6 (saved before the body; an armed `FailAuditInsertInterceptor` gives 500 with no dispute data).
- Stale grants on rerun: 5.1 changes no role keys (all four exist); the new actor key is covered by the extended "is current" check (criterion 7). Changing role keys on an existing authorization stays as `provision.sh` documents it (recreate the stack).
- Simplest design: one scheme-pinned `dispute.read` policy, the named bypass in one handler, an explicit operations mapping, built-in transformers (5.1 criteria 1, 3, 4, 5; 5.5 criterion 3). Scalar is a viewer only (5.5 criterion 2).
- Test tokens against a real token: the supervisor check reads a dispute with a real token from the script; `infra/smoke.sh` already asserts the project-scoped roles claim.
- Notes in the response: decided from FR-30; every note the customer wrote is left out, the resolve note stays on its timeline entry (5.1 criteria 4 and 5, Notes).
- Browser-held credentials and CORS: moot; Scalar fetches no token, so `connect-src` is `'self'` and no cross-origin token request exists (5.5 criterion 4).
- Standards: cited in each criterion and the References.
- Gaps: malformed `disputeId`, the exact fields and order, and unknown types are fixed (5.1 criterion 4); the 404 is audited `Rejected` (criterion 6); provisioning and token acquisition (criterion 7 and the supervisor check); a browser-level Scalar check that does not rest on the CSP alone (5.5 supervisor check, a pasted token reading a dispute).
