- RFC 9110: 401 for unauthenticated (anonymous unknown route and transactions), 404 for a signed-in unknown route; no redirect on API calls.
- RFC 9457: every refusal is `application/problem+json` with the resolvable `type`, `status` and `traceId`, no exception text (`expectProblemShape`).
- RFC 9111: `Cache-Control: no-store` on the 401 and 404 bodies.
- RFC 6265bis: after sign-out `context.cookies()` is empty (session and antiforgery cleared); attributes (HttpOnly, SameSite=Strict) re-checked by the existing 2.2 spec, which passed.

- OWASP Logging Cheat Sheet: sign-in and sign-out are recorded; no token, email or password in logs or audit rows.

### Root cause of the earlier failures (E2), for stories 7.1 and 7.3

Specs that raise disputes consume seeded disputable transactions of customer A. A transaction that already has a dispute is no longer disputable, and the seed is finite (the first page of 20 held 0 disputable rows after about 13 disputes). Every suite run on the same database raises more, so repeated runs exhaust the data and two specs that assume a disputable row on page 1 fail (in a serial describe the first failure also skips the rest of the file). Fresh volumes restore the data and the suite passes.

Items for 7.1/7.3 (test-data and CI hardening):
- Specs should not depend on shared seeded rows being unused: either create their own disputable transaction (core-banking stub endpoint or seed script per run), or pick a disputable row at runtime and skip with a clear reason when none is left.
- Or give the e2e run a reset step (recreate the dev database, or a per-run seeded customer) so a rerun is repeatable without removing volumes by hand.
- Document in the e2e README that the suite is not idempotent on one database until this is done; CI is unaffected because it starts from fresh volumes.
