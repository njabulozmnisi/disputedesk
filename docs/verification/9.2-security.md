## Review

- **Trust policy.** `trust-policy.json.tftpl` is unchanged: `StringEquals` only, on `token.actions.githubusercontent.com:aud` = `sts.amazonaws.com` and `:sub` = `${subject}`, with no `StringLike`. `modules/deploy-role/main.tf` builds the subject once as `repo:<owner>@<owner-id>/<name>@<repo-id>:environment:<github_environment>`, and `envs/dev/main.tf` passes the literal `"dev"`. `deploy_role.tftest.hcl` compares the whole `Statement` for equality, with the subject `…:environment:dev`, and also asserts no `StringLike`. Any extra condition, wildcard or wider subject therefore fails the test. Ran here: 3 of 3 pass.
- **Only a `dev` job gets the subject.** The OIDC reference says the subject includes `environment:<name>` only when the job references an environment. It includes `ref:` or `pull_request` only when the job does not (GitHub, *OpenID Connect reference*, "Filtering for a specific environment", "…pull_request events", "…a specific branch").
- **The branch policy runs before the job starts.** GitHub, *Deployments and environments*: protection rules "must pass before a job referencing the environment can proceed", and the branch rule "is matched against the `GITHUB_REF` of the workflow run". The rule is of type `branch`, so only `refs/heads/main` matches it. A tag named `main` does not, and neither does a story branch.
- **`id-token: write`.** In `ci.yml`, only the caller job `deploy` (`id-token: write`, `contents: read`) and the called job in `deploy.yml` (the same two) hold it. `deploy.yml`'s workflow-level permissions are `{}`. `deploy-switched-off` has no `permissions` key, so it gets the workflow's `contents: read`. `publish` keeps `contents: read`, `packages: write`. There is no `secrets: inherit` and no secret is passed to the called workflow. `security.yml` holds no `id-token`.
- **The `main` guard.** The called job's `if: github.ref == 'refs/heads/main'` sees the caller's `github` context (`push` to `refs/heads/main`). `deploy` and `deploy-switched-off` both need `publish`, which runs only on `push` to `main`.
- **Another repository calling `deploy.yml`.** The repository is public, so other repositories can call it. Its job would then run with the caller's environment and variables and get the caller's subject, which the trust policy refuses.
- **Fork pull requests.** A fork pull request can edit the workflows in its merge commit, and two independent GitHub controls still refuse it:
  - its token's write permissions become read-only (GitHub, *Workflow syntax*, "Changing the permissions in a forked repository"; *Send write tokens* applies to private repositories only);
  - its `GITHUB_REF` is `refs/pull/<n>/merge`, which `dev`'s `main` rule does not match (*Events that trigger workflows*, `pull_request`). This holds even when the fork's head branch is named `main`.

  First-time contributors also need approval. Whether the nested `id-token: write` makes a fork pull request's run fail at creation (P13) cannot be reproduced here because no fork exists. Either way the run fails closed.
- **The call path's input bounds** (the `images` step):
  - Each input is read through `env` and matched against `^ghcr\.io/njabulozmnisi/disputedesk-<name>@sha256:[0-9a-f]{64}$`, with the name taken from the fixed list.
  - A failure prints a fixed message, never the value. Only checked values reach `GITHUB_OUTPUT` and the log.
  - I ran the extracted step as GitHub runs it (`bash --noprofile --norc -eo pipefail`) with nine inputs. The valid set passed and wrote five outputs. Each of these failed with no output written:
    - a value followed by a newline and an injected `worker=` line;
    - a trailing newline;
    - `ghcrXio`;
    - a prefixed registry;
    - `disputedesk-api-evil`;
    - a double digest;
    - a tag plus a digest.
  - An event other than `workflow_dispatch` takes the checked path. The dispatch path resolves digests from GHCR and checks the revision label, as before, and ignores the image inputs. Each path fails safe if the other is misused.
  - The SHA check covers both triggers.
- **`publish`'s outputs.** `publish` checks the same pattern on the `RepoDigests` value before writing it to `GITHUB_OUTPUT`. A tag reference fails the step.
- **Logs.** The logs print only image references, which are public digests, and fixed messages. Neither changed `run:` block uses a `${{ }}` expression. The GHCR login (stdin) and the deploy steps from *configure-aws-credentials* on are byte for byte unchanged.
- **Concurrency.** The job-level `deploy-dev` group, with `cancel-in-progress: false`, is shared by a CI deploy and a rollback dispatch. The `queue: single` limit is the marked `shortcut:` and is covered by the README's switch-off-first rollback.
- **README.** The commands in section 8 match the read-back. The environment is created before the variables, and `DEPLOY_ENABLED=true` is set only after the first deploy succeeds. The offline limit is stated. GitHub's docs show the immutable subject only in its `ref:` form, so the `…@<repo-id>:environment:dev` form rests on `use_default: true` plus the immutable prefix. It is proved only by the first deploy's `AssumeRoleWithWebIdentity`, as the README says.
