**How it works**
- **Counting.** One raw SQL statement adds the attempt to the login's current challenge and returns the row in the same step.
- **Comparing.** The code's HMAC is always computed and compared with `FixedTimeEquals`, against a 32-byte dummy when no OTP was sent.
- **Linking.** A correct code consumes the challenge, inserts the link and records `Linked` in one explicit transaction. The session and its key are not touched.
- **Race losers.** A link that loses on either `UQ_CustomerLinks_*` index rolls back and answers as a counted wrong code.

**Where the code sits differs from the story's Touches list.** The story puts the handler in `Application/Linking/VerifyOtp/`, but Application can't reach `CustomerLink` or run raw SQL. So the handler sits in `Infrastructure/Linking/VerifyOtpHandler.cs`, beside 6.1's job class. Application gets the comparison (`Otp.Matches`), the errors and the attempt limit; Domain gets a `BusinessRule` overload that carries extensions such as `attemptsRemaining`.

**The raw SQL** (`OtpAttempts.CountAttemptAsync`, run through `Database.SqlQuery<CountedAttempt>`):
```sql
UPDATE "LinkingChallenges"
SET "Attempts" = "Attempts" + 1
WHERE "LoginSub" = @p0
  AND "SupersededAtUtc" IS NULL
  AND "ConsumedAtUtc" IS NULL
  AND "Attempts" < @p1          -- @p1 = LinkingChallenge.MaxAttempts (3)
RETURNING "Id", "CustomerId", "OtpHmac", "ExpiresAtUtc", "Attempts"
```
The query builder can't express this: `ExecuteUpdate` returns only a row count, and reading the row before writing would let parallel attempts all get past the limit. `UPDATE … RETURNING` does both under the row lock. The limit is a parameter tied to the constant rather than a literal `3`. Supervisor break 2 still applies: delete the `"Attempts" < …` line.
