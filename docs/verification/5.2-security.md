### 1. Resolve accepts any content type at routing (builder's open question): safe, keep it
- **Without the change:** when the body is not JSON, routing picks a framework-made 415 endpoint that carries no policy. The cookie-only fallback policy then answers it, so a bearer caller gets a cookie 401 with no `WWW-Authenticate: Bearer`.
- **With the change:** `OperationsEndpoints.cs` adds `.WithMetadata(new AcceptsMetadata([], typeof(ResolveDisputeRequest)))`. Routing now always reaches the real resolve endpoint, which runs its own JwtBearer policy first.
- **Nothing is loosened.** The endpoint's JSON body binding still checks the content type, so a `text/plain` body still gets 415 (`Resolve_TextPlainBody_Returns415ValidationAndWritesNoRow` uses a valid resolve token). The only change is that 401 and 403 now come before 415, which matches deny-by-default (ASVS 5.0 V8.2.1).
- **CSRF stays irrelevant.** The policy is bearer-only, and the body must still be JSON.
- **`openapi.json` is unchanged.** I checked: resolve's request body is still `application/json` and required.
- **If a future framework version changes this,** the result is the old cookie 401, which still fails closed. `Resolve_TextPlainBodyWithNoTokenOrARefusedToken_Returns401BearerOr403Before415` checks for the Bearer challenge, so it would catch that.
- **Standards.** `AcceptsMetadata` is a public, documented type, but using an empty content-type list to step around routing's 415 is not a documented pattern. I could not confirm that behaviour against Microsoft Learn or the framework source in this session; the builder's tests are the evidence. That is a low standards note, not a security weakness.
- **The alternative is worse.** Letting the fallback policy accept bearer tokens would let any validly signed token for the project satisfy deny-by-default on every endpoint that names no policy. That weakens AD-8 and AD-10. Keep it rejected.

### 2. Wrong HTTP method (405) on operations paths: not a security issue (low, interop)
- **What happens.** A wrong method gets a framework-made 405 endpoint that has no policy, as does an unmatched path under `/api/v1/operations`. The cookie-only fallback answers it:
  - anonymous and bearer callers get 401 with no Bearer challenge (RFC 6750 §3);
  - a signed-in customer gets 405 with `Allow`.
- **Why it is safe.** No handler runs, nothing is read or changed, and no audit row is written. The route list is already public at `/openapi/v1.json`, so a customer learns nothing new.
- **Recommendation.** Add a line to `docs/production-path.md` or a later story rather than a fix here. Optionally add a test that a wrong method on each operations route never succeeds and writes no row.
