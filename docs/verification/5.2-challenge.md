## Pre-mortem
- [story] Resolve sometimes returns 400 for an unknown dispute instead of the required 404. `.DisableValidation()` disables validation, not JSON body binding; a malformed body can fail before the handler loads the dispute. This breaks criterion 3 and AD-8’s promised check order.
- [story] A version clash is treated as an ordinary EF concurrency exception, or the retry reuses stale state. This codebase detects the clash through the **stored-event unique index** and `UniqueViolationException`; EF documents that an insert’s unique-constraint failure is not `DbUpdateConcurrencyException`.

## Simplest design
- [story] Put the three status rules in `Dispute` and use one plain handler pattern per action: load and replay the operations-visible stream, validate the request, apply the action, save through the existing commit path, and on the **named version clash only** reload and decide once more. Reuse the existing outbox mapping and customer timeline mapping. No state-machine library, second concurrency token, new event mapper, or general-purpose retry framework is needed.
- [story] For resolve, read and deserialize the body **after** the dispute lookup if 404 must beat even malformed JSON. A typed body parameter cannot provide that ordering.

## Assumptions
- [story] Criterion 4’s “two resolves” race starts **Under review or Escalated**; from Submitted, FR-24 rejects both before either commits. Name the starting status in the test.
- [story] `sla_escalated` means an earlier `DisputeEscalated` stored event whose actor type is `Automation`, not merely a dispute that reached Escalated. Manual escalation uses the same event type, so the latest status cannot distinguish them.

## Standards
- [decision] AD-8 presents `.DisableValidation()` plus handler-side validation as the way to guarantee 404 before 400 for resolve. That does not cover malformed-body binding. Amend that mechanism to use handler-side body reading after lookup, following [Minimal API parameter binding](https://learn.microsoft.com/aspnet/core/fundamentals/minimal-apis/parameter-binding?view=aspnetcore-10.0) and [validation](https://learn.microsoft.com/aspnet/core/fundamentals/validation?view=aspnetcore-10.0); test malformed JSON against an unknown valid dispute ID.
- [story] Keep the existing named-constraint handling, not a catch-all concurrency retry. [EF Core’s concurrency guidance](https://learn.microsoft.com/en-us/ef/core/saving/concurrency) explicitly distinguishes unique violations on inserts from `DbUpdateConcurrencyException`.

## Gaps
- [story] Criterion 5 requires `Details.outcome`, but `AuditLogEntry`, `AuditLog.Record` and its EF configuration have **no `Details` field**. Specify the schema change and migration, plus the exact cases that include the outcome. A 403 result handler runs before body binding and should not inspect the resolve body to obtain it.
- [story] Specify invalid outcome values—including numeric enum values—and missing, malformed and oversized resolve bodies. The stated 1–500-character bound covers only the trimmed note; without these cases, the 400-before-409 and 404-before-400 requirements are not fully testable.
- [story] Criterion 7 should say whether counters increment **only after commit**, and test a failed save and a clash followed by a successful retry. Otherwise one customer-visible action can be counted twice.

## Human decision (2026-10-30)

The `[decision]` point on AD-8: binding failures (malformed JSON, wrong JSON types, a non-JSON body) answer the framework's 400 before the lookup; only a well-formed body is checked after the 404, as story 3.4 settled for withdraw. AD-8 is amended to say so; no custom body reading.
