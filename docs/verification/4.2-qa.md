## Warnings during a 30 s outage

Window 06:32:39.961Z to 06:33:11.355Z (31.4 s, Redpanda stopped so its DNS name stops resolving). Same count in three
runs: **67 warnings** (129 log entries in the window).

| Count | Message |
|---|---|
| 62 | `Outbox relay cannot reach kafka (Local_Resolve)` |
| 3 | `Outbox relay cannot reach kafka (Local_AllBrokersDown)` |
| 2 | `Outbox relay could not send an event (Local_MsgTimedOut); it stays Pending and is retried` |

The remaining entries are `fail`-level lines `Kafka client log line (FAIL)` (librdkafka's FAIL facility mapped to error level,
see O1). Every warning matches one of three fixed templates holding only a dependency name, an error code or a facility: no
dispute ID, connection string, broker address, exception or record value. The paused-broker code of criterion 1 was not exercised
here (`stop` rather than `PauseAsync`); on the stack the codes are `Local_Resolve`, `Local_AllBrokersDown` and `Local_MsgTimedOut`.

## Privacy (R31, NFR-SEC-5, POPIA)

- Worker log for the outage, the shutdown and the restart: none of the customer ID, actor ID, account reference, transaction ID,
  description or note of any raised dispute, no dispute ID in the outage window, no `Password=`, `Host=`, broker address or
  `Exception` text.
- Aspire dashboard: the trace of each outage raise (API span plus the Worker's producer spans), `/traces` and `/structuredlogs`
  page text hold none of those values. Failed sends show as spans with `Status = Error`; the first raise of the outage has three
  producer spans (10 s, 10 s, then the successful one after recovery).
- Topic records hold only `disputeId`, `disputeVersion`, `occurredAt`, `reason`, `status` in `data` (4.1's test, green).

## Observations (not defects)

- O1 (low, log noise and level): during an outage librdkafka's `FAIL` facility lines reach the log at `fail` (error) level
  (about 187 to 273 error lines in 5 minutes of tests), beside 2 warnings per second. The story's carry-over item asked for the
  client's level to be kept, so this is as specified, but a 30 s outage yields 67 warnings plus about 60 errors, which is loud for
  an alert that is meant to be actionable. Consider rate-limiting the repeat in `docs/production-path.md`.
- O2 (info): `docker compose stop worker` took 8.9 to 9.4 s when a send was in flight, i.e. it waits for the 10 s delivery
  timeout rather than aborting, as criterion 5 requires.

## e2e changes (QA-owned)

- New `e2e/tests/outbox-relay-failure-paths.spec.ts` (7 tests): outage rows and health, warning shape and count, delivery after
  recovery, privacy in log and traces, shutdown with a send in flight, resume, shutdown with the broker up.
- Coordinator corrections applied before finishing: (1) the Error producer span is asserted for at least one row attempted during
  the outage, not for every row, because a transient failure ends the batch so unattempted rows first send after recovery and have
  only a successful span (observed: the first raise has 3 spans, the other two one each); (2) the topic is asserted to hold at
  least one record per row with every copy carrying the row's CloudEvent `id` and the dispute ID as key, not exactly one, because
  AD-17 is at least once.
- `e2e/tests/outbox-relay.spec.ts`: the dashboard row name pattern is now `disputedesk-worker[^:]*: MSG kafka ...`. After the
  Worker has been restarted the dashboard names the resource `disputedesk-worker-<instance>`, which made 4.1's trace test fail
  when it ran after any Worker restart (its assertions are unchanged).
