## Criteria, four hops

Count columns below are D|T|A|O|K = Disputes, TimelineEntries, AuditLogEntries, OutboxMessages, IdempotencyKeys deltas.

### 1 Key required and well formed (400 `validation`, nothing written)
- Network: all 400 `application/problem+json`, type `.../problems/validation.md`, detail "The Idempotency-Key header must be one quoted string of 1 to 255 printable characters, such as "<uuid>"." for: no header; unquoted `abc`; unquoted uuid; `""`; empty header value; unterminated `"abc`; trailing garbage `"abc"x`; parameter `"abc";p=1`; sf-integer `123`; sf-binary `:YWJj:`; bad escape `"a\nb"`; non-ASCII (UTF-8 e-acute); tab inside; 256 characters; two `Idempotency-Key` header lines both quoted. A valid key with a body missing `reason` gets 400 with `errors.reason`; a valid key with malformed JSON gets 400; no key and an invalid body gets 400.
- Database: delta after all 18 requests `0|0|0|0|0`. The invalid-body cases wrote no key row either (the key check runs before the claim; a body failure runs before the filter claims).
- Accepted: a 255-character quoted key gives 201 (stored length 255). The escaped key `"h\"<uuid>\\z"` gives 201 and stores `h"<uuid>\z` (decoded sf-string).
- Order with a key present: bad antiforgery token 400, no cookie 401, unlinked C 403 `linking-required`; delta `0|0|0|0|0`.
- OpenAPI: `backend/openapi.json` declares `Idempotency-Key` as `in: header, required: true` on `POST /api/v1/disputes`.

### 2 Replay returns the original

Replays: the same bytes again; a reordered JSON with extra whitespace and an unknown property `unknownField`; and 2 seconds later. Every replay: status 201, body bytes identical (`cmp`, md5 `fe40ea01...`), `Location` identical, response headers identical apart from `Date` and `Set-Cookie`.
- Database: delta of the first request `1|1|1|1|1`; after three replays still `1|1|1|1|1`; rows for TXN-B-0021 `1|1|1|1`. The key row: `Completed`, `ResponseStatus` 201, `ResponseLocation` set, `ResponseBody` 626 bytes with md5 equal to the md5 of the body the client received, `ExpiresAtUtc` minus `CreatedAtUtc` = 1 day.
- The 201 body carries no `traceId` (it is not a problem body); the byte-for-byte traceId requirement is seen on the stored 4xx bodies in criterion 4.

## Standards check
- draft-ietf-httpapi-idempotency-key-header: 400 for a missing or malformed key, 422 for a reused key with a different payload, 409 for a concurrent request with the same key, replay of the original response. Matches.
- RFC 9651 sf-string parsing: quotes, `\"` and `\\` escapes accepted; bad escapes, non-ASCII, control characters, parameters, tokens, integers, binary and multiple lines refused. Matches.
- RFC 9110: status codes and `Location` on the 201 as expected; 4xx replays carry no `Location`. RFC 9457: all refusals are `application/problem+json` with `type`, `title`, `status`, `traceId`. RFC 9111: `Cache-Control: no-store` on 201 and replays. OWASP API1: B asking for A's key or A's transaction gets the same 404 as a nonexistent one.
- Sensitive data: EF Core logs show parameters as `'?'`, and the lost-race `Detail` is redacted.

## Findings
1. **Low: a lost unique-index race is logged at `fail:` level.** Each loser of the different-keys race (and each lost raise) emits `Microsoft.EntityFrameworkCore.Update[10000]` and `Database.Command[20102]` errors with `23505 duplicate key ... UQ_Disputes_AccountRef_TransactionId`, although the handler handles it and answers 409. In production that is 2 error lines per double click, which would trip an error-rate alert. Decide: filter those two event ids for the 23505 path, or accept and document. Not a data issue.
2. **Info: the 409 `idempotency-in-progress` carries no `Retry-After`.** The draft does not require one; a client cannot tell how long to wait. A held request frees within 5 s on core-banking failure, so a short `Retry-After` would be accurate. Optional.
3. **Info: a leftover `InProgress` key row remains on the dev stack** (attempt 2, API unreachable at the time, TXN-B-0021 key). It expires in 24 hours and any retry would take it over after 60 s. A raised dispute for that transaction exists from attempt 3 (a separate key), so it is only residue.
4. **Info, pre-existing:** ZAP warns the same two rules as 3.1.
