# Terraform dev environment and OIDC deploy

## Description

Adds the Terraform for the one AWS dev environment (AD-28: a bootstrap root for the state bucket, the named modules and one root `envs/dev`), the EC2 user data that prepares the instance, the manual `deploy.yml` that assumes the GitHub OIDC role and waits for SSM Run Command's result, and the instance's deploy script that writes `.env` from SSM SecureStrings and starts story 7.4's stack by image digest. The AWS account does not exist, so the story closes on `terraform fmt -check`, `terraform validate` and `terraform test` plans against mocked providers, plus the written apply, deploy, rollback, post-deploy check and destroy procedure; no AWS command is ever run (decided 2026-10-30). The images it deploys are the ones story 7.3 publishes to GHCR; this story only consumes them (AD-32).

## Requirements

Verify: `terraform fmt -check -recursive infra/terraform`; `terraform init -backend=false`, `terraform validate` and `terraform test` in both `infra/terraform/bootstrap` and `infra/terraform/envs/dev` (every run `command = plan` against `mock_provider "aws"`, decided 2026-10-30); a grep finding no `prevent_destroy` under `infra/terraform` (a lifecycle setting plans cannot show); all pass locally and in a new CI `terraform` job; `actionlint` passes; `infra/aws/deploy.test.sh` passes in the CI `platform` job; no step reaches an AWS endpoint or needs credentials.

How the plans assert (Terraform 1.11 or later, *Tests: mocks*): `mock_provider "aws"` sets `override_during = plan`, with `mock_resource` defaults for every computed attribute an assertion reads (`arn`, `id`, `public_dns` and the like), so they are known in a plan; `override_data` gives every data source that is indexed or decoded (availability zones, the AMI, the CloudFront origin-facing prefix list, the managed CloudFront policies, region, caller identity); IAM, KMS and S3 policies are written with `jsonencode()` (Terraform, *jsonencode*), never an `aws_iam_policy_document` data source, so `jsondecode` in an assertion reads the real document; managed-policy lookups are asserted by their `name`.

Inputs:
- Terraform variables of `envs/dev`, each with a `validation` block: `aws_region` (one of `us-east-1`, `us-west-2`, `eu-west-1`, `eu-central-1`; no default); `github_repository` (`<owner>/<name>`, `^[A-Za-z0-9-]+/[A-Za-z0-9._-]+$`); `budget_limit_usd` (a whole number from 1 to 100); `budget_alert_email` (one address, a simple `^[^@\s]+@[^@\s]+$` check; personal data, so it is passed as `TF_VAR_budget_alert_email`, the existing `.gitignore` already ignores `*.tfvars` but `*.tfvars.example`, and tests use `example.com`); `ssm_path` (default `/disputedesk/dev`, starts with `/`, no trailing `/`); `dataprotection_ssm_path` (default `/disputedesk-dataprotection/dev`, starts with `/`, no trailing `/`, and not under `ssm_path`, so the deploy never reads the key ring).
- Terraform variables of `bootstrap`, each with a `validation` block: `aws_region` (the same list); `state_bucket_name` (3 to 63 characters, `^[a-z0-9][a-z0-9-]{1,61}[a-z0-9]$`, no dots; Amazon S3, *Bucket naming rules*). `envs/dev`'s backend block holds no bucket or region (a backend block cannot read variables); `terraform init -backend-config="bucket=…" -backend-config="region=…"` passes them (Terraform, *Backend configuration: partial configuration*).
- Generated values: the origin-verify value and the RDS master password are each a `random_password` with `length = 64` and `special = false`, so they meet story 7.4's `^[A-Za-z0-9]{32,128}$` and RDS's master-password rules (no `/`, `@`, `"` or space); the RDS master user name is the constant `dbmaster`, shared by the database module and `deploy.sh`.
- `deploy.yml` input `sha`: the full 40-character lower-case commit SHA (`^[0-9a-f]{40}$`), reaching scripts only through `env:` and checked before any AWS step; the workflow derives the image tag as story 7.3 defines it (`sha-` plus the first 12 characters) and resolves each of the five images to its digest; a SHA with no published image fails the run before the SSM command. Repository variables, set from Terraform outputs by the README's procedure: `AWS_DEPLOY_ROLE_ARN`, `AWS_REGION`, `DEPLOY_INSTANCE_ID` and `DEPLOY_DOCUMENT_NAME`.
- SSM parameters under `ssm_path` that a person creates as SecureStrings before the first deploy, each generated from `[A-Za-z0-9]` (plus `-` for the Zitadel admin password, base64 for the HMAC key) and created with `--key-id` naming the customer-managed key (the README lists each with its bound): `APP_DB_PASSWORD`, `ZITADEL_DB_PASSWORD`, `LOGIN_SESSION_COOKIE_SECRET`, `ZITADEL_MASTERKEY`, `ZITADEL_ADMIN_PASSWORD`, `LINKING_OTP_HMAC_KEY`, `MAILPIT_UI_AUTH` (story 7.4's bounds), and `QA_DB_PASSWORD` (32 to 128 characters of `[A-Za-z0-9]`; `infra/db/10-roles-and-databases.sh` reads it for `qa_readonly`). Terraform writes the rest to SSM under `ssm_path`, every SecureString with `key_id` set to the customer-managed key: `APP_HOST`, `AUTH_HOST`, `MAILPIT_HOST`, `DB_HOST`, `OTEL_LOG_GROUP`, `DATAPROTECTION_SSM_PATH`, `DATAPROTECTION_KMS_KEY_ID`, `GATEWAY_ORIGIN_VERIFY` and `RDS_MASTER_PASSWORD`.
- `deploy.sh`'s inputs, by source. `.env` holds exactly story 7.4's `AWS_INPUTS` (`infra/aws/input-bounds.sh`), each checked with that file's `within_bounds`, which `deploy.sh` sources unchanged:
  - from SSM by name, the allow-list: the seven person-created secrets above and the eight Terraform-written values other than `RDS_MASTER_PASSWORD`; any other parameter under `ssm_path` is ignored;
  - from its five arguments: `API_IMAGE`, `WORKER_IMAGE`, `GATEWAY_IMAGE`, `CORE_BANKING_IMAGE`, `PROVISION_IMAGE`;
  - script constants: `RDS_CA_BUNDLE` and `GATEWAY_REALIP_CONF`, two fixed paths on the instance;
  - from the document command, rendered by Terraform: `AWS_REGION` and `ssm_path`.
  - Init only, never in `.env`: `QA_DB_PASSWORD` (its bound checked in `deploy.sh`, since 7.4's file lists only the override's inputs) and `RDS_MASTER_PASSWORD`, read by name and passed only in the init's environment.

## Boundaries

- Never run an AWS command, `terraform apply`, `terraform plan` against a real provider, or `deploy.yml`; tests use mock providers and stubs only.
