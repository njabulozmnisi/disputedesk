# ad-012: CI and deploy follow GitHub flow

**Status:** accepted (2026-11-05). The human decided the choices below on 2026-11-05, before and after the decision-time challenge (`docs/verification/ad-012-challenge.md`, RETHINK: its three `[decision]` points are answered in the table; its `[story]` points are folded into the Decision).

**Context.** CI runs on every push to `main` and `story/**` and on pull requests, which are never used. A story reaches `main` by `scripts/push-and-watch.sh` and `scripts/merge-story.sh`, which fast-forward `main` to the branch head once CI and Security pass on it; `main` has no branch protection. A `changes` job (`scripts/ci-changes.sh`) skips the heavy jobs on a docs-only push. The five images are built twice: in Security's Trivy job and in CI's `publish`. The Compose install block appears three times and the Trivy install twice. Deploy is a manual `workflow_dispatch` that takes a typed SHA and resolves the image digests again. A green run takes about 9 minutes (CI) and 3 minutes (Security), so the aim is a plainer shape, not speed.

**Human decisions, 2026-11-05.**

| Question | Answer |
| --- | --- |
| Branching model | GitHub flow: short-lived `feature/<story>` branches, a pull request to `main`, checks on the pull request, deploy on merge. Not strict Gitflow (no `develop`, `release/*` or `hotfix/*`). |
| Merge method | Squash merge, with the branch required to be up to date with `main`. |
| Deploy on merge while no AWS account exists | Wired, switched off: the deploy job runs after `publish` on `main` only when the repository variable `DEPLOY_ENABLED` is `true`; until then it writes a notice and makes no AWS call. |
| Pre-merge image scan (challenge; PRD NFR-SEC-8, R33) | Kept: Security builds and Trivy-scans the five images on every pull request as a required check, and `publish` builds, scans and pushes them once on `main`. Two builds at two gates: one blocks an unsafe merge, the other scans the bytes published. |
| AD-28 (challenge; R38) | Amended: deploy runs after `publish` on `main` when enabled, and the deploy role trusts the subject `environment:dev`, with `dev` restricted to `main`. Offline limit: the mocked Terraform tests pin the new subject; the live role assumption is proved only by the first deploy. |
| The commit on `main` (challenge; AGENTS.md Commits) | Replaced: pull-request checks test GitHub's merge of the up-to-date branch, and `main`'s own run builds, scans and publishes the squash commit. The fast-forward rule ("main gets the exact commit CI tested") goes. |
| CodeQL findings (NFR-SEC-8, R33) | The ruleset also carries the `code_scanning` rule for CodeQL (high or higher security alerts, error alerts), so a finding blocks the merge; if GitHub does not offer it on a user-owned public repository, the gap goes to `docs/production-path.md`. |

**Decision.**

1. **Pull requests carry the checks.** `ci.yml` runs on `pull_request` (GitHub tests the would-be merge commit) and on `push` to `main`; the `story/**` push trigger goes. Every check job runs on every pull request; the `changes` job and `scripts/ci-changes.sh` go. One job, `ci-passed`, needs every check job, runs with `if: always()` and fails unless each succeeded; it is the CI required status check (GitHub Docs, *About status checks*; a skipped job counts as passing, so the gate reads each result).
2. **A ruleset protects `main`.** It requires a pull request, the two gate checks by name (`ci-passed` and `security-passed`), an up-to-date branch, and blocks force pushes and deletion (GitHub Docs, *About rulesets*). Squash is the only merge method because the repository settings disable merge commits and rebase merging (the linear-history rule alone also allows rebase); auto-merge and deleting the head branch on merge are enabled. No merge queue: GitHub offers it only on organization-owned repositories.
3. **Images: scanned before merge, built for release once.** Security's image job builds and Trivy-scans the five images on every pull request, as today. On `push` to `main`, `publish` builds, Trivy-scans and pushes them once, tagged by SHA, and exposes the five digests as job outputs. Security also gets a gate job, `security-passed`, that needs each of its jobs and fails unless each succeeded; gitleaks, CodeQL, the filesystem and config scan and the vulnerable-package check stay, on pull requests, `main` and the weekly schedule.
4. **Deploy follows publish.** `deploy.yml` becomes a reusable workflow (`workflow_call`) that takes the SHA and the five digests; its called job sets `environment: dev` (GitHub Docs, *Reuse workflows*) and one concurrency group with `cancel-in-progress: false`. CI's `deploy` job always runs after `publish` on `main`: when `vars.DEPLOY_ENABLED != 'true'` it writes a notice and stops, otherwise it calls the reusable workflow. `workflow_dispatch` stays for rollback: redeploy a previous SHA, whose digests it resolves as today. The environment `dev` allows only `main`. The deploy role's OIDC trust moves from the subject `ref:refs/heads/main` to `environment:dev`, keeping the exact audience and the immutable repository identity; the Terraform assertion and the one-time check in `infra/terraform/README.md` follow (GitHub Docs, *OpenID Connect reference* and *Configuring OpenID Connect in Amazon Web Services*). This amends AD-28.
5. **Repeated steps become composite actions.** The Compose install (with its pinned version and SHA-256) and the Trivy install each become one local composite action under `.github/actions/` (GitHub Docs, *Creating a composite action*).
6. **The supervisor merges through the pull request.** Once every stage has passed, `gh pr create` and `gh pr merge --squash --auto` replace `scripts/push-and-watch.sh` and `scripts/merge-story.sh`; the supervisor then confirms the pull request merged and `main`'s run succeeded. A story stacked on an unmerged story opens its pull request against that story's branch; when the base squash-merges, the stacked branch is rebased onto `main` (`git rebase --onto main <base>`), its pull request is retargeted to `main`, and its checks run again. AGENTS.md's Commits section, the skills and `docs/process/agentic-sdlc.md` follow (a rule change, so the human approves that diff).
7. **Rollout order.** The new triggers, gate jobs and composite actions land first, while the `story/**` trigger still runs; the ruleset and repository settings are applied once a pull request shows both gates reporting; then the `story/**` trigger and the two scripts go.

**What does not change.** The check content (build, tests, drift checks, lint, e2e journeys and the ZAP baseline, Terraform checks, scans, the pull-request image scan), actions pinned by full commit SHA, least-privilege permissions, the caches, and images tagged by SHA and deployed by digest.

**Options rejected.**

- *Strict Gitflow.* Its author's 2020 note advises a simpler workflow for continuously delivered software, and Atlassian calls it a legacy workflow that is hard to use with CI/CD.
- *Fast-forward to `main` from the command line, as today.* A ruleset that requires a pull request blocks it; the human chose pull requests.
- *Workflow-level `on.paths` to skip docs-only changes.* A required check whose workflow does not run stays pending (GitHub Docs); `dorny/paths-filter` with a gate works but adds a third-party action for about 9 minutes saved per docs change.
- *A merge queue.* Not available on a user-owned repository; for one maintainer, "require branches up to date" gives the same guarantee.

**Sources.** `~/disputedesk-research/research_notes/ci-simplification/external-research.md` (outside the repository) holds the cited primary sources: GitHub Docs on workflow triggers, status checks, rulesets, merge methods, environments, reusable workflows, composite actions and OIDC; Driessen's 2020 note; Atlassian on Gitflow; DORA on trunk-based development.
